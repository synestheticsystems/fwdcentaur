# Decisions

Every ruling the project has recorded, cited by its number (`D12`). A ruling attached to a scope governs that scope's work, and one attached to none governs the whole project: the project-wide rulings come first, then each scope's under its name. Accepted rulings are in force; proposed ones wait for a ruling; rejected, superseded and repealed ones stay, so that what cited them can be found.

## Project-wide

### Accepted

- **D1: The vision** (product, 2026-09-24, decided by dnorman, recorded by lead-fwd): a task graph stored as fine-grained as possible with dependencies and motivations; a VS Code extension with a graph panel (add, remove, propose, comment) and line annotations in code and diff views that are stored, linkable to tasks, and queued to an agent inbox; a CLI intended for agents; a list of active scopes per team member with status, user, intention, working directory (not necessarily persisted to the server) and assigned tasks; two agent roles, implementing and supervising. Free to self-host; a business on top.
  - Context: opening brief
- **D2: Storage: a local Ankurah node from day one** (architecture, 2026-09-24, decided by dnorman, recorded by lead-fwd): Storage: a local Ankurah node from day one. No JSON file stage. Ankurah is Daniel's project, so fwdcentaur has carte blanche to drive features into it.

- **D10: Messages, notifications and tasks** (2026-09-24, decided by dnorman, recorded by lead-fwd): messages (comments) and tasks are durable, visible in the UI, each with one status field; notifications are created only when a specific party needs to know about a thing, are thin (recipient, type, status Unread/Read/Dismissed, Json `target` and `originator`), and carry no disposition; Json `context` maps hold relationship context. Tasks therefore have a single status (Draft, Proposed, Open, InProgress, InReview, Done, Cancelled, Rejected) with assignment as a separate relation and readiness derived; the separate Annotation and Proposal entities are dropped (comments on code are messages with an anchor in their context).

A task created in response to a message notifies the message's author that the task exists, which beats a reply they would have to read before looking at the task.
