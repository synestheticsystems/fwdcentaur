# Mainstream issue trackers: hierarchy, dependencies, agents, noise, limits

Research note, 2026-09-24. Compiled by a research agent against fetched primary sources; items marked "unverified" could not be confirmed against a primary source. Dates are the source's publication date.

Question this note answers: could GitHub Issues (or Linear, or a self-hostable tracker) serve as the v1 store for a fine-grained, agent-driven task graph, and what breaks first?

## 1. GitHub Issues

**Hierarchy and dependency model.**
- Sub-issues: GA since the "Evolving GitHub Issues and Projects" changelog (2025-04-09). Limits: 100 sub-issues per parent, 8 nesting levels, cross-repository parents allowed (docs, "Adding sub-issues"). REST: `GET .../issues/{n}/parent`, `GET/POST .../sub_issues`, `DELETE .../sub_issue`, `PATCH .../sub_issues/priority`. GraphQL: `addSubIssue`, `removeSubIssue`, `reprioritizeSubIssue`; `Issue.parent`, `subIssues`, `subIssuesSummary`.
- Issue types: 25 per organization, defaults task/bug/feature; org-only (docs). REST support since 2025-03-18.
- Issue fields (new, distinct from Projects fields): typed org-level metadata (Priority, Effort, Start/Target date, custom), GA 2026-07-02, readable/writable through the GitHub MCP server. This is where a "why"/scope value could live without a Project.
- Dependencies ("blocked by"/"blocking"): public preview 2025-07-10, GA 2025-08-21. Cap: 50 issues per relationship type per issue. REST: `GET/POST .../dependencies/blocked_by`, `DELETE .../dependencies/blocked_by/{issue_id}`, `GET .../dependencies/blocking`. GraphQL `addBlockedBy(issueId, blockingIssueId)`, `Issue.blockedBy/blocking`; webhooks supported. Search: `is:blocked`, `is:blocking`, `blocked-by:`, `blocking:`. gh CLI v2.94.0 (2026-06-10) added `--blocked-by/--blocking/--parent/--type` and JSON fields. "Blocked" is advisory only: the docs describe a "Blocked" icon on boards and the Issues list, nothing prevents closing. Cross-repository dependencies: not stated anywhere in the docs; third-party orchestrator projects report native edges cannot cross repos (unverified). Projects still has no blocked-by column and there is no graph/dependency visualization anywhere in GitHub (community feedback thread #165749, "Issue Dependencies public preview feedback").
- Projects v2: 50,000 items per project (GA 2025-04-09, up from 1,200); GraphQL-only API; draft issues generate no assignment/mention notifications until converted to real issues (docs, "Converting draft issues").

**Agents.** Copilot's cloud agent (renamed from "coding agent" during 2026) is assigned by picking it in the Assignees dropdown; it works in Actions, opens a draft PR, and reports through PR body, comments, and session logs. Mission control (2025-10-28) lives at github.com/copilot/agents, GitHub Mobile, VS Code, and the CLI. Agent HQ status today: Claude and Codex are in public preview on Copilot Pro+ and Enterprise since 2026-02-04; you can assign an issue to Claude, Codex, Copilot, or all three; each session costs one premium request. Programmatic entry: the agent tasks REST API `POST /agents/repos/OWNER/REPO/tasks` (prompt, base_ref; states queued/in_progress/completed/failed/idle/waiting_for_user/timed_out/cancelled), public preview 2026-05-13 for Business/Enterprise, extended to Pro/Pro+/Max 2026-06-04, user-to-server tokens only. The official GitHub MCP server exposes `add_sub_issue`, `get_sub_issues`, and issue fields.

**Notifications (what actually fires).** You are auto-subscribed to a thread when you open it, are assigned, comment, are @mentioned (user or team), or change its state. Repository watching is a separate layer: "All activity" or Custom with "Issues" ticked notifies you of every issue, including pre-existing ones and regardless of author. Custom watch options are exactly Issues / Pull requests / Releases / Security alerts / Discussions; there is no label filter in the watch UI (community request #16645 open since May 2022 with no staff response; label filters exist only in the GitHub Slack/Teams apps). Auto-watch on joining a repo or team is on by default. Bot-authored issues notify like any other, which is why the inbox filter `author:app/dependabot` exists; supported inbox qualifiers are `repo:`, `is:`, `reason:` (assign, author, comment, participating, mention, review-requested, state-change, team-mention, ci-activity, ...), `author:`, `org:`, with no NOT/exclusion syntax. Practical tactics teams use: (a) put bot-generated issues in a separate repo, since watch/ignore is per-repo; (b) give the agent a GitHub App identity so `author:app/<name>` filtering works; (c) Renovate's pattern of one long-lived "Dependency Dashboard" issue instead of many issues; (d) draft issues in a Project, which are silent; (e) label-triggered Actions or Slack label filters for opt-in routing.

**Rate limits (docs, current).** Primary REST: 5,000 requests/hour per user token; GitHub App installation 5,000 plus 50 per repo and per user beyond 20, capped at 12,500; Enterprise Cloud 15,000; `GITHUB_TOKEN` 1,000/hour/repo. GraphQL: 5,000 points/hour (10,000 Enterprise), max 500,000 nodes per call, `first/last` at most 100. Secondary limits (shared): 100 concurrent requests; 900 REST points/minute; 2,000 GraphQL points/minute; **80 content-creating requests/minute and 500/hour**; 90 s CPU per 60 s. The sub-issue and dependency POST/DELETE endpoints each carry the explicit "creating content too quickly may result in secondary rate limiting" warning, so each edge write counts against the 500/hour budget.

**Line-anchored comments.** Only two objects anchor to code: PR review comments (`path`, `line`, `side`, optional `start_line/start_side` for ranges, `commit_id`, or `subject_type: file` for file-level; `position` is deprecated) and commit comments (`path` + `position` on a commit SHA). Issues and Discussions have only markdown permalinks. When a later commit touches a commented line, the comment disappears from Files changed and appears in the Conversation tab flagged "Outdated" showing the old code; GitHub staff: automatic tools "have no way of knowing if the comment targeted at the old line still makes sense on the new line" (community #23138). The new Files changed page (default since 2026-01-22) allows comments on unchanged lines of changed files (preview 2025-09-25), plus a comments panel (2026-02-19) and side-by-side (2026-03-19).

Sources: docs.github.com sub-issues, issue-dependencies (REST), rate-limits, inbox-filters, pulls/comments, commits/comments; github.blog changelogs 2025-04-09, 2025-08-21, 2025-10-28, 2026-02-04, 2026-05-13, 2026-06-10, 2026-07-02.

## 2. Linear

- Relations: related, blocked by, blocks, duplicate (API enum also has `similar`); GraphQL `issueRelationCreate`. Community reports that creating a relation on a pair that already has one converts the edge rather than adding a second (unverified against docs). Sub-issues inherit team/priority/project; nested sub-issues shown in all list views since 2026-02-09 (Linear on X); no documented depth cap. No issue-level dependency graph; only project-level dependencies drawn on the project timeline (changelog 2024-08-08).
- Agents: "app users" via OAuth `actor=app`, not billable; AgentSession/AgentActivity model (thought, action, elicitation, response, error), must emit a thought within 10 seconds of delegation; delegation keeps the human as owner. Still labelled Developer Preview (developers/agents). Directory (linear.app/agents): Linear Agent, Cursor, OpenAI Codex, Devin, Sentry Seer, ChatPRD, Oz by Warp, Factory, Charlie, Ranger, Tembo. Claude Code is not a listed agent, but "Coding sessions" (changelog 2026-06-11) run Claude Code or Codex in a Linear-managed sandbox when you delegate an issue to Linear, attach the diff to the issue, and need Basic+ plus AI credits ($20 x users initially); deeplinks to Claude Code/Codex/Conductor/Cursor since 2026-02-26; Linear Agent itself launched in beta 2026-03-24; Loops 2026-09-14.
- MCP: `https://mcp.linear.app/mcp` (streamable HTTP, `/readonly` variant, SSE deprecated), OAuth 2.1; native in Claude, Cursor, VS Code, Windsurf, Zed, Jules, Codex, v0. Tools cover find/create/update issues, projects, comments; relation tools not documented.
- Webhooks: issues, comments, labels, projects, cycles, documents, initiatives, customers, agent sessions; 3 retries (1 min, 1 h, 6 h). IssueRelation is not in the documented list.
- Rate limits: API key 2,500 requests/hour/user and 3M complexity points/hour; OAuth app 5,000 requests/hour per user or app user, 2M points; 10,000 points max per query.
- Noise: subscriber-only model (creator, assignee, @mentioned, manual); the docs describe no team-wide "all new issues" broadcast, so agent churn is quiet by default.
- Pricing: Free $0 with a **250-issue cap**, 2 teams, unlimited members; Basic $10, Business $16/user/month (annual); Enterprise custom. Not self-hostable.

## 3. Jira (brief)

Standard issue links (blocks / is blocked by) on all plans; the Plans "Dependencies view" (tiles with arrows, red for off-track, filter/group) is Premium and Enterprise only. Rovo agents can be set as assignee, @mentioned, attached to workflow transitions, or to board columns; output lands privately in the work item's "Agents" section until published; Rovo credit allowances start 2026-12-03. Rovo Dev (coding agent) went GA Oct 2025 at $20/developer/month with 2,000 credits. Sources: support.atlassian.com (dependencies view; "Collaborate on work items with AI agents"), atlassian.com/software/rovo-dev/pricing.

## 5. Trackers with a real dependency-graph UI

- Height: shut down 2025-09-24, data deleted, no migration path.
- Kitemaker: acquired by ClickUp (2025-05-06), service ended 2025-09-01.
- Shortcut: auto-generated Mermaid relationship chart on Epic and Iteration pages showing blocks/blocked-by with state colouring (blog, 2025-03-14).
- YouTrack: "Issue Dependencies" marketplace app renders upstream/downstream links as graph, tree, or timeline; YouTrack 2025.2 lets apps draw hierarchical link graphs.
- Jira Plans dependencies view (Premium), Asana Timeline arrows (red when late, one notification when all blockers finish), Fibery dependencies on Timeline (2025-02-13), Linear project-level timeline lines.
- Agent-native, git-adjacent: Beads (steveyegge/beads, MIT, 27.4k stars, now Dolt-backed as of v1.3.0) with `blocks`, `parent-child`, `discovered-from`, `related` edges and `bd ready` for unblocked work; community TUIs draw the DAG; lighter forks include wedow/ticket, Beans, Trekker. Dagobert stores tasks as a Markdown DAG with "ready when all dependencies done."
- "Rhythm": could not identify a tracker by that name with a dependency graph; unverified. No rigorous research on task-DAG UIs for engineering work surfaced; the Beads ecosystem is the closest prior art for the agent workflow.

## 6. Discussions, Projects, and the separate-repo trick

GitHub Discussions have GraphQL-only APIs (a github/docs issue from 2026-05-05 confirms REST is missing), no hierarchy or dependency edges, and their own custom-watch toggle; they are a poor graph node. Projects v2 draft issues are the quietest native object (no notifications until converted, 50,000 items, GraphQL-only) but cannot hold dependency or sub-issue edges, which exist only between real issues. A private "tracker" repo is the cleanest isolation because watching, ignoring, and `repo:` inbox filters are all per-repo, and sub-issue parents can cross repos; the unresolved question is whether dependency edges can cross repos, which nothing in the docs confirms.

## Assessment: can GitHub Issues be the v1 store?

Yes for a first release, but only inside a dedicated tracker repo with the agent acting as a GitHub App, and with the expectation of outgrowing it. What breaks, in order:

1. **Noise breaks first, and immediately, if the graph lives in the code repo.** Every teammate who auto-watched the repo on join receives one notification per node the agent creates, and there is no label filter or exclusion syntax to save them. Moving the graph to a separate repo removes this entirely; humans then subscribe to individual nodes by being assigned or @mentioned, which matches the "inbox" design.
2. **Write rate limits break next, during bulk graph creation or re-planning.** Every node is one content-creating request and every parent link or blocked-by edge is another, capped at 80/minute and 500/hour per token. A 500-node, 800-edge project costs about 1,300 creating requests, so roughly 2.6 hours of wall-clock minimum, and re-planning that regenerates edges hits the same wall. Reads are cheap: a 1,000-issue graph with `blockedBy(first:50)` and `subIssues(first:100)` costs a few dozen GraphQL points against 5,000/hour.
3. **Expressiveness is the ceiling you cannot engineer around.** Only two edge types exist (parent-child, blocked-by), 50 blockers per issue, 8 levels, 100 children, blocking is advisory, cross-repo blocking is unverified, and there is no motivation/"why", discovered-from, or scope edge; issue fields (GA July 2026) can carry a "why" string and a scope value but not typed edges. Line anchors exist only on PR review and commit comments and go "Outdated" on the next push, so the VS Code annotation feature needs its own anchor store from day one.
4. **Latency is fine.** Webhooks fire on issue, sub-issue, and dependency changes, and Copilot/Claude/Codex sessions already start from an issue assignment.

Linear is the strongest hosted alternative on noise (subscriber-only) and agent model (app users, sessions, MCP), but the 250-issue free cap and no self-hosting rule it out as a zero-setup default. Among self-hostables, OpenProject has the richest typed edges and Vikunja the lightest API, but none delivers a graph UI or agent inbox, so the custom-backend path mainly buys typed edges and unlimited write throughput.
