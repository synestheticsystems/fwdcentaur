# Inbox delivery to mid-task agents, and running a supervisor: platform mechanics and prior art

Research note, 2026-09-24. Compiled by a research agent from official docs fetched that week unless marked otherwise. Three items are flagged unverified because the agent's search budget ran out.

## A. Claude Code mechanisms usable for inbox injection and stop-blocking

Source: the hooks reference at code.claude.com/docs/en/hooks (current for v2.1.26x). All hook events fire in terminal, IDE, Desktop, `-p`, and cloud sessions; a `-p` run loads project hooks unless `--bare`.

**Events (32 in 2026):** SessionStart, Setup, UserPromptSubmit, UserPromptExpansion, PreToolUse, PermissionRequest, PermissionDenied, PostToolUse, PostToolUseFailure, PostToolBatch, Notification, MessageDisplay, SubagentStart, SubagentStop, TaskCreated, TaskCompleted, Stop, StopFailure, TeammateIdle, InstructionsLoaded, ConfigChange, CwdChanged, DirectoryAdded, FileChanged, WorktreeCreate, WorktreeRemove, PreCompact, PostCompact, PreModelSwitch, PostModelSwitch, Elicitation, ElicitationResult, SessionEnd.

**Injecting context.** `hookSpecificOutput.additionalContext` is honored on PreToolUse, PostToolUse, PostToolUseFailure, PostToolBatch, UserPromptSubmit, SessionStart, SubagentStart, Stop, SubagentStop (and PermissionRequest). On exit 0, plain stdout is also added as context for UserPromptSubmit, UserPromptExpansion, SessionStart, PostModelSwitch. Verbatim: "Plain stdout and the `additionalContext` value are each injected as a system reminder that starts with the hook's name." Each string is capped at 10,000 characters; overflow is written to a file and replaced by the path plus a 2,000-char preview, and "Claude Code doesn't ask Claude to read the file." The best per-model-call injection point is `PostToolBatch`: "A full batch of tool calls resolves, once per batch before the next model call" (SDK hooks page). Shape:

```json
{"hookSpecificOutput":{"hookEventName":"PostToolBatch","additionalContext":"<unread inbox messages>"}}
```

**Blocking Stop.** Stop input carries `stop_hook_active`, `last_assistant_message`, `background_tasks`, `session_crons`. Decision control is top-level:

```json
{"decision":"block","reason":"Must be provided when Claude is blocked from stopping"}
```

Exit 2 with the reason on stderr is equivalent. A softer form keeps the turn going without a hook-error notification: `{"hookSpecificOutput":{"hookEventName":"Stop","additionalContext":"Please run the test suite before finishing"}}`. Both go through the same loop protection: "Claude Code overrides the hook and ends the turn after 8 consecutive blocks." Stop does not fire on user interrupt; `/goal` is a built-in prompt-based Stop hook. SubagentStop uses the same fields; `TeammateIdle`/`TaskCompleted` block via exit 2, or `{"continue":false,"stopReason":"..."}` stops the teammate outright. Universal fields: `continue:false` + `stopReason` halts everything; `systemMessage` is user-facing.

**Hook handler types** beyond `command`: `http` (event JSON POSTed to a URL; response body uses the same output JSON; gated by `allowedHttpHookUrls`), `mcp_tool`, `prompt` (single-turn model evaluation), `agent` (experimental). Fields: `if` (permission-rule syntax), `once`, `async` (results "delivered on the next conversation turn"; cannot block; killed at `-p` teardown), `asyncRewake` (background, "wakes Claude on exit code 2" with stderr as a system reminder). Default timeout 600 s, 30 s on UserPromptSubmit.

**How a hook would poll an inbox:** a `PostToolBatch` + `UserPromptSubmit` command hook runs an inbox-pop command and emits `additionalContext`; a `Stop` hook re-checks and returns `decision:"block"` with the unread text as `reason` while `stop_hook_active` is false or a bounded counter is under 8. Resume caveat: injected text is replayed from the transcript on `--resume`, not re-run.

**Three push paths exist that are better than polling:**

1. *Cross-session messaging* (v2.1.224+, code.claude.com/docs/en/cross-session-messaging). Each session binds a Unix-domain inbox socket, exported to hooks and Bash as `CLAUDE_CODE_MESSAGING_SOCKET` (token in `CLAUDE_CODE_MESSAGING_TOKEN`); the docs explicitly cover "when you want a script or hook to post into a session." Delivery timing: "The receiving Claude reads the message between tool calls during an active turn, so a running tool is never interrupted. When the receiving session is idle, Claude Code starts a new turn with the message." `-p` sessions bind the socket (not `--bare`); unattended workers need `--settings '{"crossSessionInbound":"accept"}'` or the default hold/approve rules apply. Receipts: the sender is told when a message is held, delivered, denied, or expired. Limits: ~1M chars, burst refusal, 50-message queue, identical-repeat dropping, loop throttling. Wire format is not in the docs; the third-party `ccsock` Go package (v0.1.1, 18 Aug 2026, pkg.go.dev/github.com/PeterSR/claude-code-socket-transport) documents one JSON object per line then half-close: `{"msgV":1,"msg_id":"<uuid>","type":"user","message":{"role":"user","content":"..."},"priority":"now|next|later","from":"uds:...","session_id":"<uuid>"}`, optional first line `{"type":"auth","token":"..."}`, and `peer_message_status` receipts. Treat the format as reverse-engineered and version-fragile.
2. *Channels* (research preview, code.claude.com/docs/en/channels-reference). An MCP server declares `capabilities.experimental['claude/channel']` and emits `notifications/claude/channel` with `{content, meta}`; Claude sees a channel-tagged block. Timing is weaker: "Events queue into the session and are processed in order. If several notifications arrive while Claude is busy, they're delivered together on the next turn." No ack ("Claude Code doesn't acknowledge notifications"), silent drop if not enabled, allowlisted plugins only (custom servers need `--dangerously-load-development-channels server:<name>`), not on Bedrock/Vertex/Foundry, works with `-p`, optional permission relay so a remote party can approve tool use.
3. *Streaming input / SDK.* `claude -p --input-format stream-json` and the Agent SDK queue user messages; the TypeScript reference states that if "Claude Code picks up a regular message of yours between tool calls, the turn answers that message from then on," and `interrupt()` returns a receipt. `--resume <id>` works from any directory (v2.1.223), SIGTERM exits 143 and resume "continues the turn that SIGTERM left unfinished," `--permission-prompts none` (v2.1.259) for unattended runs.

Adjacent facts: agent teams (experimental flag, interactive only) use mailbox files at `~/.claude/teams/{team}/inboxes/{agent}.json`; the `Monitor` tool watches a script or WebSocket and "Claude interjects when an event arrives" (5-min default deadline, 10 min max under `-p`); session cron (`/loop`, `CronCreate`) fires "between your turns," 1-min minimum, 7-day expiry; Desktop scheduled tasks run locally at 1-min granularity in fresh sessions; Remote Control makes "outbound HTTPS requests only and never opens inbound ports," registers and "polls for work," and "Prompts you send mid-turn" are queued; the `claude agents` supervisor daemon keeps background sessions alive, restarts crashed ones, and exposes `claude agents --json`. Desktop task chips: Claude "offers the work as a task chip in the chat. Click the chip to start that work in a new session with its own worktree."

**Context-cost argument (MCP vs CLI).** Anthropic, "Code execution with MCP" (4 Nov 2025): loading all tool definitions plus intermediate results cost 150k tokens vs 2k with code APIs (98.7%). "Advanced tool use" (24 Nov 2025): Tool Search Tool cuts ~77k to ~8.7k tokens (85%). Mario Zechner (2 Nov 2025): Playwright MCP is "21 tools using 13.7k tokens" vs a 225-token README of CLI scripts; a July 2026 mcpservers.org roundup says his later benchmark found comparable success and cost once tool design was controlled. MCP 2026-07-28 removed sessions and the initialize handshake, deprecated sampling/roots/logging, moved server-initiated elicitation into "multi round-trip requests," and replaced GET streams with `subscriptions/listen`. Unverified: a Yegge post arguing CLI over MCP (Beads ships both `bd` and `beads-mcp`), and Eric Holmes's "MCP is dead" (Feb 2026, seen only secondhand).

## C. Prior art: agent messaging and supervisors

**Protocols.** A2A 1.0: tasks with states including `INPUT_REQUIRED`, `contextId`/`taskId`/`referenceTaskIds` for threading, webhook push configs, "All implementations MUST deliver events in the order they were generated," no ack primitive. MCP 2026-07-28: `subscriptions/listen` for opted-in change notifications; tasks moved to an extension polled via `tasks/get` with `tasks/update` for client input. AGNTCY SLIM: point-to-point, group, and RPC patterns; names are `organization/namespace/service/<hash-of-public-key>`; MLS encryption; ordering not documented.

**Gas Town / Beads (Yegge).** Mail is stored as beads and delivered through Claude Code hooks that Gas Town writes and passes with `--settings`: `mail-check` on UserPromptSubmit, `session-prime` on SessionStart, `pre-compact-prime` on PreCompact, `costs-record` on Stop; hook-less runtimes get a startup fallback (`gt prime`, `gt mail check --inject`). `gt nudge` is "Real-time messaging between agents... without going through the mail system." Addressing is per-role (mayor, deacon, witness) and per-Hook: "A special pinned Bead for each agent. The Hook is an agent's primary work queue," with GUPP: "If there is work on your Hook, YOU MUST RUN IT." Witness (per rig) and Deacon (cross-rig patrol) detect "GUPP Violation" (hooked work with no progress) and nudge or hand off. Beads adds `bd ready`, atomic `--claim`, and a Message issue type with `--thread`. DoltHub's trial (15 Jan 2026) reported ~$100 in tokens, "about 10X the cost of a normal Claude Code session," four low-quality PRs, and an autonomous merge "despite the integration tests failing."

**Mailbox systems.** MCP Agent Mail (Dicklesworthstone): adjective+noun identities, pull-only `fetch_inbox(unread_only=true)` "cuts token-burn for polling agents," explicit `acknowledge_message`, replies inherit `thread_id`, advisory file reservations. Paperclip (MIT): "Agents wake on a schedule, check work, and act," plus event triggers on assignment and @-mentions, via a "DB-backed wakeup queue with coalescing, budget checks..."; Claude Code/Codex adapters "resume the same task context across heartbeats"; monthly per-agent budgets stop runaway spend. Claude Code's own team mailboxes are validated JSON files; its cross-session layer adds held/delivered/expired receipts and burst throttling.

**Tracker-as-inbox.** Linear agents: assignment sets the app as `delegate`, "not the `assignee`"; an AgentSession (pending/active/error/awaitingInput/complete/stale) receives `created` and `prompted` webhooks, user follow-ups arrive as `prompt` activities, and "you are expected to send an activity or update your external URL within 10 seconds to avoid the session being marked as unresponsive." Devin: Slack @mention opens a thread-bound session with bidirectional sync; Linear assignment, playbook labels, automation triggers with "edge detection"; mid-session messages go "in the agent session thread." Cursor cloud agents and Codex cloud tasks follow the same "one run at a time per agent" shape.

**Supervisor/triage agents.** Dosu: webhook-synced, auto-label, dedupe, preview-vs-auto responses, "learns from your corrections," and an open-source auto-label action that "runs in your own GitHub Actions, so you pay only Actions minutes plus your model's usage." GitHub Agentic Workflows (tech preview 13 Feb 2026): Markdown workflows triggered by cron or issue events, read-only agents, and "safe outputs" with hard caps (`add-comment` max 1, `add-labels` max 3, `create-issue` max 1, `deduplicate-by-title`, `hide-older-comments`, `close-older-issues`); failures are auto-filed as issues such as "Auto-Triage Issues produced no safe outputs" (#63057, 24 Sep 2026). Rovo agents are invoked from Jira automation rules. Anthropic's routines doc lists "Backlog maintenance" (nightly grooming with a summary to Slack) as a canonical use. Reported failure modes: noisy or wrong labels (community guidance: only auto-label at confidence >= 85 and emit a `skip_reason`), auto-labeling "bot-created empty issue shells," agents finishing with no action, cost blowups (Gas Town), and message loops (which Claude Code now throttles). Ellipsis "won on signal-to-noise" in one 2026 comparison (secondhand); Sweep/Codegen/Bugbot not verified.

**Lessons.** Separate three states: delivered-to-session, read-by-model, acted-on; require an explicit ack command. Address by scope id with role fallback (Gas Town Hook, Linear delegate) rather than by ephemeral session id. Thread every message to a task and a thread id; replies inherit. Label sender principal and trust level in the wrapper (Claude does this with channel and cross-session wrappers, and routines' fire payloads marked untrusted). Cap write actions per run and dedupe (gh-aw), coalesce bursts (Paperclip, Claude channels), and bound loops (8-block Stop cap, 50-message queue).

## D. Candidate designs

**Deliver inbox to a mid-task implementing agent**

1. *Socket push (Claude Code, local).* A local daemon holds one outbound WebSocket to the server; a `SessionStart` hook registers `session_id`, scope, and `$CLAUDE_CODE_MESSAGING_SOCKET` with the daemon; the daemon writes a JSONL user frame (`priority:"next"`, `from` set so the agent can reply) and records the `peer_message_status` receipt. Pros: delivered between tool calls mid-turn, ordered, receipts, no per-turn polling, works with `-p`. Cons: wire format is undocumented and may change; needs `crossSessionInbound: accept`; Claude Code only; not `--bare`.
2. *Hook pull (portable).* `PostToolBatch` + `UserPromptSubmit` hooks run an inbox-pop command and return `additionalContext`; `Stop` returns `decision:"block"` with unread text while unread exist. Pros: no daemon; hosted variant uses `type:"http"` hooks straight to the server; same pattern maps to Codex (identical events, `decision:block`) and Gemini (AfterAgent deny, AfterTool context). Cons: latency bounded by tool-call cadence, blind during a long single tool, 10k-char cap, one CLI call per batch.
3. *Channel plugin.* An MCP channel server subscribes to the server and emits `notifications/claude/channel` with task/from/msg_id metadata and a reply/ack tool. Pros: purpose-built framing and instructions, two-way. Cons: preview allowlist, next-turn delivery only, no ack, silent drops, Bun/Node runtime.

Recommended by the research agent: 1 for mid-turn delivery, 2's Stop hook as the "do not finish with unread mail" guard and SessionStart drain, 3 later if channels leave preview. For Codex use `turn/steer`; for Cursor/Codex cloud, queue server-side and retry on 409.

**Run the supervising agent**

1. *Self-hosted event-driven worker.* The daemon subscribes to graph events, debounces, and runs `claude -p --bare --resume <supervisor-session> --permission-mode dontAsk --allowedTools "Bash(fwd *)"` with the batch as prompt (or keeps one streaming-input `-p` process fed via stdin). Cheap: Haiku/Sonnet, cached system prompt, `--max-turns`; reliable via a small supervisor loop (Claude Code's own background-session daemon is the precedent) plus SIGTERM/resume semantics. Guardrails borrowed from gh-aw: per-run caps on link/amend/create ops, dedupe, confidence threshold, `skip_reason`, idempotent CLI.
2. *Hosted on Anthropic.* Routines with an API trigger: `POST .../routines/<id>/fire` with a bearer token; payload arrives as an untrusted fire payload so the prompt must opt in; fresh cloud session per fire, 1-hour schedule minimum, daily run cap, runs as the user's identity, no mid-run steering. Managed Agents (beta, `managed-agents-2026-04-01`) fit better for a long-lived supervisor: sessions accept "additional user events to guide the agent mid-execution," stream SSE, and support scheduled deployments; per-session-hour pricing figures seen only in third-party posts (unverified).
3. *Hybrid.* Supervisor as a background Claude Code session under `claude agents`, fed by the socket, with `loop.md` as the idle sweep and a Stop hook that blocks while the supervisor inbox count is nonzero.

Uncertainties: socket wire format (third-party), whether `UserPromptSubmit` fires for socket/channel-initiated turns (not stated), OpenCode busy semantics, Amp hook details, Vibe Kanban/Conductor follow-up internals, and Managed Agents pricing.
