# Line annotations, re-anchoring, graph UI in a VS Code webview, and comment-to-agent loops

Research note, 2026-09-24. Compiled by a research agent; all fetches dated 2026-09-24; secondary sources flagged; a few items marked unverified because the agent's search budget ran out.

## 1. VS Code Comments API and the GitHub Pull Requests extension

**Stable surface** (`src/vscode-dts/vscode.d.ts`, main, fetched today):

- `vscode.comments.createCommentController(id, label): CommentController`. Controller has `commentingRangeProvider?` ("If not provided, users cannot leave any comments."), `options?: CommentOptions {prompt?, placeHolder?}`, `reactionHandler?`, `createCommentThread(uri, range, comments)`, `dispose()`.
- `CommentingRangeProvider.provideCommentingRanges(document, token): ProviderResult<Range[] | CommentingRanges>`, where `CommentingRanges { enableFileComments: boolean; ranges?: Range[] }`. VS Code re-requests ranges on every `onDidChangeModelContent` through a 200 ms delayer (`commentsController.ts` ~line 958), so the provider must be cheap.
- `CommentThread`: `readonly uri`, `range: Range | undefined` ("The thread icon will be shown at the last line of the range. When set to undefined, the comment will be associated with the file, and not a specific range."), `comments`, `collapsibleState`, `canReply: boolean | CommentAuthorInformation`, `contextValue?`, `label?`, `state?: CommentThreadState` (`Unresolved = 0`, `Resolved = 1`), `dispose()`.
- `Comment`: `body: string | MarkdownString`, `mode: CommentMode` (`Editing`, `Preview`), `author: {name, iconPath?}`, `contextValue?`, `reactions?: CommentReaction[]` (`{label, iconPath, count, authorHasReacted}`), `label?` (rendered next to the author name), `timestamp?: Date`.
- `CommentReply { thread, text }` is the argument to commands contributed to `comments/commentThread/context`. Menu points: `comments/commentThread/title|context`, `comments/comment/title|context`; when-clause keys `commentController`, `commentThread`, `comment`, `commentThreadIsEmpty`, `commentIsEmpty`.
- Draft: no draft concept in the stable API. The sample emulates it with `thread.contextValue = 'draft'` and `comment.label = 'pending'`. Proposed `commentsDraftState` adds `Comment.state?` (`Published | Draft`).
- Other proposals (all enabled by the PR extension): `commentThreadApplicability` (`Current | Outdated`; `thread.state = {resolved, applicability}`), `commentReveal` (`thread.reveal(comment?, {focus})`, `hide()`), `activeComment` (`controller.activeCommentThread`), `commentReactor`, `commentingRangeHint` (`provider.resourceHints?: {schemes}`), and menu placeholders `comments/comment/editorActions`, `commentsView/commentThread/context`.
- New and directly relevant: `vscode.proposed.agentEditorComments.d.ts` (PR #324207, merged 2026-07-03, "adds agentEditorComments proposed API for markdown editor"): `window.createAgentEditorComments(uri)` returns `{comments: {id, range, body, author?}[], acceptsComments, onDidChange, onDidRevealComment, addComment(range, body), deleteComment(id)}`, "sourced from the workbench's agent/session comment store (the same store the built-in code editor renders its session comments from)". VS Code 1.131 (2026-07-29) shipped the hybrid Markdown editor with "agent-actionable comments"; 1.132 (2026-08-05) added commenting on web-page elements in the integrated browser. VS Code itself is building a comment-to-agent channel, separate from the Comments API.

**Diff editors, git URIs, virtual documents.** The API is URI-keyed: VS Code calls `provideCommentingRanges` for each side's `TextDocument` and shows a thread wherever its `uri` is open, so an extension attaches threads to either or both sides by choosing the URI. The PR extension encodes side-ness in `uri.query` JSON: `ReviewUriParams {path, ref?, commit?, base: boolean, isOutdated: boolean, rootPath}` and `PRUriParams {baseCommit, headCommit, isBase, fileName, prNumber, status, remoteName, previousFileName?}` (`src/common/uri.ts`). Its `provideCommentingRanges` (`src/view/reviewCommentController.ts` ~505-565): a `review`-scheme URI (left side) returns hunk ranges for `query.base` with `enableFileComments: true`; a repo-root-scheme file (right side / working tree) maps each hunk's new-line span through the HEAD-to-buffer diff (`mapOldPositionToNew`) and returns `{ranges, enableFileComments: ranges.length > 0}`; anything else returns undefined. The built-in git diff's left side is `git:` scheme with `query = JSON.stringify({path, ref})` (`extensions/git/src/uri.ts`, `toGitUri`), so a provider can accept `git:` documents and read `ref`. The URI format is verified; the widget on `git:` documents was not exercised (inferred). Virtual documents work the same way.

**Range tracking on edit: what VS Code does and what is left to the extension.** On the renderer side, `CommentGlyphWidget` places a model decoration on the thread's end line; when edits shift that decoration, `onDidChangeLineNumber` fires and `commentThreadZoneWidget.ts` (~426-431) shifts the main-thread thread's `range` by the delta. So the glyph and widget follow inserted/deleted lines. That shift never reaches the extension: the ext-host protocol only has `$createCommentThreadTemplate`, `$updateCommentThreadTemplate(range)` (the not-yet-submitted template only), `$updateCommentThread(changes)` whose handler reads only `collapseState`, `$deleteCommentThread`, `$provideCommentingRanges`, `$toggleReaction`, `$setActiveComment`. The extension's `thread.range` is stale after edits. Issue #243152 (2025-03-11, "CommentController should be able to enumerate its own threads/comments"; reporter notes ranges "do not appear to get updated as lines shift") was closed as not planned. Consequences for fwdcentaur: keep your own anchor model; apply `workspace.onDidChangeTextDocument` content changes to it if you want live-accurate ranges; recreate threads on activation/open (threads are in-memory); write `thread.range` back when your re-anchoring moves.

**How the PR extension handles the same problems.** It does not listen to `onDidChangeTextDocument` for positions; it recomputes at submission time with `mapNewPositionToOld(diff, thread.range.start.line)` then `+1` for GitHub's 1-based lines. `src/common/diffPositionMapping.ts` walks hunks accumulating a delta. Review mode = checking out the PR branch; working-tree threads are placed with `mapOldPositionToNew(repository.diffWithHEAD(path), line)`. Outdated threads (`IReviewThread.isOutdated`, plus `originalStartLine/originalEndLine`, `diffSide`, `subjectType LINE|FILE`; `IComment.commitId/originalCommitId/position/originalPosition/diffHunk`) are rendered on a read-only virtual document at path `commit~<sha8>/<path>` built from `comments[0].originalCommitId` with `isOutdated: true`, ranged by the original lines; threads live in three maps (workspace / review-scheme / obsolete) and move to obsolete when GitHub flags them; `contextValue` gets `outdated` appended and `applicability = Outdated`. Extension version 0.166.1, engine `^1.137.0`.

## 2. CodeStream (New Relic)

CodeStream let developers leave "codemarks" (comments, issues, permalinks) on code blocks in VS Code/JetBrains/Visual Studio, threaded, with multi-range codemarks since 5.0 (2019-10-16). Docs (via Wayback): "In most cases, a codemark will automatically remain linked to the block of code it refers to as the file changes over time... For example, if you pasted the block of code into a different file. In these cases, the Reposition codemark allows you to select the new location." Archive/resolve states with green/purple/gray glyphs.

End of life: docs.newrelic.com EOL notice published 2026-05-05, effective 2026-11-05: extensions "removed from all IDE marketplaces, along with associated cloud-based components and API endpoints"; reason given: "AI and agentic code creation are transforming how developers interact with observability data"; migration to the New Relic AI MCP Server. (A search snippet claimed an April 2024 "no longer recommended" date; unverified.) The main `TeamCodeStream/codestream` repo is gone (404); the 2023 fork `annias/codestream` still holds the agent source that was read.

Anchoring algorithm (`shared/agent/src/markerLocation/calculator.ts`, `managers/markerLocationManager.ts`):
- Stored anchor: a marker has `referenceLocations[]`, each `{commitHash, location: [lineStart, colStart, lineEnd, colEnd], flags}` (a canonical one plus `flags.baseCommit`); computed locations are cached per `(fileStream, commitHash)`. A codemark on uncommitted code is first "backtracked" (`backtrackLocation`) to the file's committed revision so the stored anchor sits on a commit; the uncommitted buffer copy is cached locally.
- Relocation is diff-driven, never content-search-first: `structuredPatch(commitText, liveBuffer)` (npm `diff`) walks hunks keeping a running line balance; for lines inside a hunk it picks the added line with the best `string-similarity.compareTwoStrings` score (`LINE_SIMILARITY_THRESHOLD = 0.5`), else marks the line `DELETED`. Partially deleted ranges are trimmed to surviving lines (`meta.startWasDeleted / endWasDeleted`); an entirely deleted range triggers `findMovedLocation`, which searches every hunk whose added text resembles the deleted text (`CHANGE_SIMILARITY_THRESHOLD = 0.5`) and re-picks start/end lines; if nothing matches the range collapses to one line at the hunk with `meta.entirelyDeleted = true`; any overlap sets `meta.contentChanged`; columns are recomputed. Source comment: "TODO room for improvement here: we could also look at changes in other files to try to find blocks of code moved across files".
- Across commits: `git.getDiffBetweenCommits(referenceCommit, currentCommit)` feeds the same calculator, with ancestor/descendant checks; failure reason `MarkerNotLocatedReason.MISSING_ORIGINAL_COMMIT`. A Bitap fallback (`findBestMatchingLine`, diff-match-patch `match_main`, pattern <= 32 chars, guessed offset) exists for single-line content search.

## 3. Durable code anchors: design space

| System | Anchor representation | Re-anchoring | When it cannot find it |
|---|---|---|---|
| GitHub PR review comments | `commit_id`, `path`, `line`/`start_line`, `side`/`start_side`, `subject_type line\|file`, plus stored `original_line`, `original_commit_id`, `diff_hunk`; deprecated `position` | Server maps to the head diff; "Not using the latest commit SHA may render your comment outdated if a subsequent commit modifies the line" | Thread `isOutdated`, hidden from Files-changed at the new line, still viewable on the original commit |
| Gerrit ported comments | patch set + file + line/range + side | `CommentPorter` / `GitPositionTransformer`: rewrite paths via file mappings (copies duplicate the comment), then walk each file's range mappings shifting lines; only earlier-patch-set comments, whole threads | `BestPositionOnConflict`: range overlaps a change: drop the line range (becomes a file comment); file gone: drop the file (patchset level). REST doc: callers "must be able to deal with this" |
| Phabricator/Phorge Differential | diff id, changeset, line + length | Ports inlines forward on every update; "very aggressive... even in the presence of heavy changes" | Shown as pale "ghost" comments with a jump-to-original-context button; admits ports "into places that don't make sense" |
| Review Board | `filediff` (specific diff revision), `first_line`, `num_lines`, optional `interfilediff` | None; comments stay on their revision | Warning box "you have additional comments on an older revision" with a link back |
| Reviewable | discussion at a line in a revision | "will also appear in the diffs of other revisions, at the nearest corresponding line... even if the underlying file changes drastically" (details proprietary) | Red dog-ear: "current context may be inaccurate because of significant changes"; click to see original context |
| Critique (Google) | "attached to a specific line and column range in a specific file snapshot" (AutoCommenter paper, 2024) | Internal; the AutoCommenter study used "an automated AST-based line mapping approach" between snapshots | Not publicly described |
| CodeStream | commit hash + line/col range + reference locations | Diff walk + string similarity, moved-block search within file (thresholds 0.5) | Trim, collapse to one line with `entirelyDeleted`, or manual Reposition; cross-file moves unsupported |
| CodeTour | `file`/`uri`/`directory`, `line` (1-based), `selection`, optional `pattern` regex (used only when `line` is unset), tour-level git `ref` | Regex re-search at play time (since v0.0.43, 2021-02-02); `ref` pins to a commit; CI "tour drift" tasks | Wrong line silently; issue #53 (2020) asked to store line text to detect drift |
| Comment Anchors | tags inside source comments | None needed: the anchor is in the file | Deleted with the code |
| Hypothesis | three selectors: XPath range, char offsets, quote + 32-char prefix/suffix | Try range, then position, then quote with position hint; current client `matchQuote` scores quote 50 / prefix 20 / suffix 20 / position 2, `maxErrors = min(256, len/2)`, and asserts the quote after any strategy ("quote mismatch") | "unable to anchor": Orphans tab (client 1.2.0, 2017-03-01) |
| `git blame -L`, `-M`/`-C` | line range or `:funcname` regex | Move/copy detection: `-M` within file (default >= 20 alphanumerics), `-C` across files changed in the same commit (>= 40), `-C -C -C` any commit; `-w` | Attributes to the child commit |
| `git log -L<start>,<end>:<file>` / `-L:<funcname>:<file>` | line range or hunk-header function name | Traces the range's evolution through history; single file, single start revision | Range must exist in the start revision |
| CodeMapper (Hu & Pradel, arXiv 2511.05205, 2025-11-07) | any region in a commit | Candidates from diff analysis, code-movement detection, fragment search; ranked by similarity; language-agnostic; 71.0–94.5% accuracy on four datasets | Returns best candidate; no explicit orphan state |
| Deterministic anchoring (arXiv 2606.26979, 2026-06-25) | structured comment blocks with stable ids co-located with entities | None (in-file) | n/a; reports +2.2 pp Func@5 and halved run-to-run variance for agents |
| Sourcegraph Notebooks | symbol/file blocks at a revision | n/a | Removed in Sourcegraph 7.0 (2026-02-25) |

Synthesis. (a) Representation: every robust system stores several independent handles: a base identity (`path` + blob/commit SHA), a range, and content evidence (the quoted lines, context before/after, a hunk, or an AST path). GitHub stores hunk + original line; Hypothesis stores quote + context; CodeStream stores commit + range and derives content on demand. For fwdcentaur, store: repo-relative path, blob SHA of the anchored version, 0-based range, the exact anchored text, N context lines each side (Hypothesis uses 32 chars; a few lines is the code equivalent), and optionally a tree-sitter node path; keep the original values immutable and record a re-anchor history. (b) Re-anchoring: the winning order is cheap-first: same blob, identity; committed change, `git diff` line mapping (the PR-extension `mapOldPositionToNew` / Gerrit `GitPositionTransformer` walk) with move detection (`git diff -M`/`-C` semantics or CodeStream's hunk-similarity search); live buffer, apply `onDidChangeTextDocument` deltas; last resort, fuzzy quote match with context scoring and a position hint; verify the quote after every strategy, as Hypothesis does. (c) Unfindable: nobody deletes. Gerrit widens to file/patchset level; Phabricator ghosts and links back; Reviewable flags red and links back; Review Board and GitHub keep the original snapshot viewable; Hypothesis lists orphans. The consistent lesson is a visible "orphan/outdated" state that still shows the original snapshot and offers manual reposition (CodeStream's Reposition).

## 4. Graph visualization in a VS Code webview

Bundle sizes (bundlephobia, today): cytoscape 3.34.3 436 KB min / 137 KB gz; sigma 3.0.3 96 / 26 KB plus graphology 0.26.0 66 / 13 KB; @xyflow/react 12.11.6 188 / 60 KB; elkjs 0.12.0 1.45 MB / 433 KB; @dagrejs/dagre 3.1.1 47 / 16 KB; vis-network 10.1.2 413 / 118 KB; d3-force 3.0.0 15 / 6 KB; cytoscape-elk 2.3.0 1.45 MB (embeds elkjs). npm unpacked sizes only: @antv/g6 5.1.1 7.6 MB, force-graph 1.51.4 6.5 MB, cytoscape-dagre 4.0.1 830 KB.

Layout: elkjs is Sugiyama layered with ports, edge routing, and compound nodes, Web Worker "supported out of the box" (`elk-worker.min.js`), GWT-transpiled; React Flow's layouting guide calls it "the most configurable option available, but it's also the most complicated" with a 1.4 MB+ bundle and async computation, and says "we highly recommend dagre" for trees while noting an open dagre sub-flow bug. Mermaid 12 made ELK its default (secondary). Performance: sigma.js targets "thousands of nodes and edges" via WebGL; React Flow's docs give no numeric limit and stress memoization, hidden/collapsed nodes, and simple CSS; Cytoscape documents `hideEdgesOnViewport`, `textureOnViewport`, `cy.batch()`. A 2026 PkgPulse comparison (secondary) puts canvas renderers (Cytoscape, vis-network) at roughly 3–5k nodes before frame-rate loss and Sigma beyond that.

Implementation references in VS Code: Nx Console embeds `@nx/graph`, whose peers are cytoscape + cytoscape-dagre + cytoscape-fcose + cytoscape-avsdf; Dendron's graph is Cytoscape with the euler layout; Beads-Kanban (Kanban/table/dependency graph over Beads) uses React + @xyflow with a hierarchical layout and drag-and-drop status changes; Git Graph draws its own SVG; Foam's docs say graphlib holds the model (renderer unverified). Task/kanban UX: Kanbn, lbauskar Kanban, taskr (Task Master), sharable-kanban-boards, GitScrum; the PR extension shows issues as tree views, not a graph.

Recommendation: @xyflow/react for the canvas (custom React nodes for add/remove/propose/comment affordances, selection, drag, built-in minimap/controls, small bundle) with elkjs `layered` computed in a Web Worker for the DAG, falling back to dagre when a layout must be synchronous. Reasoning: the product needs rich per-node interaction more than graph algorithms; xyflow renders DOM nodes so comment badges, inline editors, and VS Code theme tokens are plain CSS; ELK gives the layered quality a dependency DAG needs. Mitigate xyflow's DOM cost at thousands of nodes with collapse-by-subgraph and hidden nodes (the docs' own advice) and consider Sigma/graphology only if a fully expanded 5k+ view becomes a requirement; Cytoscape is the alternative if you want centrality/path queries in the same object.

## 5. Comment-to-agent loops in IDE review tools (2026)

- GitHub Copilot: code-review comments post as normal review comments; "Fix with Copilot" opens a dialog then hands off to the cloud agent, and "Fix batch with Copilot" batches several comments (changelog 2026-05-19), both only for Copilot's own comments. Human requests route through `@copilot` mentions: "To request changes from Copilot on its pull request, mention @copilot in a comment, or push commits directly to the branch". 2026-09-18 changelog: Copilot resolves its comments with `Won't Fix`/`Incorrect` reasons and honors replies. In VS Code, "Generate Code > Review" or the Source Control review button create Comments-API threads with "Apply and Go To Next" / "Discard and Go to Next"; no documented handoff from a VS Code review comment to agent mode.
- CodeRabbit: IDE extension lists findings in a sidebar and inline; "Fix with AI" sends directly to Copilot, opens a terminal for Claude Code / Codex CLI / OpenCode, hands the prompt to the Claude Code, Cline, Roo, Kilo, or Augment extensions, or copies to clipboard; "Apply suggested change" for one-click fixes. On PRs, `@coderabbitai autofix` (an inline reply limits it to that thread), `autofix stacked pr`, `local commit`, `fix-ci`, and "start a coding task" from a finding. Docs do not describe acting on a human's own inline comment.
- Cursor Bugbot: inline PR comments with "Fix in Cursor" deep links (pre-filled prompt) and "Fix in Web"; reads human top-level and inline PR comments as context; `@cursor` in a GitHub PR/issue comment starts a cloud agent; `@cursor remember [fact]`; in-editor review via `/review` skills. Whether an inline review comment mention triggers the agent is not specified.
- Claude Code: the VS Code extension opens plans as Markdown where "you can add inline comments to give feedback before Claude begins"; the editor selection is attached automatically and `Option+K` inserts `@file#5-10`; diffs open in VS Code's diff editor with accept/reject. Line-anchored comments on code diffs are not offered (issue #96081, 2026-09-22, asks for it in the TUI and notes the Desktop app has it; #33932 asks for a diff review UI). The GitHub Action triggers on `pull_request_review_comment` containing `@claude` and implements changes.
- GitLens Code Suggest (help page updated Aug 2025): a reviewer edits files on the PR branch and "Suggest Changes for PR" posts a PR comment linking to gitkraken.dev; the author applies locally or commits from the web; no AI.
- Graphite VS Code extension: stack management only; no inline review. Diamond was folded into Graphite Agent (Oct 2025, secondary).
- VS Code core: the 1.131/1.132 agent-actionable comments and the `agentEditorComments` store are the closest platform primitive to fwdcentaur's inbox model.

Not researched (budget): Devin, Jules, GitLab Duo.
