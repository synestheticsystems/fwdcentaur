# The local daemon (`fwd daemon serve`): the durable node and its auto-spawn contract

Draft for discussion, 2026-09-24, revised the same day after Daniel's corrections. The auto-spawn contract is adopted from Manifold's architecture doc; the node roles are Daniel's (R).

## Roles (R)

- **v1 is single-user and local-only.** Central hosting and multi-user come later; the design keeps the seams (a Principal per person with a GitHub id, services that can move to a server) without building them.
- **The daemon hosts every project's durable Ankurah node.** There is one durable node per project, and one daemon per OS user hosts all of them.
- **Every client is an ephemeral Ankurah node**: the `fwd` CLI (native, in-memory storage), the VS Code webview (WASM), and later the extension host. Clients connect to the daemon through Ankurah's WebSocket connector and use ordinary Ankurah reads, live queries and transactions. There is no bespoke RPC layer for data.
- **An ephemeral node requires the durable node to be online.** Nothing queues writes; if the daemon is not running, the CLI spawns it; if it cannot, the command fails with exit 7.

## Projects, repositories, checkouts (R, 2026-09-25)

A **project** is the task graph and its database: a UUID and a name, kept under the data directory (`~/Library/Application Support/fwd/projects/<uuid>/` on macOS, `$XDG_DATA_HOME/fwd/projects/<uuid>/` on Linux) holding the Ankurah SQLite engine and the daemon's local-only files for that project. Daniel's ruling: the word is "project", not "workspace", because a workspace suggests "this specific set of folders", which is the wrong way to organize a task graph; every clone and worktree of a project's repositories can be deleted and recloned and it is still the same project with the same graph.

A project is a **set of repositories, each identified by its upstream remote** (`ops::repo_key`: host and path, without scheme, user or `.git`), never by a directory. A **checkout** is any clone or worktree of a member repository on this machine: local, dynamic (worktrees appear and disappear), and never an entity in the graph. The daemon keeps a registry of the checkouts it has seen (`checkouts.json` beside the database; `fwd checkouts` lists it), refreshed from `git worktree list` whenever a client reports the checkout it runs in, so it can resolve anchors against any branch present on this machine.

**Resolution** from a directory: its git upstream, then the local index (`projects.toml` in the data directory, one entry per project with the upstreams it claims). A committed `.fwd/project.toml` marker is optional: it names the project on a fresh machine, and the first resolution through it records the upstream in the index, so every other worktree of that repository resolves without it, whatever branch it is on. That first resolution writes the index even for a command that only reads, and when it cannot (a sandbox that forbids writing the data directory, a lock file that may not be written), the command stops with an error that names `projects.toml`, the data directory and what the command was doing, with the error from the write beneath it (`../DECISIONS.md`, D86, "A read-only command that cannot write the project index stops with an error that names projects.toml", 2026-09-28). `fwd init` joins the project the repository already belongs to (by marker or by upstream) rather than minting a second one; `--new` forces a new project, `--project <name|id>` joins a named one (which is how a project spans several repositories). `--project` on any command also takes a name, an id or a directory. The one daemon hosts each project as its own `Node`.

## Where the semantics live

Ankurah-native: clients write transactions and the daemon runs services as reactors over the durable node. In v1 the node uses Ankurah's `PermissiveAgent` (R), so nothing is refused at commit time; the rules run in two places that do not need a policy agent:

- **Pre-checks in `fwd-core`** run inside the client before the transaction: a `depends_on`, `subtask_of` or `step_of` relation that would close a cycle; starting a task assigned to someone else (a second accepted `assigned_to` until assignment became a field on 2026-09-28, `../DECISIONS.md`); starting a task worked in scopes none of which is the caller's; `accept` by the principal who submitted; an agent exceeding the rights of its role (`data-model.md`, Rules). The CLI prints the cycle or the conflicting scopes and does not commit. Until 2026-10-03 a second accepted `worked_in` for a task was refused too; a task may be worked in several scopes since then (D136, "A task may be worked in several scopes").
- **A validation service in the daemon** re-runs the same rules over the durable node after the fact (clients can race, and a misbehaving client can skip pre-checks). A violating relation gets `status = refused` with a reason, and `fwd diagnostics` lists everything it found. Single-user, local-only, so a small window of after-the-fact correction is acceptable. (The design marked a task worked in two scopes with a diagnostic until 2026-10-03, D136; the service is not built.)
- **Later, with multi-user**: the same `fwd-core` rule functions move into a real `PolicyAgent::check_event` (it sees the entity before and after, with the node available for lookups) and become refusals at commit time, alongside authentication.
- **Services in the daemon** (live-query reactors): routing (creates `Notification` entities per recipient from messages, proposals, assignments and unblocked tasks; coalesces bursts); the git observer (per member repository: watches `.git/HEAD`, `refs/` and the index; rebases worktree anchors and re-resolves anchors in touched paths on commit); the session registry (local-only: which agent session is attached to which scope, its messaging socket path, pid); later the triage driver and the GitHub adapter.

Multi-entity commands (a start is a status change, the assignee and a `worked_in` relation; a message is its text and a `mention` relation per reference) are one Ankurah transaction. Ankurah persists events individually rather than as a cross-entity atomic barrier (Manifold's feedback memo), so the invariants that matter are checked per entity: a second start is caught at the task's status and assignee, whatever happened to the relation.

## Runtime directory and listeners

- Runtime dir: `$TMPDIR/fwd-<uid>/` on macOS (no `XDG_RUNTIME_DIR` there), `$XDG_RUNTIME_DIR/fwd/` on Linux. Mode `0700`.
- **One daemon per OS user, one listener for every project.** The daemon listens on loopback unless the person chose the LAN (`daemon.toml`, below), on the port it had last time when that port is free and on an ephemeral one otherwise. Free includes that nothing accepts a connection to it on `127.0.0.1`, where every client on this machine connects: macOS lets a listener on every interface bind a port another program holds on loopback, and the clients would then reach that program. Once it is listening it writes `daemon.ws` (`{port, pid, instance_id, started, bind}`) with mode `0600`; the `build` field, which `/health` gives already (below), joins them when a newer CLI has to tell an older daemon to restart (Versioning, below). Ankurah's `WebsocketServer` takes one node, so the daemon keeps one per project and routes each project's socket by its path.
- `daemon.bootstrap.lock`: an advisory `flock` taken by any client that intends to spawn the daemon.
- `daemon.lock`: an advisory `flock` held by the daemon for its whole life (the lifetime lock).
- The files of the proof of concept's one daemon per project (`<uuid>.lock`, `<uuid>.ws`, `<uuid>.bootstrap.lock`): the daemon removes the port files and bootstrap locks left over when it starts, and holds `<uuid>.lock` for every project it hosts, for as long as it hosts it. An `fwd` from an earlier build still reads them: it spawns a daemon of its own for a project whose `<uuid>.lock` it finds free, and that daemon would open the same database as a second durable node; finding the lock held, it waits and gives up instead.
- In the data directory: `daemon.toml` (`bind = "loopback"` or `"lan"`, and `port`, the port the daemon last listened on, tried first at the next start so a phone's bookmark usually survives a restart), `daemon.log` (one log for every project), `projects.toml` (the index), and per project `projects/<uuid>/` (the SQLite database and `checkouts.json`). Beside the data directory, `<its name>-backups` holds the backups (Backups, below).

The listener's routes. Only the sockets and the MCP endpoint carry data; the rest is local control and the web UI.

- `GET /health`: `{ok, pid, instance_id, started, bind, build}`. `build` names the binary's build, which `crates/fwd/build.rs` stamps into it as the VS Code extension's `version.mjs` names the extension's builds: the crate's version, the number of commits behind the checkout's commit, `.g` and its short hash, and `.dirty.<UTC time>` when the checkout had changes not committed (`0.0.1-<commits>.g<short hash>[.dirty.<time>]`); `FWD_BUILD`, when it is set for the build, names it instead. A page asks for it when it boots and again each time its connection comes back, to tell when the daemon has restarted on another build (`web-ui.md`, "A newer page after a restart", task pNkDAdfq). The port file does not carry it yet (above).
- `GET /projects`: `[{id, name, error?}]` for every project the daemon hosts, with `error` when one failed to open. The names are read from the index at each request, so a project renamed with `fwd project rename` is listed under its new name without a restart.
- `POST /projects` with `{"id": "<uuid>"}`: opens a project from the index that the daemon does not host yet, such as one `fwd init` just created, so a new project needs no restart. Asking for a hosted project changes nothing.
- `GET /p/<uuid>/ws`: that project's Ankurah WebSocket.
- `GET|POST /p/<uuid>/checkouts`: that project's checkout registry.
- `POST /webview-origins` with `{"origin": "vscode-webview://<id>"}`: admits a VS Code webview's origin for as long as the daemon runs (Security, below). The extension registers its panel's origin before the page there loads, and again whenever that page loses its connection; the daemon keeps 64 at most, dropping the oldest first, and registering one again makes it the newest.
- `POST /mcp`: the MCP endpoint, Streamable HTTP and stateless, which serves the CLI's commands as tools over the project's durable node, each call attributed to the Codex thread whose metadata it carries (`mcp.md`).
- `POST /stop`: drain and exit.
- `GET /` and the files beside it: the web UI (`web-ui.md`).

## `ensure_daemon()`: the shared startup routine

One implementation in `fwd-core`, used by the CLI and, through `fwd daemon start` and `fwd daemon status`, by the extension host.

1. Resolve the runtime dir, the project, and the daemon binary (the running `fwd` itself; never searched on `PATH`).
2. Read `daemon.ws` and ask the daemon on that port who it is (`GET /health`, whose `instance_id` and `pid` must be the file's) and for its project list. A port file alone proves nothing; only an answer from the instance it names does, since after a crash the port may belong to another daemon or another program.
3. If nothing answers and autostart is permitted (`--no-autostart` is available to scripts), take `daemon.bootstrap.lock`, ask once more (another launcher may have won), then spawn `fwd daemon serve --runtime-dir <dir> --data-dir <dir>` detached (its own process group, so a Ctrl-C in the launching terminal does not reach it; stdio to `daemon.log`) with an inherited pipe for readiness. The daemon takes `daemon.lock` before opening any storage or listening; if the lock is held it exits 0 quietly.
4. Wait on the readiness pipe with a bounded deadline (default 10 s). No sleep-and-hope. On timeout, exit 7 with the log path.
5. Release `daemon.bootstrap.lock` and make sure the daemon hosts the project: a project its list lacks (created after the daemon started, or one that failed to open) is asked for with `POST /projects`, and the daemon answers once that project's node is ready, or with the reason it could not open it.
6. Connect to the project's socket and let Ankurah's protocol negotiation run (peers negotiate an exact protocol version or part ways; this exists in Ankurah 0.10).
7. A stale port file is removed only after a failed answer and a successful `daemon.lock` acquisition by the launcher, which proves no daemon holds it. Pids are never killed on the strength of a pid file.

Lifecycle states: `absent -> starting -> ready -> draining -> stopped`, plus `ready -> faulted -> starting` (new instance; clients reconnect and re-subscribe). During `starting` the daemon opens every project before its listener opens, so clients simply wait on the readiness pipe.

## Lifetime

The daemon stays alive while any ephemeral node is connected, while any agent session is attached to a scope in an active state (inbox delivery has to work while the agent is mid-task), or while a `watch` subscription is open. With none of those it exits after an idle grace of 10 minutes. `fwd daemon status` never autostarts. `fwd daemon stop` drains (lets in-flight transactions commit, flushes, closes every project's node, removes the port file under the lifetime lock). `fwd daemon start --lan` or `--loopback` (and `fwd ui --lan`) records the bind in `daemon.toml` and restarts a daemon that listens the other way, including one that was starting when the setting changed and so read the old one; no data moves. Sessions detach on `SessionEnd` hooks or when their pid disappears (polled every 30 s).

## Backups

The data directory holds the only copy of every project's graph on this machine, and the daemon keeps each project's database open and may write to it at any moment. `fwd admin backup` makes a copy that survives the directory's deletion, a damaged database or a bad migration, and it runs while the daemon runs, from a terminal or a daily schedule (`../using-fwd.md`, Backups). It is a command rather than a script so that it runs the same on every machine and can copy the databases through SQLite. A backup, in order:

1. It refuses a data directory without `projects.toml`, which holds no project: a scheduled run with the wrong `FWD_DATA_DIR` would otherwise replace the good backups with empty ones. It also refuses a backups folder inside the data directory, which the directory's deletion would take with it.
2. It creates `<time>.<pid>.partial`, owner-only, in the backups folder: `--to` names any folder, a synced one included; the default is beside the data directory and named after it, `~/Library/Application Support/fwd-backups` on macOS, so that it outlives the directory and is never copied into the next backup.
3. It copies each SQLite database (a file that begins with SQLite's header: `project.sqlite`, `anchors.sqlite`) through SQLite's online backup, never as a file. The databases run in WAL mode, so a committed write stays in `-wal` until a checkpoint moves it into the main file; a daemon that has just written can have almost nothing in `project.sqlite` and the rest in its log. A file copy can take the two files at different moments, or a page halfway through being written. The online backup reads inside one read transaction, which sees one committed state of both files and does not hold up the daemon's writes, and copies every page in one step, since a write by another process between steps would start it over. It copies pages rather than rebuilding the database as `VACUUM INTO` does, since SQLite documents that a vacuum may renumber the rows of a table without an integer primary key, as Ankurah's tables are (their keys are text). The copy is then switched to a rollback journal, so that it is one file with nothing that must travel beside it (the daemon switches it back to WAL when it opens it), and it must pass SQLite's `PRAGMA integrity_check`.
4. It copies every other file as it is: `projects.toml`, `daemon.toml` and each `checkouts.json`, which are replaced whole by a rename when they change, so a copy never catches one half written, and `identity.toml`, which only `fwd init` writes. It leaves out the logs, the lock files, the `.tmp` files a writer is still writing, and the databases' `-wal`, `-shm` and `-journal`, whose committed content the database copies already hold.
5. It writes `backup.json` last: when the backup was taken, the host name, the data directory, the projects the index lists, and every file with its size and SHA-256. A folder without it is not a finished backup.
6. It renames the folder to `<time>`, local time with its offset from UTC (`2026-09-28T204012-0700`), followed by `-2` when another backup took that name in the same second.
7. It removes the oldest backups of this data directory taken on this machine, as their `backup.json` says, so that `--keep` of them remain (seven by default), the new one among them. Nothing else in the folder is counted or removed: another machine's backups in a shared synced folder, another data directory's, a partial one, anything of the person's.
8. It prints where it wrote, each project with its files and their sizes, and the backups kept and removed.

A failure before the removals deletes the partial folder and removes no older backup, so a failed run never costs a good one.

`fwd admin restore <backup> [--into <folder>]` puts a backup back, in order:

1. It reads the backup's `backup.json`. A folder of backups is refused with its newest backup named, and a backup of a later format than the build's is refused.
2. The restore writes into `--into`, or into the data directory of its environment (`FWD_DATA_DIR` or the default). For the latter, it takes the daemon's lifetime lock, `daemon.lock`, and holds it until it has finished: taking it proves that no daemon serves the directory, and a command meanwhile starts none. When a daemon holds the lock, the restore stops and names the daemon's pid and `fwd daemon stop`.
3. It refuses a folder that is not empty, so a restore never overwrites a graph. To replace a data directory, the person stops its daemon, moves the directory aside, and restores into its place; the old one stays until they delete it.
4. It checks every file against `backup.json`, present with its size and SHA-256, before it writes anything, and names each file that changed since: a backup may have sat for weeks in a synced folder.
5. It copies the files into a hidden folder beside the target, checks each database there with the integrity check, and renames that folder to the target, so the target holds the whole backup or nothing.
6. It prints what it restored. For a folder other than its environment's data directory, it says to run `fwd` there with `FWD_DATA_DIR` naming the folder and `FWD_RUNTIME_DIR` naming a folder of its own: with the usual runtime directory, `fwd` would reach the running daemon, which serves the live graphs under the same project ids.

Tests: `crates/fwd/tests/backup.rs` backs up while a client writes tasks into one of two projects, one after another, restores into a new folder and opens it with a daemon of its own: both projects open, and the one being written holds the tasks written before the backup began and a gap-free run of those written while it ran. It checks that `--keep` removes the oldest backups of the data directory and leaves another data directory's backup and a folder of the person's; and that a restore is refused into a folder that is not empty, into the data directory while its daemon runs, into it once stopped (it is not empty), and from a folder of backups, leaving the data directory as it was. `crates/fwd-core/src/backup.rs` checks that a backup holds rows still in the write-ahead log of a database held open, as one file, without the files it leaves out; that a restore refuses a backup with a changed file before writing anything; and that a manifest cannot name a path outside the backup. `scripts/smoke-roles.sh` backs up and restores on the real binary.

## Status for sutra

Sutra (`github.com/synestheticsystems/sutra`) is Daniel's dashboard of the dev runners on his machine. The daemon takes part (Daniel, 2026-09-25) so the dashboard shows whether the daemon runs, on which port, and how many projects it has open, and so sutra's one control, a stop button that sends SIGTERM to a runner's pid, stops it like `fwd daemon stop`. Sutra reads files and nothing else, from one registry directory: `~/.dev-runner/`, or the directory `FWD_DEV_RUNNER_DIR` names (the tests and `scripts/smoke-roles.sh` point it at a scratch directory). The daemon creates the directory when it is missing; when it cannot create it or write to it, the daemon logs one warning and runs without sutra.

The daemon is one card, the supervisor in sutra's terms, with one row, `daemon`. Sutra is for seeing what runs on the machine (Daniel, 2026-09-26: "The point of sutra is just to understand 'whats running on my system rn?'"), and the daemon is one process, so the projects it hosts have no rows of their own (Daniel, the same day: "I don't think projects should have individual status lines in the sutra card. just `daemon` should be fine."): the row counts them, and the log and `/projects` say which failed to open and why. The card's files are named after an id, the first 16 hex digits of the SHA-256 of the data directory's absolute path, so the same data directory has the same card at every start. Each file is written to a temporary file and renamed into place: sutra watches the directory, and a file rewritten in place can be read empty.

- `<id>`, the meta file: `DIR` (the data directory; sutra names the card after its last component, `fwd`), `PID`, `STARTED` (Unix seconds) and `DAEMON_PORT`, the daemon's port. Sutra gives the port of a key that ends in `_PORT` to the row named like the rest of the key, lowercased, so `DAEMON_PORT` is the `daemon` row's, and from that row sutra offers to open `http://localhost:<port>` in a browser; the page opens on its project selector.
- `<id>.daemon.status`, the row, a single line: `starting`, then `ready: <n> projects` (`ready: 1 project`), `<n>` being the number of projects open.

In order: the daemon takes the lifetime lock (a daemon that finds it held writes nothing), removes the meta file and every `<id>.*` that a crashed daemon for the same data directory left, and writes the row `starting`. It opens every project; once the listener is bound, it writes the row `ready: <n> projects`, counting the projects that opened, and then the meta file. Sutra builds a card from a meta file only, so it shows none before the daemon listens: the card appears with its row already `ready`, and `starting` is seen only in the registry directory. A project opened later through `POST /projects` rewrites the row with the new count. A project that fails to open, at start or on request, changes nothing on the card: its reason goes to the log and to `/projects`. At exit, whether by `fwd daemon stop`, Ctrl-C or SIGTERM, the daemon removes the meta file and the row once the listener has closed. Nothing else rewrites the row, and it is never `stopped`, since the daemon's exit removes it; a project that fails after it opened stays in the count, and the log shows the failure. A daemon killed outright, or one that fails before its listener is bound, leaves its files until the next start for its data directory removes them.

## Versioning

Ankurah's protocol negotiation handles the wire version. The daemon and CLI share a build; a newer CLI against an older daemon asks it to drain and restart (`fwd daemon restart`); an older CLI refuses a newer protocol and prints the upgrade hint. Each project database carries a schema version; an older daemon refuses a newer database; migrations take a backup first.

## Security

v1 uses Ankurah's `PermissiveAgent`: no authorization at the node (R). What stands between the graphs and everyone else is where the daemon listens and which requests it answers:

- **Loopback by default, the LAN by explicit choice.** The listener is `127.0.0.1` unless the person ran `fwd daemon start --lan` or `fwd ui --lan` (a phone on the same Wi-Fi); then it is `0.0.0.0` until `fwd daemon start --loopback`.
- **`Host` and `Origin` checks on every request.** A request must name one of the daemon's own addresses as its `Host`: `127.0.0.1:<port>` and `localhost:<port>`, plus on a LAN bind `<hostname>.local:<port>` and every non-loopback IPv4 address the machine has. The daemon lists its interfaces when it starts and again when a request names a host it does not know (at most every 5 seconds), so after the laptop moves to another network a phone there is answered without a restart. A browser's `Origin` must be the daemon's own page, `http://` and one of those (or `FWD_DEV_ORIGIN`, for a trunk dev server), or the origin of fwd's own VS Code webview, which the extension registers with the daemon (`POST /webview-origins`) before the page there loads; a browser request from any other origin is refused, another extension's webview's included. Any extension's webview, a Markdown preview with scripts, or a notebook's HTML output can run script, so being a webview proves nothing: until 2026-09-26 the daemon admitted every `vscode-webview://` origin, and a review reached the sockets, the project list, the checkout registry and `POST /stop` from one that was not fwd's. An answer to a registered webview names its origin (`Access-Control-Allow-Origin`): the webview runs the page from the extension's own files, so its page is on another origin, and a browser shows a page an answer from another origin only when the answer names it (`web-ui.md`, `?daemon=`). So a page from another site, a DNS-rebinding page that answers for its own name, or another extension's webview, is refused; a client that sends no `Origin` (the CLI, the extension host) is let through.
- **No framing.** The page and its files are sent with `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'`, so another site cannot show the page in a frame and lead a click onto it; with no key, a framed page would work. The VS Code webview bundles the app instead of framing this page.
- **Control routes answer only a process on this machine that is not a web page.** `POST /projects`, `POST /stop`, `POST /webview-origins` and the checkout registry refuse a peer that is not on this machine, so a daemon that listens on the LAN cannot be stopped or reconfigured from another device, and the paths of this machine's checkouts do not leave it. They also refuse any request that carries an `Origin`, which the CLI and the extension host never send and a browser sends with every POST and with every request a page makes to another origin (where a webview's page is): no page calls these routes, the daemon's own included, and a page that could would stop the daemon with a plain-text POST, which a browser sends without asking first.
- **The MCP endpoint answers only a process on this machine that is not a web page**, as the control routes do: it asks for no login, so a LAN bind does not expose it, and no page can call it (`mcp.md`, "Transport").
- **No secret gates the sockets** (Daniel, 2026-09-25: "Yes, remove it. We'll do an auth pass later."). Any process on this machine, another user's included, can read and write every graph the daemon hosts, and on a LAN bind so can every device on that network, until the auth pass, which is Ankurah's JWT extension at the node.

Identity is still recorded correctly so it carries over to hosting: `fwd init` captures the person's GitHub user id and login (from `gh api user` when the `gh` CLI is authenticated, otherwise asked once) into `~/.config/fwd/identity.toml`, creates the human Principal, and every transaction carries `by`. Agent principals are established by the agents themselves: an agent names itself (`fwd principal add`), and the fwd plugin's hook stamps each of its fwd commands with the ids of its Claude Code session and agent, so its transactions are attributed to the principal bound to them (`agents-and-inbox.md`, "An agent's identity"; `../DECISIONS.md`, D112 and D118). Until 2026-09-29 this paragraph designed a session registry instead, never built: the SessionStart hook would run `fwd session attach --scope S3`, and later calls would present the session id it returned via `FWD_SESSION`, with pid ancestry as the fallback, so their transactions would be attributed to the session's agent principal (to the scope's, until scopes stopped belonging to a principal: D108). Locally this is trusted, not verified: any process can set the variables the hook sets. A Codex thread that calls the MCP endpoint is attributed the same way, from the thread and session ids Codex attaches to each tool call, and acts as the principal bound to `codex:<session>/<thread>` (`mcp.md`, "Who calls"); any local process could send those ids too.

When multi-user arrives: Ankurah's JWT extension for authentication, the rule referee in `PolicyAgent::check_event`, and row-level scope filters.

## Team mode (deferred)

Two shapes are possible once several people share a project: each daemon stays a durable node and replicates with a server durable node (durable-to-durable), or the server becomes the project's durable node and each daemon connects to it as an ephemeral node, so writing requires the server to be reachable, exactly as the CLI requires the daemon. Daniel deferred the choice until hosting is designed (Q1, 2026-09-24); the routing and validation services run on whichever node is durable.

## Reliability notes

- The CLI generates an idempotency key per invocation and agents may pass their own for retries; the validation service flags a replay whose payload hash differs (a referee refuses it once multi-user arrives).
- Receipts: every transaction's events are visible through `fwd log`, attributed to the authenticated principal.
- The git observer is best-effort; anchor resolution is also triggered lazily by any read that needs it, so a missed filesystem event costs latency, not correctness.

## Implementation notes (T4, 2026-09-25)

`crates/fwd-core/src/project.rs` (index, markers, checkouts, paths), `crates/fwd-core/src/daemon.rs` (the client side: port file, locks, the bind setting, `ensure_daemon`, `connect`, `status`, `stop`) and `crates/fwd/src/serve.rs` (the daemon) implement the contract above with these proof-of-concept deviations, all deliberate:

- **One binary.** There is no separate `fwdd`: the CLI re-executes its own executable as `fwd daemon serve --runtime-dir … --data-dir …` (a hidden subcommand), the pattern tmux, watchman, sccache and Caddy use. One artifact to install, no sibling lookup, and client and daemon are always the same build (Daniel, 2026-09-25). `FWD_DAEMON_BIN` overrides the executable for development. The bind and the port are settings in `daemon.toml`, not arguments.
- **One daemon per OS user** since the evening of 2026-09-25 (before that, one process per project). At start the daemon takes the lifetime lock, removes the per-project port files and bootstrap locks left over, opens every project in the index (its `<uuid>.lock` taken first and held while the project is hosted, then `Node::new_durable` over its SQLite engine, the system created when missing, the routing service started), and only then listens. A project that fails to open is logged and listed with its `error`; it never stops the others. Storage did not move. A per-project daemon from an earlier build that still runs keeps its files and its project: the new daemon lists that project with an error naming the old daemon's pid until it is stopped (`kill <pid>`), and the next `fwd` command in the project opens it.
- **No idle exit yet.** The daemon runs until `fwd daemon stop` (`POST /stop`) or a signal (Ctrl-C, SIGTERM). Ankurah's server does not expose connection counts, so the idle grace needs either a lease count kept by the daemon or an Ankurah feature. The lifetime lock and every hosted project's `<uuid>.lock` stay held until the process exits, after the sockets still open at the stop have closed, so no other daemon, of this build or an earlier one, opens a database this one still has open.
- **Readiness by answer, not by pipe.** The launcher polls for the port file and an answer to `GET /health` (from the instance the file names) and `GET /projects` under a 10 s deadline, then joins the project's node (`wait_connected` plus `wait_system_ready`); the port file is written atomically only after the listener is bound, which is after every project has opened. A stale port file is removed only after the launcher has taken the lifetime lock, which proves no daemon holds it; pids are never killed. A launcher that gives up fails with the log path, with exit 1 rather than 7 so far. A `POST /projects` with no answer within 10 s is reported as a project the daemon is still opening. `fwd daemon stop` waits for the daemon's process to end (a signal-0 probe, which sends nothing), not for the lifetime lock: the moment the lock is free, a concurrent command may start a successor that takes it.
- **Stop neither refuses nor drains.** The refusal while other clients are connected, and a `--force` to override it, are not built: the daemon cannot count its connections yet (see the idle exit above), and `fwd daemon start --lan|--loopback` and `fwd ui --lan` stop a daemon while pages are connected to it. Nor does the stop drain the clients: axum's graceful shutdown does not wait for upgraded WebSocket connections, so the clients connected at the stop lose their sockets when the process exits and reconnect to the successor when it listens on the same port (Ankurah's WebSocket clients retry the address they were given, with backoff). `fwd watch` and the VS Code extension's node also follow a successor on another port, since each joins a new node once the daemon answers again (`vscode-extension.md`, When the daemon restarts). Any other command stops waiting instead: one whose socket closes while it runs ends with exit 7 and an error naming the port it joined and what became of the daemon, as soon as the daemon has come back on another port, or once the socket has been closed for ten seconds, time enough for a daemon restarting on the same port to let it carry on (`crates/fwd-core/src/daemon.rs`, `Client::while_connected`). Until 2026-09-30 a command caught waiting for its new node to be ready, which needs the daemon's answers to the node's first queries, never ended when the daemon came back on another port (task tXSgMMXC). A command that writes also ends with exit 7 whenever its socket closed at any moment while it ran, even when it succeeded, with an error saying that what it wrote may not have reached the daemon and to look before writing it again: Ankurah relays a commit to the durable peers the command's node has, and while the socket is closed the node has none, so the commit goes to the node's own store alone, succeeds, and is lost when the command exits, while a commit made before the close may have reached the daemon. One whose socket closed after it joined the daemon and before it began to write begins nothing (`Client::while_writing`; task NRrogFlb, where until 2026-09-30 such a write was printed as made). `fwd inbox pop`, which marks what it prints as read, ends as a read does: a mark that reached no daemon brings the same notifications back at the next pop, while Claude Code drops what a hook printed when the hook exits 7. The durable fix is Ankurah's: a commit on an ephemeral node with no durable peer should fail there.
- **The URL the client is given is the base** (`ws://127.0.0.1:<port>/p/<uuid>`); Ankurah's WebSocket client appends `/ws` itself.
- **`fwd daemon status`** prints the port file, the hosted projects and, when the current directory resolves to a project, its id as `project` (the VS Code extension reads it); it exits 7 when no daemon answers.
- **Serves the web UI.** `GET /` and the files beside it come from `crates/fwd-web/dist`, embedded at build time (`crates/fwd/build.rs`, `include_dir!` in `serve.rs`); the page lists `/projects` for its selector. See `web-ui.md`.
