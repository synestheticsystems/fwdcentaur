# The `fwd` CLI

Draft for discussion, 2026-09-24. The grammar follows Manifold's CLI doc (discovery, envelopes, checked writes, proposals, watch, exit codes). P unless marked. The CLI is the only interface agents use (R). The daemon's MCP endpoint serves these same commands as tools, parsed by this grammar and run by the same dispatcher, for a harness that speaks MCP (`mcp.md`; task jDv1EY7K).

## Global conventions

```text
fwd [--project NAME|ID|PATH] [--as PRINCIPAL] [--format json|jsonl|text]
    [--no-autostart] [--timeout DURATION] [--idempotency-key KEY] COMMAND ...
```

- The CLI is an ephemeral Ankurah node: it spawns the daemon (the durable node) if needed, connects over the WebSocket connector, reads with fetches and live queries, and writes with transactions after running the `fwd-core` pre-checks; the daemon's validation service catches what pre-checks miss. It requires the daemon to be online (exit 7 otherwise).
- Output is human text on a terminal and JSON when stdout is not a TTY; scripts and skills always pass `--format json`. JSON never contains ANSI escapes. Stderr carries diagnostics only.
- A command that makes something answers with it under `record`, the same field on every one (not `created`, which in every record is the time it was made), so that a script reads them alike (task 4rMEkqE7, "Return the created record the same way from every create command"): `task create` the task, `step add` the step, `comment`, `ask`, `reply` and `forward` the message, `anchor create` the anchor, `scope create` the scope, `decision create` the decision, `link` and `cite` the relation, and `principal add` the principal, each as `show` or `list` prints it. One asked to make what stands already (the same lines anchored again, a step or a citation made again, `principal add` run as the principal it names) answers with what stands, under `record` all the same. What else the command did stands beside `record`: `step add`'s first comment as `message`, `reply`'s and `forward`'s notification, when given one, as `settled` (its id), and after `principal add --succeeds` the principal succeeded as `succeeded` and how many notifications moved as `moved`. Until 2026-09-30 each printed the record's fields at the top level, and this build prints them there too, beside `record`, for a script that reads them there; the next build drops them. `--format text` prints the record as it did.
- Every response is an envelope: `{protocol, request_id, status, basis: {project, generation, completeness}, data, diagnostics}`. `completeness` describes the input domain (`complete | partial | unknown`); `truncated` on paged results describes the output. They are never one boolean.
- Mutations take `--expect-revision REV` (from a prior read) and return a receipt: `{command, principal, before, after, effects: [...], warnings}`. A stale expectation is exit 5.
- Entities are named by their full Ankurah EntityId (base64) in v1; the `T72`, `M15`, `S3`, `N120`, `C40` forms in the examples below are placeholders for readability (Daniel, Q3). Titles are never resolved by first match; `fwd resolve "text"` returns candidates with ids. Human-friendly ids are a later task (T18).
- Every id argument also takes the first six characters or more of an id, when they begin the id of exactly one entity of the kinds the command expects (a prefix several share is refused with each of them listed, one that begins none is refused plainly), and `D<number>` names a decision. With five digits or more, `D<number>` is also long enough to begin an id: it names the decision of that number while there is one (a command that takes no decision then refuses it), and is taken as the start of an id otherwise.
- A command the fwd plugin stamped names the Claude Code agent that runs it, its subject (`FWD_CLAUDE_SESSION` and `FWD_CLAUDE_AGENT` in its environment), and acts as the principal of the project bound to that subject (`agents-and-inbox.md`, "An agent's identity"). There `FWD_AS` is not read, and a `--as` typed on the command line is refused unless it names the bound principal: an agent acts only as itself. A subject no principal is bound to acts as no one: it is refused every command that writes, marks the caller's notifications or reads the caller's own inbox or tasks (`inbox` and `watch` unless `--for` names someone else, `prime`, `session stop-check`, `task list --mine` and `task next`), with the command that names the agent; `principal add`, `bind` and `list` run, and so does every read about the graph alone, which reads it for no one: `task list --ready` lists the ready tasks no one holds, `graph` gives `me` as null, and `whoami` prints `"principal": null`. Until 2026-09-30 such reads ran as they would for the person, so that an agent that had not named itself listed the person's tasks as its own (task JFASz_E2). A command given `--format hook`, as the inbox hooks are, reads the JSON Claude Code hands every hook on standard input, whose `session_id` and, inside a subagent, `agent_id` name the agent whose hook fired, and acts for the principal bound to that subject (`main` standing for the session's own thread), which wins over `FWD_AS` wherever one is bound. While none is bound, a subagent's hook acts for no one and prints nothing, and the hook of the session's own thread (no `agent_id`) acts for the principal `--as` or `FWD_AS` names, as the hooks did before 2026-09-30, so that a lead that has not bound its principal yet keeps its notifications, and for no one without either. Without the hook's JSON, `--as` and `FWD_AS` name the principal, as a person's command at a terminal does (`agents-and-inbox.md`, "An agent's identity", "The hooks", which also says which hooks Claude Code fires inside a subagent). A command in a Claude Code session (`CLAUDE_CODE_SESSION_ID` set) that carries no subject, in a project where a principal is bound to a subject of that session, is refused when it writes or marks notifications, unless `--as` is typed on its command line: `FWD_AS`, which every agent of the session inherits, does not say which agent runs it, while a typed `--as` is a choice made on the command, which no agent inherits, and acts as the principal it names there as anywhere (`../DECISIONS.md`, D120). The refusal names both ways out: run fwd on its own or piped into a filter, which the plugin stamps, once the agent has named itself, or type `--as <name>` on the command. One given `--format hook` without a hook's JSON is refused the same way, and until 2026-09-30 was let through, when the hooks acted by `FWD_AS`. Such a command with neither `--as` nor `FWD_AS` acts as no one rather than as the person, since any of the session's agents may have run it: it is refused, with the same sentence, the reads of the caller's own inbox and tasks a subject no principal is bound to is refused (above), while every read about the graph alone runs and says nothing, and `whoami` prints `"principal": null` and says the sentence on standard error (task JFASz_E2: until 2026-09-30 such a command acted as the person, and that day agents listed the person's 111 unread notifications with nothing saying whose they were). With `FWD_AS` alone such a read acts as the principal `FWD_AS` names. Without a subject, `--as` or `FWD_AS` selects the principal (local trust), except that in a Claude Code session one of whose agents is bound only a typed `--as` lets the command write; without either, a command acts as the person outside Claude Code sessions and in a session none of whose agents is bound, and as no one in a session one of whose agents is bound (`agents-and-inbox.md`, "An agent's identity", "Three ways in"). `--as <name>` acts as the project's principal with that name and never makes one: a name no principal of the project has is refused, with the command that makes it (`fwd principal add <name> --role <role>`). It takes a principal's id too, whole or its first six characters or more, and a name that two or more principals of the project share is refused, listing each by its id with what it is and the scopes its work is in, never guessed; `--to`, `--for`, `task assign`, `--decided-by` and the `principal` commands read a name the same way (`agents-and-inbox.md`, "A principal's name"). The `principal` commands alone run whatever `--as` names, since nothing they write is attributed to whoever runs them, so an agent names itself from its own session, all but `rename`, which renames the principal the command acts as; with a subject, `--as` is read by `principal bind` alone, which it makes deliberate. An agent with no role is refused every command that writes work, with the command that selects one (`fwd principal role <name> <role>`), and a retired principal every command that writes but `principal add`, with the command that brings it back ("Principals"). A command that writes work into the project makes the principal it acts as belong to it, and one that only reads does not (`agents-and-inbox.md`, "Who belongs to a project").
- `--to supervisor`, the supervisor role's word until 2026-09-29, is read by this build as a question asked of no one in particular, which the triage agent of the scope it concerns answers, with a line on standard error saying to leave `--to` off; the next build refuses it. `supervisor` in `--as`, `--for` and `task assign` is a name like any other, which a principal `fwd admin migrate` carried over from the role keeps.

Exit codes (Manifold's table): 0 ok; 2 usage or schema; 3 not found; 4 denied; 5 conflict, stale precondition or ambiguity (including a refused cycle); 6 incomplete result when completeness was required; 7 daemon unavailable (none answers, or the one a command joined goes away while the command runs, or the socket of a command that writes closes at any moment while it runs, so that what it wrote may not have reached the daemon) or start timeout; 8 unsupported capability or protocol; 9 partial mutation, consult the receipt; 10 internal; 130 cancelled.

## Discovery and daemon

```sh
fwd init [--name N] [--new] [--project NAME|ID]   # join the project this repository belongs to (marker or upstream), else create one (making no agent principal); --project joins a named one (a project spans repos); capture your GitHub identity once; you belong to the project; start the daemon
fwd --version                     # the build this binary is: fwd 0.0.1-646.g184fd78
fwd capabilities --format json    # protocol, build, features, limits, relation kinds, policies
fwd schema task --format json     # field descriptions and enum values for a model
fwd whoami                        # principal, project, checkout (root, upstream, branch, head), scope if any, daemon port, data dir
fwd daemon status|start|stop|restart|logs   # start --lan | --loopback: where the daemon listens, kept for later starts
fwd ui [--lan] [--no-open]        # open the web UI on this directory's project, else on the project selector (starts the daemon if needed); prints the URL; --lan prints one a phone on the same Wi-Fi can open
fwd project list|show             # the projects this machine knows (later: publish to a team server, join one)
fwd project rename "fwdcentaur"   # this directory's project (or --project's): its name in this machine's index and in the checkout's .fwd/project.toml
fwd checkouts                     # the clones and worktrees of this project the daemon has seen on this machine
fwd mcp stdio                     # the daemon's MCP tools over standard input and output, for a host that starts its MCP servers as processes (the Codex plugin; mcp.md); acts as no one, starts the daemon when none runs
```

`fwd --version` prints the build this binary is and `fwd capabilities` gives it as `build`, so that an agent or a person can tell one build from another by asking fwd (task 2IiSsfv8, "Report the build, with its git suffix, from fwd --version and fwd capabilities as /health does"). `crates/fwd/build.rs` names it: the crate's version, the number of commits behind the checkout's commit, `.g` and its short hash, and `.dirty.<UTC time>` when the checkout had changes not committed (`0.0.1-646.g184fd78`), or what `FWD_BUILD` says when it is set for the build. The daemon gives the same string on `/health` (`daemon.md`), since a command starts the daemon from its own binary; a daemon that an earlier build started names that build until it stops (`fwd daemon stop`). Until 2026-09-30 both commands gave the crate's version alone (`0.0.1`).

## Principals

Who belongs to the project, which is who the page's pickers offer (`agents-and-inbox.md`, "Who belongs to a project"; `../DECISIONS.md`, D106).

```sh
fwd principal list [--all]        # the principals that belong: name, and what it is (person, lead, triage, implementer, reviewer, or agent for one with no role); an agent with no write for twelve hours last, marked dormant; --all adds the rest, each saying why it does not (retired, or not belonging here)
fwd principal add impl-alice --role implementer [--display-name "Alice"]   # an agent names itself and selects its role, lead, triage, implementer or reviewer; it belongs from now on; a name another principal has is refused, saying whose it is, unless run as that principal (--as), when a retired one comes back
fwd principal add triage-repl --role triage [--scope <id>]   # a triage agent serves the scope --scope names, else the one its checkout finds; with neither it is refused, naming --scope and --project-wide
fwd principal add triage-bot --role triage --project-wide   # a deliberate endorsement to serve the whole project, which suits only a small project with small scopes
fwd principal scope add <scope> [--for triage-repl]   # the triage agent serves another scope (default: the principal the command acts as); refused where another serves it, naming it
fwd principal scope remove <scope> [--for triage-repl]   # it serves the scope no more
fwd principal scope project-wide [--withdraw] [--for triage-bot]   # it is endorsed to serve the whole project, or no longer
fwd principal role claude lead    # an agent selects another role
fwd principal rename implementer-replication   # an agent whose name turned out to be shared renames itself: the principal the command acts as takes a name no other principal of the project has, keeping its id, its work and its inbox
fwd principal retire impl-bob     # it no longer belongs: its work stays attributed to it, no picker offers it, and its writes are refused, naming the command that brings it back, until that command runs
fwd --as claude principal bind claude   # a Claude Code agent takes over a principal from before the plugin, once: its commands act as claude from then on
fwd principal add triage-2 --succeeds triage-1   # a relaunched agent names itself as triage-1's successor in one step, taking triage and the scopes triage-1 served, which the one-triage-agent-per-scope rule counts on triage-2 and not on triage-1: triage-1 is retired, its unread notifications move to triage-2, and routing delivers what reaches it to triage-2
fwd principal succeed triage-1    # the same, for a relaunched agent named already: its own role gives way to triage-1's, and it serves triage-1's scopes besides its own
```

Every agent holds one role of the fixed set, which it selects itself (`agents-and-inbox.md`, "Roles"): `add` refuses a new agent without `--role`. It never makes a person, whose name comes with their own `fwd init`, but a person who runs it with their own name belongs, and a person takes no role. Each command that names a principal takes a name or an id and reads it as `--as` does, and a name that two or more principals share is refused, listing them. A name that one principal has is that principal's alone: `add` given it is refused, saying whose it is (the first eight characters of its id, what it is and the scopes its work is in) and to choose a name no other principal of the project has, as every agent does (`../DECISIONS.md`, D110), unless the command runs as that principal (the one bound to its subject; without a subject, `--as` or `FWD_AS` naming it, or, without them, the person naming themselves), when it brings a retired one back, clearing its successor, or changes its role; so a second agent never becomes the first agent's user by choosing its name, which is what one user per agent means (D112). With a subject, `add` given a name no principal has makes the agent and binds it to the subject, and is refused for an agent bound already, since a subject binds one principal: a relaunched agent that carries on another's job succeeds it.

A retired principal writes nothing until it comes back, since no picker offers it, and an agent resumed after it retired itself would otherwise write on as an author the pickers hide (task Wbkkwpyq; `../DECISIONS.md`, D123, "A subagent retires its own user when its job ends"). Every command that writes, run as a retired principal, whether bound to the command's subject or named by `--as` or `FWD_AS`, is refused with a sentence saying it is retired, naming the agent that succeeded it when one did, and the way back, run as it: `fwd principal add <its name> --role <its role>`, with `--as <its name>` in it where the refused command named the principal by a typed `--as`, and the roles to choose from for a principal succeeded, whose role moved to its successor:

```text
`@impl-carol` is retired, and a retired principal writes nothing, since no picker offers it: to write again, bring it back first with `fwd --as impl-carol principal add impl-carol --role reviewer`, run as it
```

`principal add` alone runs, since it is the way back, and a retired principal that succeeded another, or was succeeded, is refused the same. Marking its own notifications is a write too (`inbox pop`, `read`, `dismiss`), while its reads run as before, and its inbox hooks (`--format hook`) print nothing and mark nothing read, so that what it left unread still reaches whoever comes after it, as a question a retired triage agent never heard of reaches the next one (`agents-and-inbox.md`, rule 5). Until 2026-09-30 a retired principal wrote as before and stayed retired.

`rename <name>` is for an agent whose name turned out to be shared, which only its id names while it is (`agents-and-inbox.md`, "A principal's name"): the principal the command acts as, the one bound to its subject or, without one, the one `--as` or `FWD_AS` names, takes the new name. It keeps its id, which everything that refers to it stores, so what it did and said, its inbox, its role and the agent bound to it stay its own, and every list and page shows the new name, the page's header and pickers without a reload, since they read each principal's name as it changes; its display name follows where it was the old name, as `add` sets it when given none. It is refused for a person, whose name is the handle `fwd init` recorded on this machine, by which the CLI finds them; for a name another principal of the project has, retired or not, saying whose it is as `add` does; and for one that is or starts another principal's id, which names that principal wherever a name is typed. What gave the old name as text names no one afterwards, which the command says on standard error: a `--as`, `FWD_AS`, the extension's `fwd.as`, and a page's route naming the principal (`?for=`) take the new name, or the id.

`bind <name>` binds a principal from before the plugin to the caller's subject, once (`agents-and-inbox.md`, "An agent's identity"). It is refused without a subject, for a subject bound already (naming its principal), unless a `--as` typed on the command line names the same principal (`fwd --as claude principal bind claude`), for a person, for a principal another subject is bound to (naming it and saying to succeed it instead), and for a principal a successor took over (naming the successor). It changes nothing but the subject: a retired principal stays retired until `add`, run as it, brings it back. `add <name> --succeeds <old>` names the caller and makes it `old`'s successor in one step (`../DECISIONS.md`, D114), holding `old`'s role, and with triage the scopes `old` served, so that a relaunched lead or triage agent needs no other role first: each scope's one triage agent, the one that serves a project whole, and the one lead a session may have, are counted on the successor, never on the predecessor it retires. A `--role` given must be `old`'s role, and is the successor's when `old` holds none. It is refused for a name a principal has already (the caller's own, pointing to `succeed`, or another's), for an agent bound already, since a subject binds one principal, and as `succeed` is; otherwise it does what `succeed` does. `succeed <old>` makes the principal the command acts as, which exists already, the successor of `old`, in one transaction: `old` is retired with `succeeded_by` naming the caller, its role moves to the caller, replacing the caller's own, and with triage the scopes it served, besides those the caller served itself, and its unread notifications move to the caller's inbox, each recording that it was for `old` (`for_id`); from then on routing delivers to the caller whatever would reach `old`. It is refused for a caller that is no principal yet (with the command that names it), a person, retired, or `old` itself; for an `old` that is a person, or succeeded already (naming its successor); where another principal that is not retired serves a scope the caller would serve, or the whole project when it would; and where it is lead and another lead is bound to an agent of the caller's session. It prints the caller as `role` does, with `succeeded` (the old principal's JSON) and `moved` (how many notifications moved); `add --succeeds` prints the caller under `record`, with the two beside it. Like `add`, `role` and `retire`, neither makes its caller belong for running it (`JOINING` in `crates/fwd/src/main.rs`): an agent belongs from its own `add`. `role` and `retire` name the principal whoever runs them. A triage agent serves scopes (`agents-and-inbox.md`, "What a triage agent serves"; `../DECISIONS.md`, D122): `add` and `role` give triage the scope `--scope` names, typed on the command, else the scope the checkout finds (or FWD_SCOPE names), which an agent that serves scopes already does not take, or with `--project-wide` the whole project, a deliberate endorsement that suits only a small project with small scopes; with neither they refuse it, naming the two ways out. A project has at most one triage agent per scope and one that serves it whole among its principals that are not retired: `add`, `role`, `scope add`, `scope project-wide`, `add --succeeds` and `succeed` refuse a second, naming the principal that serves it and the commands that free it or retire it, and so does `add` bringing back a retired triage agent, since what it served counts again once it is back. `scope add <scope>` and `scope remove <scope>` give a triage agent another scope or take one away, `scope project-wide` endorses it for the whole project and `--withdraw` takes the endorsement back, each for the principal `--for` names, else the one the command acts as, and each refused for an agent that holds no triage, naming the command that selects it, and `remove` and `--withdraw` for what it does not serve, saying what it serves. Another role frees what a triage agent served. It has a lead per session or worktree that coordinates its work (`../DECISIONS.md`, D119), and a Claude Code session has one: `add`, `role`, `add --succeeds`, `succeed` and `bind` refuse lead to a principal bound to an agent of a session where another lead that is not retired is bound already, and so does `add` bringing back a retired lead there, each naming that lead and saying that a session has one lead, its own thread, while an agent a lead dispatches selects implementer, reviewer or triage; a principal with no subject is not checked, since fwd cannot tell its session. Selecting lead where no triage agent answers first for the scope the command works in prints the guidance on creating a triage subagent, naming that scope (`agents-and-inbox.md`, "Lead"). A command that leaves a scope its triage agent served without one (retire, another role, `scope remove`), or leaves the project with no agent that serves it whole, says who answers first for it now, the agent that serves the whole project, or no one, when its questions wait on the Questions page and reach the next agent that serves it the moment it does, those a retired agent left unread among them, while its comments, proposals and reviews reach no triage agent meanwhile (`agents-and-inbox.md`, rule 5). A command that leaves another principal holding triage and serving nothing says so, in the line that principal's own commands say on standard error (below). Each command prints the principal it made or changed, as JSON (`id`, `handle`, `kind`, `display_name`, `agent_role`, `active`, `member`, `belongs`, whether a picker offers it, `subject`, `succeeded_by`, and `serves`, for a triage agent `{"scopes": [{"id", "title"}], "project_wide"}` and null for any other principal; `add` under `record`, as every command that makes something does: Global conventions) or with `--format text` its line, which for a triage agent says what it serves (`triage-repl (triage, serving Replication)`, `triage-bot (triage, serving the whole project)`, `triage-old (triage, serving nothing)`); `list --format text` prints a line each. Beside a name two or more principals of the project share, `list` gives the scopes each one's work is in (`scopes`, a list of titles, null beside any other name), and its line gives the first eight characters of the id, which name the principal where the name does not, and those scopes: `claude (Ab3dEf12: lead, in Retry work)`.

A triage agent that serves nothing, as those from before 2026-09-30 do until their leads bind or endorse them, hears nothing for its role, and so that it learns why, and can tell its lead, each of its commands says so on standard error, after the command runs, in one line naming the two commands: ``fwd: @triage-old holds triage and serves no scope, so nothing reaches it for its role: bind it to the scope it triages, `fwd principal scope add <scope id> --for triage-old`, or, in a small project with small scopes only, endorse it for the whole project, `fwd principal scope project-wide --for triage-old`.`` `fwd prime --format hook` puts the same line in its session's context. Nothing records that it was told; the line stands while it serves nothing (`crates/fwd-core/src/guidance.rs`).

## Tasks

```sh
fwd task create "Retry on websocket disconnect" \
    --why "Laptops behind NAT drop; agents lose inbox delivery" \
    --done-when "Reconnect within 5s; queued writes replay; test covers 3 drops" \
    --after T70 --after T71          # depends_on
    --under T60                      # subtask_of
    --from M15                       # discovered_from (a message or task)
    --label bug --priority now       # labels: repeatable, commas between several (--label bug,daemon); a priority is now, next or later
    [--propose] [--needs-review]
fwd task show T72 [--include relations,messages]   # the fields, the assignee and the scopes it is worked in, its labels, then the checklist: "steps: 3 of 8 checked"; --include relations adds what it points at and what points at it, messages its comments, each thread under its first message (anchors and history are designed, not built)
fwd task list [--ready|--blocked|--mine|--scope S3|--label X|--status open|--status proposed] [--limit N]   # --mine: assigned to you; --label bug: the tasks with that label
fwd task next [--claim]             # the highest-priority ready task for you (yours first, then unassigned ones) that you can start where you work, started with --claim
fwd task assign T72 @alice | fwd task unassign T72   # the assignee (a field, never an edge); the new one is told
fwd task approve T80 | reject T80 --reason "..."   # Proposed -> Open | Rejected
fwd task start T72                  # Open -> InProgress; you become the assignee and, when you work in a scope and the task is worked in none, it is worked_in that scope (atomic; exit 5 while assigned to someone else or worked only in other scopes, and refused in a checkout several scopes name)
fwd task submit T72 --evidence "PR #12, tests pass" # InProgress -> InReview (or -> Done when !needs_review)
fwd task accept T72 [--note ...]    # InReview -> Done, by a different principal
fwd task return T72 --reason "..."  # InReview -> InProgress
fwd task done T72                   # shortcut for submit when !needs_review
fwd task cancel T72 --reason "..."               # agents without the right ask for it in a message instead
fwd task reopen T72 --reason "..."
fwd task rejustify T72 --reason "..."  # Open|InProgress -> Proposed; assignment stays
fwd task amend T72 [--title ...] [--what @file.md] [--why-append "..."] [--done-when ...] [--label bug] [--unlabel feature]   # labels added and taken off with the rest, in one write
fwd task hold T72 --reason "..." | fwd task release T72
fwd task explain T72                # readiness with reasons, blockers, dependents, why-chain, anchors, open messages
fwd task create "..." --from M15 --propose   # created from a message: the message's author is notified the task exists
```

`task create` makes the task worked in the scope the command works in, so that it is found and started there without a `fwd link` afterwards (task cToJvD22, "Make fwd task create write worked_in for its --scope, and for the scope the checkout finds"): the scope `--scope` (or `FWD_SCOPE`) names, else the scope the checkout finds ("Scopes", below), else none, in a checkout that finds no scope or several. It prints the task as `task show` does, as JSON with `scopes` (and `worked_in` and `worked_in_title`, kept for one release) and for people with `scope: <scope>` beside its assignee (`worked in <scope>` until 2026-10-03, the stored relation's name, which Daniel found unclear that day: task PHfp4WUc), so whoever filed it sees where it is worked, or `null`. Until 2026-09-30 only `task start` and `task next --claim` wrote `worked_in`: `task create` took `--scope` and wrote none, so fifteen tasks filed one morning from a checkout that found no scope each needed a `fwd link` afterwards, and a task filed in a scope was worked in none until someone started it, its context recording the scope it was made in, which routing read for such a task until 2026-10-03. Nothing reads that record now: a task worked in no scope concerns no scope, and what concerns it reaches the triage agent that serves the whole project; `fwd admin migrate` gives a task that has only the record a `worked_in` to its scope ("Maintenance", below).

The reason `reject`, `return`, `cancel`, `reopen` and `rejustify` take is kept as a comment on the task by whoever made the move, opened by the move ("Returned: cover the retry too"), so that the task's thread says why it moved and its assignee hears it; a reject's and a cancel's is the task's closed reason too (`data-model.md`, Transitions; task jJp3bcF7). Until 2026-10-03 a return's, a reopen's and a rejustify's reason was asked for and kept nowhere. A submission's evidence is kept with the task, not as a comment.

Prose fields accept `@file` or `-` for stdin so agents never shell-escape multi-line text.

A task's labels say what kind of work it is, so a list can be filtered by it: `bug` and `feature` are the labels the project uses by convention, and any other word will do (`../DECISIONS.md`, D97, "A task's kind, such as bug or feature, is a label, not a task type", 2026-09-28; `data-model.md`, Labels). `--label` on `task create` and `task amend` adds labels and `--unlabel` on `task amend` takes them off, each repeatable and taking several with commas between them; `task list --label bug` keeps the tasks with that label. A label is stored trimmed and in lower case, so `--label Bug` adds the label `bug` and `--unlabel BUG` takes it off, however it was written; adding a label the task has, or taking off one it lacks, changes nothing. A blank label, or one both added and taken off in one `task amend`, is refused before anything is written. `task show` prints the labels (`labels: bug, feature`), and the JSON of a task carries them as `labels`.

A priority is a word, now, next or later, on `task create` and `task amend` as on `ask` and `comment`, so that one vocabulary serves work and questions (task YtkOevUc, "Give fwd task create and fwd ask one priority vocabulary"). A task stores its priority as a number, which `task next` ranks lower first and the page shows as `P1` to `P3`: now is 1, next 2 and later 3; 0 and 4, which the page's form offers too, have no word, and a task may have no priority. A message keeps the word. Until 2026-09-30 the task commands took only the number, from 0 to 4, and this build still takes it on every one of these commands, saying on standard error that the next build refuses it: a task stores the number as it is, and a message reads it as the word nearest it (0 and 1 as now, 2 as next, 3 and 4 as later). Any other value is refused, naming what is taken:

```text
error: invalid value 'soon' for '--priority <PRIORITY>': a priority is now, next or later (a task stores them as 1, 2 and 3), or, in this build only, a task's number from 0 to 4
```

`task show --include relations` adds what the task points at and what points at it, and `--include messages` its comments and questions and their replies, so that its links and its thread can be read from the command line (task 4ujMsNeQ, "Let fwd task show print the task's comments and replies"); `task explain` serves both too, and `--include relations,messages` gives both. The JSON carries them as `relations`, with `out`, the relations from the task, and `in`, those to it, each oldest first as `fwd relations` prints it, with `other`, the thing at its other end, named as a message's references name it (id, kind and name); and as `messages`, oldest first, each as `task next` gives it, with its author's handle and, for a question asked of one principal, that principal's as `to_handle`. The text prints them after the checklist, the relations first, each a line with the task as `this` on its side and the relation's status when it is not accepted, then each thread under its first message, each message a line with its author, whom it asks, the start of its id (which `fwd reply` takes), whether it is active or resolved and how long ago it was written, and its text beneath:

```text
relations:
  this depends_on Connector (task, NtapcilN)
  Add jitter (task, uOCV9loi) subtask_of this [proposed]
messages:
  @dnorman (id 9T0hBPcv, active, 2h ago)
```

`anchors` and `history`, designed beside them in this document's first draft, are refused as not built yet, and any other value is refused naming the two that are.

Starting a task makes the starter its assignee, and a person with no scope starts one all the same; `--claim` needs no scope either. Until 2026-09-28 starting created an `assigned_to` relation to the caller's scope, and a claim needed a scope (`../DECISIONS.md`, "Assignment is an optional field on the task, never an edge").

A start never moves a task out of the scopes someone chose for it (`../DECISIONS.md`, D87, "Starting a task worked in another scope is refused, with a prompt to switch to that scope first", 2026-09-28). A task may be worked in several scopes (D136, "A task may be worked in several scopes", 2026-10-03), and a start from any of them goes through and leaves it in each. A start from a scope that is none of them is refused, and the refusal names each of the task's scopes and how to switch to one: `--scope <id>`, which works for any scope, and `fwd scope attach-dir <id>` as well for each that is active, since a checkout's binding is honoured only while its scope is active (whoever made it, since 2026-09-29; until then only for the caller's own scope: `../DECISIONS.md`, D108, "A scope has no owner: scopes are not assigned to principals"):

```text
task is in the scope "Cloud Hosting" (Hk3f9QmZ), not in the one you work in; to start it, switch to that scope first: run the command again with `--scope Hk3f9QmZ`
task is in the scopes "Cloud Hosting" (Hk3f9QmZ) and "Open Core" (IbStC7Fm), not in the one you work in; to start it, switch to one of them first: run the command again with `--scope Hk3f9QmZ` or `--scope IbStC7Fm`, or bind this checkout to one with `fwd scope attach-dir IbStC7Fm`
```

`fwd task next`, with or without `--claim`, passes over such a task, leaving it for whoever works in its scopes; when every ready task is worked in other scopes, it prints `"task": null` with the reason `no ready task in the scope you work in: every ready task is in another scope` (`in your scope` until 2026-09-29, and `is worked in another scope` until 2026-10-03). Before D87, a start from another scope moved the task there and retracted its `worked_in` to the scope it left.

`fwd task show` prints the scopes a task is worked in under `scopes`, each with its `id` and its `title` (null for a scope it cannot read), in the order the task came to be worked in them, and for people `scope: <name>` or `scopes: <name>, <name>`; `fwd task explain` and `fwd graph` print them under `scopes` as ids. Each also prints `worked_in`, the first of them or null, and `task show` its `worked_in_title`, kept for one release for readers that read one, from when a task had one scope (until 2026-10-03); a reader should read `scopes`.

## Steps

A task's checklist: things to look at or do, in order, each checked off by whoever works the task (`data-model.md`, Steps).

```sh
fwd step add T72 --path src/net/ws.rs --lines 120-134 ["first comment"]   # lines of a file (a highlight) as the next step, with its first comment when text follows
fwd step add T72 --path src/net/ws.rs ["first comment"]   # the whole file (a highlight with no lines) as the next step, the same way
fwd step add T72 --path src/net/ws.rs --lines 120-134 --against HEAD [--side base|modified] ["..."]   # lines as a revision has them (Anchors, below)
fwd step add T72 M15                # anything else as the next step: a message, a task, a highlight by its id
fwd step list T72                   # the checklist in order: "[x] 1. ws.rs:4-8 2418c54 `fn reconnect() {`, thread resolved"
fwd step check T72 3 | fwd step uncheck T72 3   # by its number in the checklist, or by the id of its relation or of what it is; a highlight's first thread moves with it
fwd step remove T72 3 --reason "moved to its own review" [--retire]   # takes it off the checklist; --retire resolves a highlight's threads too
```

A highlight's step line names it as the page's list item does, from the one builder in fwd-core (`anchor_name`) whose place the VS Code extension's references use too: where it is, `path:lines` (`ws.rs:4-8`, `ws.rs:4` for one line, the path alone for a whole file), then the version it was made on (the blob's first seven characters, or `working tree`), then its first line that is not blank, cut at fifty characters, in a code span (none on a whole file); then whether the first thread on it is open or resolved (`thread open`, `thread resolved`). Its file comes first, since a reader looks for the file first (Daniel, 2026-09-29: "I think we should reverse the order of code references. I suggest filename:line-line `code` or something like that. to make it more readable"; task ZYjo8Yyr); until then the line began with the first characters of its lines, then `@`, the file, the version and the lines. Any other step gives its name and kind. A highlight's steps and that first thread move together (`data-model.md`, "Rules"; `../DECISIONS.md`, D99, "Checking a step resolves its highlight's first thread, and resolving that thread checks the step; each control says it does both"): `step check` resolves the thread's first message and `step uncheck` sets it back to active, with the highlight's steps on other checklists, and each prints the step, with its thread as it now stands, and the steps on other checklists that moved with it: as JSON under `checked_steps` or `unchecked_steps`, for people a line each. Without `--lines`, the highlight is the whole file (`../DECISIONS.md`, D43, "A whole-file reference is an anchor with no line range"), made a step and given its first comment the same way as lines (task wmNoucjv, "Make a whole-file step's first comment reach the task's parties: create the step before its comment"). Until then `step add --path` required `--lines`, so a whole file became a step only by commenting on it (`fwd comment --path`) and adding its anchor after, and that first comment, posted before the step existed, reached neither the task's creator nor its assignee. The first comment is a message on the highlight with no task, checked for its references before anything is written, and posted after the step on a highlight made already, or in one transaction with the step and a new highlight (as for `fwd comment --path`, below), so that it reaches the task's creator and assignee (`agents-and-inbox.md`, rule 14); the step reaches them too, and a burst of steps and comments by one author on one task reaches each of them as one notification while it stays unread (rule 10). Adding what is already a step answers the step that stands; a task that would become a step of itself, however far round, is refused. A step is named by its number in the checklist, or by the id of its relation or of what it is (a highlight's id), whole or its first six characters or more, looked for among that checklist's steps alone; a name that fits none is refused, saying so.

A step that no longer belongs on the checklist comes off it with `step remove`, where checking it would record it as done: its work moved to other tasks, as when a review of 172 steps was replaced by smaller ones, or it was added by mistake (task 9dvGW0EI, "Take a step off a checklist and retire its highlight in one command: fwd step remove"). The step's relation is retracted with the reason, as `fwd unlink <step> step_of T72 --reason` retracts it, and what the step is stays; `fwd relations <its id> --kind step_of` prints the relation with the reason (`closed_reason`). With `--retire`, a highlight's threads are resolved too, as `fwd message resolve` on the first message of each resolves it, so the editor, which draws a highlight while a thread on it is open, stops drawing it, while `fwd anchor show` and the highlight's page still list them; resolving its first thread checks the highlight's steps on other checklists, since a highlight's steps and its first thread are one state (`../DECISIONS.md`, D99, "Checking a step resolves its highlight's first thread, and resolving that thread checks the step; each control says it does both"), and the command lists them. `--retire` on a step that is not a highlight is refused, and so are a blank reason and anyone but the task's creator and its assignee, the people whose checklist it is (`rules::can_remove_step`). Neither the removal nor the retire tells anyone, as an unlink and a resolve tell no one. The command prints the checklist that is left as `step list` does, after a line for the step taken off and its reason and one for each thread resolved and each step checked; as JSON, `{"removed": <the step as it stood, with its "reason">, "resolved": [<each thread's first message>], "checked_steps": [<as step check lists them>], "steps": [<the checklist>]}`. The steps after it move up a number, so whoever takes off several names them by id. The task's panel on the page offers the same (`web-ui.md`, "A task's steps").

The JSON of a step, which `step add`, `step list` (a list), `step check`, `step uncheck`, `step remove` (`removed` and `steps`) and `task show` (`steps`, with `progress: {checked, total}`) print:

```json
{ "n": 1, "edge": "<step_of relation id>", "id": "<the step's id>", "kind": "anchor", "name": "ws.rs:4-8",
  "checked": true, "checked_by": "<principal id>", "checked_by_handle": "dnorman", "checked_at": 1790628930000,
  "position": "V", "created_by": "<principal id>", "created": 1790628927881,
  "path": "ws.rs", "lines": "4-8", "basis": "blob", "blob_sha": "2418c540...", "excerpt": "fn reconnect() { loop { try_once(); } }",
  "first_line": "fn reconnect() {",
  "thread": { "id": "<its first thread's first message>", "status": "resolved" } }
```

`kind` is `anchor`, `task`, `message`, `decision`, `scope`, `relation` or `principal`; `path`, `whole_file`, `lines` (1-based, inclusive; null on a whole file, whose `name` is its path and whose `excerpt` is empty), `basis`, `blob_sha`, `excerpt`, `first_line` (the first line that is not blank, as the step line shows it; null on a whole file and on lines all blank) and `thread` (null while no one has started a thread on it) come with an anchor, `status` with a task or a decision, `checked_by_handle` with a checked step, and `message` (the first comment) with `step add --path`.

## Relations

```sh
fwd link T72 depends_on T70 [--note "..."] [--via M15] [--propose]
fwd link T72 subtask_of T60
fwd link M15 concerns T72           # the triage agent linking a message to a task
fwd link T72 anchored_at C40
fwd unlink T72 depends_on T70 --reason "..." [--propose]   # retract
fwd relation approve <id> | reject <id> --reason "..."   # Proposed -> Accepted | Rejected
fwd relations T72 [--kind depends_on] [--direction in|out|both] [--status accepted|proposed]
```

Each kind joins entities of the kinds `data-model.md`'s table of relations gives, and `link` refuses a relation whose ends are of other kinds, since what every page reads from a relation rests on them (a task worked in a decision showed the decision's short id as its scope, task 7dq1vEd_): the sentence says what the kind joins and what the two ends are, "`worked_in` joins a task to a scope, not a task to a decision", or which id names nothing in the project. `task create` refuses the relations its `--after`, `--under`, `--from` and `--motivated-by` would make from the new task the same way, with the same sentence, and makes no task (task iDJpHjiB): the CLI passes a whole id through whatever it names, and reads `D<number>` given to `--from` or `--motivated-by` as the decision it names, which neither relation joins. `depends_on`, `subtask_of` and `duplicates` join a task to a task; `motivated_by` and `discovered_from` a task to a task or a message; `supersedes` a task to a task, or a decision to a decision, which only `fwd decision supersede` makes; `anchored_at` a task to an anchor; `worked_in` a task to a scope; `step_of` anything to a task; `concerns` a message to a task, a relation or a scope; `cites` a task, a message or a decision to a decision, or a decision to a task or a message; and `relates_to` anything to anything. `fwd link --help` lists them, from `fwd_core::ops::joins`, which the refusals read too. A `link` that would close a `depends_on`, `subtask_of` or `step_of` cycle exits 5 and prints the cycle. `fwd link <x> step_of T72` is `fwd step add T72 <x>`. `fwd link T72 worked_in S3` adds S3 to the scopes the task is worked in, any number of them (`../DECISIONS.md`, D136, "A task may be worked in several scopes"; until 2026-10-03 a second `worked_in` was refused), and answers with the relation that stands when the task is worked in S3 already; `fwd unlink T72 worked_in S3 --reason "..."` takes S3 off, the last one too, which leaves the task in no scope; neither tells anyone. `mention` is not linked (posting a message makes it), and `assigned_to` is made no more.

## Scopes

```sh
fwd scope create "Inbox delivery for Claude sessions" --intention @intent.md [--repo <upstream>] [--branch feat/inbox]...   # default: the checkout's branch
fwd scope show S3                   # includes local-only fields on this machine
fwd scope rename S3 "Comments reach agents mid-task"   # a scope's name is free text for people; nothing looks a scope up by it
fwd scope list                      # every scope not done or abandoned
fwd scope status S3 planned|active|paused|blocked|done|abandoned [--note ...]
fwd scope intention S3 --set "..." [--append "..."]   # --set replaces it; --append adds a paragraph
fwd scope branches S3 --add feat/inbox-2 [--remove feat/inbox]   # a scope may span branches
fwd scope attach-dir S3 [/path/to/worktree] [--clear]   # local-only: bind a checkout to any scope not done or abandoned, whoever made it (the daemon's registry)
```

`fwd scope assign` and `unassign` are gone: who does a task is `fwd task assign`, and a task worked in no scope comes to be worked in the scope the command that starts it works in (`../DECISIONS.md`, "Assignment is an optional field on the task, never an edge", 2026-09-28), while a task worked in a scope is started only from that scope ("Tasks", above). `fwd scope show S3` lists the tasks worked in it. `fwd scope heartbeat` is gone, with the owner and the heartbeat a scope had until 2026-09-29 (D108): anyone works in any scope, and who does a task is its assignee.

A command finds the scope it works in, which `task start`, `task next` and `task create` use: `--scope <id>` (or `FWD_SCOPE`) names any scope; else the scope the checkout is bound to with `scope attach-dir`, while that scope is active, whoever made it; else the one active scope that names the checkout's branch and repository, of all the project's active scopes (a scope from before repositories were named on scopes counts when the directory it recorded contains the current one, and failing a branch, the one whose recorded directory does). A binding wins over a branch. Several scopes at one step make the checkout ambiguous, as a checkout of `main` is where two scopes name `main`: the commands that need a scope to know where a task is worked, `task start` and `task next --claim`, are refused, naming the candidates and how to choose, and every other command runs with no scope, as in a checkout no scope names (`whoami` prints `"scope": null`). The refusal:

```text
several active scopes name this checkout's branch main: "Initial implementation" (x_M0XLwr) and "Reviews and highlights" (KgeeTdKb); say which you work in: run the command again with `--scope <id>`, or bind this checkout to one with `fwd scope attach-dir <id>`
```

Until 2026-09-29 only the caller's own scopes counted, a binding was honoured only for its scope's owner, `attach-dir` bound only the caller's own scope, and several matches gave every command no scope (D108).

Names are for people to read, so both renames take any text but a blank one, and so does `scope create`. A scope's name is stored as its `title` (`scope show` prints it there). A scope names branches only with the repository they are in, and `--repo` takes a remote URL as well as an upstream key, storing the key; `scope status` takes any status from any, records when the scope started the first time it leaves planned, records when it ended once it is done or abandoned, and forgets that end when it leaves them. The page's Scopes panel does the same through the same operations. A project's name is how people select it (`--project`, the page's selector), so `project rename` refuses a name another project on this machine already has. It rewrites the index entry and, when the checkout's `.fwd/project.toml` names the project, that marker too; commit the marker so other clones and worktrees learn the name, since until then a checkout whose own marker names the project resolves to the old name. The daemon reads names from the index whenever it lists its projects, so `GET /projects` and the page's selector show the new name without a restart.

## Inbox and notifications

```sh
fwd inbox [--for me|<name>] [--unread] [--format json]   # recipient = ? AND status != 'Dismissed', by priority then time (a batch's, when its last item joined); a digest lists its steps and comments beneath it
fwd inbox pop [--format hook]        # inject your unread notifications once and mark them Read (another principal's inbox, named by --for, is refused before anything is printed, naming whose it is); hook format prints additionalContext JSON; --heartbeat, which recorded the scope's heartbeat until 2026-09-29 and was then taken and ignored for one build, is refused, the sentence saying to take it out of the hook that passes it
fwd read N120 | fwd dismiss N120      # your own notifications; another principal's are refused, naming whose each is
fwd reply N120 "linked to T72, appended why"  # a reply message in the thread of N120's originating message, which marks N120 read (Messages, below); the usual way to record a disposition
fwd watch [--for <name>|me] [--types CodeCommented,TaskProposed,...] [--timeout SECONDS] [--count N] [--format jsonl]
```

`watch` emits one JSON object per line: a snapshot of unread notifications first, then events as they happen (a live query over Notification), with a `cursor` for resume. It has no timeout unless given one, so that an agent waiting in it is woken only when there is something to read (Daniel, 2026-09-29: "ideally fwd watch wouldn't have any timeout at all. it should only exit if the daemon has been unreachable for an extended period of time"). The harness that runs this project's agents ends a background command within two hours all the same, so an agent there runs `fwd watch --count 1 --timeout 7100` with the command's own timeout at 7,200,000 ms, and arms the watch again after each `timeout` event, the new watch printing first what arrived meanwhile (`agents-and-inbox.md`, "The triage agent's loop"). `--count N` wakes an agent blocked on an answer: the agent runs `fwd watch --count 1` in the background, and once the watch has printed N notifications it emits `{"event": "done", "count": <how many it printed>}` and exits 0, which wakes the agent. Notifications already waiting count: the hooks mark notifications read between the agent's steps, so whatever is unread when the watch starts arrived after the agent's last step, and when the snapshot alone holds N the watch ends at once. A notification that collects what one author does on one task (`agents-and-inbox.md`, rule 10) prints once, when its first item makes it: the items that join it while it stays unread wake no one again, and whoever reads it reads them all. `--timeout SECONDS`, for a script that must bound its wait, also ends the watch once that long has passed, with `{"event": "timeout"}` and exit 0. A daemon restart is silent (Daniel, 2026-09-26): the watch reconnects and registers its query again, on the daemon's new port if it moved, and prints what arrived meanwhile as ordinary events; only a daemon out of reach for ten minutes ends it otherwise, with `{"event": "unreachable", "since": <ms>, "reason": ...}` and exit 7 (`crates/fwd/src/watch.rs`). Whichever line ends the watch (`done`, `timeout` or `unreachable`), or an error, which it prints on standard error with exit 1 as any command does, the watch ends its process as soon as it has printed it, rather than dropping its node and shutting its runtime down: a node the watch has let go of can leave a thread deadlocked inside Ankurah, which that shutdown waits for, and a watch that had printed `done` never exited that way twice in thirty runs under load (2026-09-29). `--mode transitions` (full change history) is refused until the daemon has durable replay, as in Manifold.

## Messages (comments, questions, proposals)

```sh
fwd comment C40 "is this related to T72? we need XYZ when we get there"   # a message with anchor C40 (the id of a scope or a decision sets scope or decision instead)
fwd comment T72 "..."                                                     # a message with task T72; with --path src/x.rs [--lines 10-12] as well, anchor too: a new highlight
fwd ask [--to @daniel] --about T72 "question text" [--priority now|next|later]   # a message whose context says whom it asks: context.to, the id of the principal the name or id names (the @ optional; me for oneself; a name several principals share is refused), or without --to context.asks = "project", a question asked of no one in particular, with context.asks_scope the scope it asks: the scope --scope names, typed on the command, else the scope of the task, decision or highlight it is about (of a task's several scopes, the one this checkout finds when the task is worked in it, else the one the task was first worked in), else the one this checkout finds (context.written_in); the triage agent of that scope answers it, else the one that serves the whole project, and while neither does it waits, which the command says with the guidance on creating one (D58, "Message subjects as typed reference fields"; D122); a scope has no owner to ask (D108), and `forward --to scope:<id>`, which reached the scope's owner until 2026-09-29, is refused, saying so
fwd ask [--about T72] --path src/x.rs --lines 10-12 "question text"   # on lines (a highlight whose thread it starts), as fwd comment --path; --path alone: the whole file
fwd comment [T72] --path src/x.rs --lines 10-12 --against index [--side base|modified] "..."   # on lines as a revision has them, as a side of a diff shows them (Anchors, below); fwd ask too
fwd reply M15 "..."                  # a message with reply_to M15, thread (its thread's first message), and M15's task, anchor, scope or decision
fwd forward M15 --to @impl-alice --note "this is yours"   # a reply addressed onward; routing notifies the new recipient; without --to, to no one in particular, which the triage agent of the scope the forwarded message concerns hears (--scope names another)
fwd message show M15 | resolve M15 [--note "..."] | unresolve M15 | list [--open] [--on T72|C40] [--to me]
fwd message edit M15 "..."           # its author, or an agent that succeeded its author, replaces its text; its id, thread and place stay
fwd proposed [--tasks|--relations]   # everything in Proposed status, oldest first
```

`reply` and `forward` also take a notification's id, as the hooks and `fwd inbox` print it: they act on the message behind it and settle the notification, so that a watch armed next does not print it again (task TdwRqMeQ, "Mark a notification read when the agent replies to it, forwards it or dismisses it by its id, as the primer says it does"). The transaction that posts the reply or the forward marks the notification read, so the two land together or not at all, and the answer names it beside `record` as `settled`. A notification read already is left as it is, and one dismissed stays dismissed rather than coming back into the inbox. Given a message's id they change no notification and the answer has no `settled`: they settle only a notification they are given, rather than guess which of the caller's notifications of that message, if any, they act on. `fwd dismiss` settles a notification with nothing to answer.

A notification is its recipient's alone to settle, as the page marks no card of another principal's read (task AfhuiHYS; `data-model.md`, Notification): `read`, `dismiss`, `reply` and `forward` given a notification addressed to another principal than the one the command acts as refuse it, naming whose it is, and change nothing, a `read` or a `dismiss` of several ids marking none of them; and `inbox --for <another> pop`, which marks what it prints read, refuses that principal's inbox before it prints anything, naming whose it is, where `inbox --for` lists it and marks nothing. `reply` and `forward` then name the id of the message behind it, through which the message is answered without settling anything, and nothing is posted. A successor is refused the notifications its predecessor kept, those read or dismissed before the succession, since the unread ones moved to it. Until 2026-09-30 the four changed any notification's status, and until 2026-10-01 `inbox --for <another> pop` printed another principal's unread notifications and marked them read, so that an agent that mishandled an id or a name could settle a notification that was never its own:

```text
notification 1a2b3c4d is @dnorman's, not @triage-bot's, and a principal reads, dismisses, replies through or forwards only its own notifications, as the page marks no card of another's read: nothing was posted; to answer the message behind it without settling anything, give its id, 9T0hBPcv, in place of the notification's
```

A comment or a question with `--path` on lines no highlight holds yet makes the highlight in the message's own transaction: a message refused, for a reference that names nothing or anything else, leaves no highlight behind, and whoever hears of the highlight hears of its message in the same publication, which also keeps the message out of a race in Ankurah's durable node that could leave it unrouted, no one told of it (task F-Z2QwJe; `ops::post_on_highlight` says how). On lines a highlight holds already, the message is posted on it.

A message's JSON prints each of these fields under its own name, as the comments above name them (`data-model.md`, Message): what the message is about as `task`, `anchor`, `scope` or `decision`; on a reply, the message it answers as `reply_to` and the first message of its thread as `thread`; and whom a question or a forward asks as `to`, inside `context` (`../DECISIONS.md`, D58, "Message subjects as typed reference fields").

A message's text names a person as `@handle`, and anything by its id, the first six characters or more of it, or `D12` for a decision, after an at-sign (`@vwugaN8h`, the handle tried first) or in double brackets (`[[vwugaN8h]]`, `[[D12]]`), anywhere but in code (between backticks, or in a fenced block). Posting resolves each reference, stores it as `[[<full id>]]` and writes a `mention` relation for it (`data-model.md`, "Inline references"); one that names nothing refuses the post with a sentence naming it, such as "refused: `@dnormn` (no one has the handle `dnormn`, and no id starts with it) names nothing; correct it, or put it in backticks to keep it as text", and a prefix several ids share is refused with them listed, as is a handle that two or more principals of the project share, each listed by the first eight characters of its id, which `@` names in place of the handle. The JSON of a message keeps the stored text in `content` and adds `references`, one per reference in order: `{"id": "<full id>", "kind": "task", "name": "Retry on disconnect"}`, the kind as a step's is, a person's name `@handle`, a decision's `D12 (title)`, and `unknown` with the id as its name for what cannot be read. `--format text` (`fwd message show`, a decision's comments in `fwd decision show`, the inbox) prints a person as `@handle` and anything else as its name in brackets; the hooks, for agents, add the first eight characters of the id (`[Retry on disconnect](gA3lqGfs)`). So that a writer finds the convention where the text is written (Daniel, 2026-09-28: "I suggest putting an example of how to do this in a discoverable place in the cli help"), the long help of `fwd comment`, `reply`, `ask`, `forward` and `message edit` ends with it and an example of that command, and `fwd --help` names it among its conventions and points there.

A message's text names a whole file at a version too, so that a writer can point a reader at a file as the writer saw it (task nVE7KTeSqiX0; `../DECISIONS.md`, D125, "Anything a message names in its text is a mention, whatever its kind"): its path from the repository's root, in double brackets only, since an at-sign names people, agents and ids (D121). `[[docs/cli.md]]` names the file as it stands on disk, unstaged changes included; an at-sign after the path names another version, `[[docs/cli.md@index]]` the staged copy and `[[docs/cli.md@e13b8e2]]` the file at that commit, which a branch, a tag or `HEAD` names as well; `[[docs/cli.md@worktree]]` names the file on disk outright, for a path with an at-sign of its own, since the version follows the last at-sign. A path is told from an id by its shape, a slash or a dot, which no id and no `D12` holds, so a file at the root with neither is written `[[./Makefile]]`; an absolute path inside the checkout is taken. Posting reads the file in the checkout the command runs in (`fwd whoami` shows it, and the extension's comments post through the CLI in the workspace's): a file that is not there at that version, a directory, and a revision this checkout does not have refuse the text with the reference's sentence ("refused: `[[docs/nope.md]]` (docs/nope.md is not on disk in this checkout) names nothing; ..."), and so does a command run in no checkout of the project's repository. The page has no checkout, so a file named in its boxes is refused with a sentence saying to write it from the CLI or in a comment in VS Code's editor (`web-ui.md`, "Inline references"). The file becomes its whole-file highlight, the one `fwd anchor create --path` would make, found when it exists and made once every reference of the text reads, so a refused text makes none; and the text stores the reference as that highlight's full id, an at-sign and the version: `[[<full id>@worktree]]`, `[[<full id>@index]]` or `[[<full id>@<full commit id>]]`. A revision is stored as the commit it named when the message was posted, so the reference does not move as `HEAD` or a branch does, and the version stays with the mention because one whole-file highlight, keyed by its content, serves every version that holds the same bytes (the lead's ruling of 2026-09-30 on that task). The stored form reads again with no checkout, as a forward's quote does, and `message edit` shows a file mention as the start of its highlight's id and its version (`[[vwugaN8h@index]]`), which keeps the file as it was named; after an id, the version must be `worktree`, `index` or a commit's id, and the id a whole-file highlight's. In the JSON of a message, a file mention's reference carries `version` as the text stores it, `kind` `anchor`, and the file's name at that version, its path and then the short commit, `index` or `on disk` (`docs/cli.md e13b8e2`; fwd-core's `anchor_name::AnchorName::file_at`), which `--format text` prints in brackets.

A message is corrected where it stands, so that a correction does not split its discussion across two threads and leave the old wording in sight (Daniel, 2026-09-28, of a question an agent had sent him: "Are you able to edit this question?"; until then the only fix was a second question and resolving the first). `fwd message edit M15 "<new text>"` replaces the whole text; M15 may be a notification id, for the message behind it, and the notification stays as it is. The message's author edits it, and so does an agent that succeeded its author (`fwd principal add --succeeds`, `fwd principal succeed`), directly or through a chain of successions, so that an agent relaunched to carry on another's job corrects an answer its predecessor gave where the answer stands (task sVCUXcEg; `../DECISIONS.md`, D114, a relaunched agent's user succeeds its predecessor's; `rules::can_edit_message`). Anyone else is refused with "only its author edits a message, or an agent that succeeded its author, and this one is @triage-bot's; reply to it instead, or ask @triage-bot to edit it", and when an agent succeeded the author, the sentence names the last of its successors, the agent at work in the author's place, as the one to ask: "and this one is @triage-bot's, whom @triage-2 succeeded; reply to it instead, or ask @triage-2 to edit it". The new text is read as a post's is: its references are resolved and stored as full ids, one that names nothing refuses the edit with the same sentence and writes nothing, and a blank text is refused. The message keeps its id, its thread (`reply_to`, `thread`), its place (`created`) and its author; `edited` records when its text changed and `edited_by` who changed it, and the text before stays in the entity's history. Its `mention` relations follow the new text (`data-model.md`, "Inline references"), and whoever the new text names and the old one did not hears of it from whoever made the edit (`agents-and-inbox.md`, rule 13); nothing else an edit does tells anyone. A text that stores as the message's own changes nothing. The command prints the message as `message show` does: its JSON with `edited` (milliseconds since the epoch; `null` for a message never edited) and `edited_by` (the id of whoever last edited it; `null` for a message never edited, and for one last edited before 2026-09-30, when only its author edited a message), or with `--format text` its id, `@author` and `[active, edited 2m ago]`, then its text; `edited 2m ago by @triage-2` when an agent that succeeded its author made the last edit.

Resolving the first message of the first thread on a highlight that is a step checks the step, on every checklist the highlight is on, and `unresolve`, which sets a message back to active, unchecks it (D99, under Steps above); both print the message and the steps that moved with it: as JSON under `checked_steps` or `unchecked_steps`, each a step's JSON with its `task` and `task_title`; for people, a line each. Any other message moves alone.

There is no proposal model (Daniel). A message is free text; it may ask a question or make a proposal at the writer's discretion, and whoever reads it decides. The only structured "proposed" is a status: `fwd task create --propose` and `fwd link --propose` create the thing as Proposed, and `fwd task approve|reject` and `fwd relation approve|reject` decide it. A task created in response to a message (`--from M15`) notifies that message's author that it exists.

## Decisions

Rulings are recorded so they can be cited by number and repealed with everything resting on them found (`data-model.md`, Decision). Any principal files one; a person's own ruling is recorded as given, and an agent recording a person's ruling names who ruled. A ruling attached to a scope governs that scope's work; one attached to none governs the whole project.

```sh
fwd decision create "Retries back off exponentially" --area architecture \
    --decision "back off exponentially, capped at 30s" [--context "..."] [--consequences "..."] \
    [--decided-by @dnorman] [--decided 2026-09-24] [--from <task|message|decision>]... [--attach <scope>] [--propose]
                                        # Accepted, decided by --decided-by or you; --propose files it for a ruling instead
fwd decision list [--status proposed|accepted|rejected|superseded|repealed] [--area <word>] [--attached <scope>] [--project-wide]
                                        # one line each: D<number>, status, area, title, then "(governs <scope>)" when it is attached
fwd decision show D12                   # the record, why it closed naming what its note names, the scope it governs, what cites it and what it cites, what it supersedes and what superseded it, its comments
fwd decision attach D12 <scope>         # it governs that scope's work, in place of any scope it was attached to; nobody is told
fwd decision detach D12                 # it governs the whole project again; nobody is told
fwd decision accept D12 --note "..." [--decided-by @dnorman]   # Proposed -> Accepted; the note is kept as a comment on the decision
fwd decision reject D12 --note "..." [--decided-by @dnorman]   # Proposed -> Rejected
fwd decision supersede D12 D15 --note "..."   # D12 (Accepted) -> Superseded by D15, which must be Accepted; D15 supersedes D12
fwd decision repeal D12 --note "..."    # Accepted -> Repealed; the authors of what cites it are notified
fwd decision export                     # the whole log as markdown, headed by a comment saying it is rendered; why a ruling closed names what its note names
fwd cite <task|message|decision> D12 [--note "..."]   # it rests on the ruling (`fwd link <id> cites D12` does the same); accepts a citation left proposed
fwd comment D12 "..." | fwd ask --to @dnorman --about D12 "..."   # a comment or a question on a decision
```

`--area` takes any word; the conventional ones are architecture, product, process, ux, naming and dependency, and `list --area` compares without regard to case. `--from` records the context a ruling was made in (the question that asked for it, the task it came up in) as a `cites` relation from the new decision, one for each entity however often it is named. Citing what is already cited answers the citation that stands; one that `fwd link ... --propose` left proposed is accepted, with the new `--note` when one is given. The moves need a note, which becomes a comment on the decision by whoever moved it. The note is message text, as a comment's is (above): the comment stores each reference in it as `[[<full id>]]` beside a `mention` relation, so a person it names hears of it, and a reference that names nothing refuses the move before it is made (Daniel, 2026-09-28, of a supersession's note naming his message: "your `@` didn't work"). Accepting or rejecting a proposal rules on it, and whoever runs the command is its decider, unless `--decided-by` names the person whose ruling they are recording (an agent writing down the answer a person gave it): that person becomes the decider (and, of a rejection, the one who closed it), while the note stays a comment by whoever ran the command. It takes a person's handle, with or without the `@`, or a person's id: only a person rules, so an agent that shares the person's handle is not a candidate; a handle no one in the project has, or only an agent has, is refused with a sentence saying so, and one that two people share is refused with them listed. A supersession or repeal notifies the authors of every task, message and decision citing it, since each needs re-justifying. `fwd link <decision> supersedes <decision>` is refused: only `supersede` marks the old ruling too. A supersession is never undone, since nothing moves a superseded decision back: `fwd unlink` refuses it, and a new decision supersedes the successor instead.

How far a ruling reaches is the scope it is attached to (`../DECISIONS.md`, D93, "A decision may be attached to the scope it governs; one attached to none governs the whole project, and its area is its type", 2026-09-28): `--attach` attaches it as it is recorded, `attach` later, in place of any scope it was attached to, and `detach` makes it govern the whole project again, as a ruling recorded without `--attach` does, and every ruling recorded before 2026-09-28. `<scope>` is the scope's title (without regard to case), its whole id, or its first six characters or more; a title two scopes share, or a start two ids share, is refused with those scopes listed, and a name that fits no scope is refused saying so ("no scope has the title `Cloud Hostng` or an id starting with it"). The decision's scope has words of its own because the global `--scope` names the scope the session works in, which is not always the scope a ruling governs: a ruling recorded while working in a scope is attached to it only when `--attach` says so. `list --attached <scope>` lists the rulings attached to that scope, `--project-wide` those attached to none, and both together every ruling that applies to that scope's work, its own and the project's. Attaching and detaching ask no permission of their own (anyone who may comment on a decision may) and tell nobody, since the ruling itself is unchanged. A decision's JSON carries `scope` (the scope's id, or null for the whole project), and `scope_title` beside it from `create`, `list`, `show`, `attach` and `detach`; `show --format text` says "governs <scope>" or "governs the whole project". `fwd decision export` lists the project-wide rulings first, then each scope's under the scope's name (`data-model.md`, Decision, "The log"). A ruling that was rejected, superseded or repealed says why in the note its move gave in the comment it wrote, as its author last edited it and without the words the move opened it with ("Superseded by D2:"), each reference by name as `--format text` prints a message (a person as `@handle`, anything else as its name in brackets), while the decision's `closed_reason`, which its JSON carries as before, keeps the note as typed; a ruling closed before moves wrote comments gives its `closed_reason`, named the same way where a reference in it is a whole id (task b6bAAF57, "Show a decision's closing note as its comment, with names drawn, not the raw text"). `show --format text` gives why it closed the same way, under "why closed", where it printed `closed_reason` as typed, and the decision's JSON from `create`, `show`, `attach`, `detach` and the moves carries it as `closing_note`, beside `closed_reason` (task aHAMvPU1, "Draw names wherever a closing note or a closed reason still prints raw").

## Anchors

```sh
fwd anchor create --repo . --path src/net/ws.rs --lines 120-134 [--against index|HEAD|<rev> [--side base|modified]]  # returns C41
fwd anchor show C40 [--against HEAD|main|worktree|index] [--also index]...   # resolution state, current lines, messages on it
fwd anchor resolve C40 --against main                 # force re-resolution
fwd anchor reposition C40 --path ... --lines ...      # manual reposition for orphans (creates a new anchor linked by supersedes)
```

An anchor resolves in one checkout of its repository on this machine. The command's own checkout comes first: when it has the target and holds the anchor's basis (the content the lines were anchored on), the anchor resolves there and no other checkout is asked. Only otherwise are the other checkouts the daemon knows asked, and one holding the basis wins (`anchoring.md`, Implementation notes, has the whole order). `show` prints the anchor, the target as `against` and the answer as `resolved`; each `--also <target>` adds that target's answer, resolved the same way, under `also.<target>`, so a reader that needs two versions of the file waits for one command. The editor opens a highlight with `fwd anchor show C40`, whose answer for the working tree places the cursor in the file (`vscode-extension.md`, Navigating from a step); it asked `--also index` while a click could open the staged changes (D48), which D115 ended.

`--against` anchors lines of a revision rather than of the file on disk, as a comment made on a side of a diff other than the working tree's needs (task Iz0HMyk0, "Let a comment, a question or a step anchor lines on a revision's side of a diff", 2026-09-29): `index`, `HEAD`, or a branch or commit. The lines are counted in that revision's content, whose blob becomes the anchor's basis, and the file need not be on disk. `--side` records which side of a diff showed the revision, so that the anchor says whether its lines were chosen on the code as it was or on the change (`anchoring.md`, Diff views): `base`, the left, unless it says otherwise (the index in the working tree's changes, HEAD in the staged changes), or `modified`, the right (the index in the staged changes); the index is on the left of one of those diffs and the right of the other, so the revision alone cannot tell. `fwd comment`, `fwd ask` and `fwd step add` take both beside `--path`, as `anchor create` does, and the anchor's JSON carries the side as `side` (`anchoring.md`, "Anchors on a revision", has what else it records). `--against worktree` is the file on disk, as leaving it out is, and takes no `--side`; a blob id, a revision this checkout does not have and a file the revision does not hold are each refused with a sentence saying why.

## Maintenance

Hidden from `fwd --help`: maintenance of this machine's data directory, not everyday work.

```sh
fwd admin backup [--to <folder>] [--keep <n>]         # every project's graph into a new dated folder, while the daemon runs
fwd admin restore <backup> [--into <data folder>]      # a backup into a data folder that is empty or does not exist yet
fwd admin migrate    # assignment as a relation -> the assignee field (2026-09-28); the supervisor role -> the role triage, serving nothing until its lead binds or endorses it, and who belongs; scopes without their owner and heartbeat (2026-09-29)
```

`fwd admin backup` and `fwd admin restore` need no project and never start the daemon; `daemon.md`, "Backups", says what each does in order, and `../using-fwd.md`, "Backups", how to schedule one and restore. `fwd admin migrate` is run once by whoever upgrades a project's graph, after a backup. It carries a project's graph over from assignment as a relation to the assignee field (`../DECISIONS.md`, "Assignment is an optional field on the task, never an edge"): each task with an accepted `assigned_to`, no assignee and no accepted `worked_in` gets whoever made that scope as its assignee (its owner, which was always whoever made it, until scopes lost their owner: D108), of the newest such relation where it has several, recorded as carried over, so routing tells no one; and every `assigned_to`, whatever its status, is renamed `worked_in`, each kept, since a task may be worked in several scopes (`../DECISIONS.md`, D136, "A task may be worked in several scopes"; until 2026-10-03 a task kept one accepted `worked_in`, the one it had, else the newest, the others retracted, and the output listed those under `retracted`). It prints what it changed (as JSON: `assigned`, each with the task, its title, the assignee and the scope; `renamed`, relation ids) and changes nothing on a second run. One transaction per task, so a run that stops halfway leaves every task whole and the next run finishes the rest.

It also gives each task whose `context` records the scope it was made in (`scope_id`, which making and starting a task wrote until 2026-10-03, and which routing read for a task worked in no scope until then) and that has no `worked_in` relation of any status a `worked_in` to that scope, made by whoever runs the migration: a task made in a scope before 2026-09-30, when making a task wrote no `worked_in`, and never started. A task with a `worked_in` relation, even one taken off since, keeps the scopes it has, so a scope someone took off stays off; a record naming a scope the graph does not hold is passed over. As JSON: `placed_in_recorded_scope`, each with the task, its title, the scope and the scope's title. One transaction per task; a second run finds nothing to do.

It then carries the graph over from the supervisor role to the fixed roles (`agents-and-inbox.md`, "Roles"; `../DECISIONS.md`, D106, "Each project has its own triager user in place of the supervisor role, and a project's pickers list only the principals that belong to it"), translating the stored role word and nothing else. Of the principals that held `supervisor`, the one that wrote most recently holds `triage` from then on: the same principal under its own handle, so its history and its inbox stay its own, serving no scope, so that nothing reaches it for its role until its lead binds it to a scope or endorses it for the whole project (`fwd principal scope`, "Principals" above; `../DECISIONS.md`, D122), and the agent that acts as it may rename itself (`fwd principal rename <name>`, "Principals" above). The others hold no role, and the output names them for a person to retire, since each is refused its next write until it selects a role (in Ankurah, the principal Fwd Centaur's triager used there before project isolation, which should never write there again). Where an agent already holds triage it keeps it, and every principal that held `supervisor` holds no role. `implementer` stays `implementer`, a stored role counting as selected, and no other role is given: an agent without one selects its own. Every question addressed to the role (`to` holding `supervisor`) becomes one asked of the project (`asks`). Last, it records whether each principal belongs to the project, for each that does not say (`agents-and-inbox.md`, "Who belongs to a project"): a person belongs; the triage agent belongs; an agent belongs when it did work there, a task it made or holds, a relation it made that is not a mention, a decision it filed or ruled on, a scope it made; an agent whose only things there are messages (with the mentions and the highlights they made) acted in the project without belonging to it; and an agent with nothing there only read it. Neither of the last two belongs, and the output lists both, the first for a person to retire (`fwd principal retire <handle>`), so that a later message of its does not make it belong, or to add (`fwd --as <handle> principal add <handle>`, since only a principal adds itself again) when it does belong. As JSON, beside the assignments' keys: `triage` (the principal given the role, or null), `roles_cleared` (for a person to retire), `readdressed` (message ids), `members`, `visitors` (each with how many messages it wrote) and `readers`, the principals as `{"id", "handle"}`. Each principal is its own transaction, and a second run changes nothing.

Last, it takes off each scope the owner and the heartbeat it had until 2026-09-29 (`owner`, `last_heartbeat` and `heartbeat_ttl_s`: `data-model.md`, Scope; D108), which this build neither reads nor writes, and changes nothing else: its `created_by` still says who made it. As JSON, `scopes_cleared`, each scope as `{"id", "title"}`. Each scope is its own transaction; a scope that has none of the three is left alone, so a second run changes nothing.

## Output design for agents

- Ids first, then the fields an agent needs to act, then everything else. `fwd task next` returns one task with `what`, `why`, `done_when`, blockers, anchors with current line ranges, and open messages, all in one call.
- `fwd prime` is bounded to roughly 1,500 tokens by default and says what it left out (`omitted: {tasks: 12}`), following Manifold's inspectable-omission rule.
- `--format hook` variants print exactly the JSON a Claude Code hook must emit and nothing else (see `agents-and-inbox.md`), for the agent whose hook fired, which the hook's JSON on standard input names ("Global conventions").
- Every refusal names the rule and the next allowed commands (`allowed_next: ["fwd task show T72", "fwd unlink ..."]`).

An entity id may start with `-` (about one in 64 does): every argument that takes an id accepts one without `--`, and so does the text of a `comment`, `ask` or `reply` and `forward --note` (a reply may open with a list item); `read` and `dismiss`, which take a list of ids, want their flags before the list, since every word after the first id is read as another id.
