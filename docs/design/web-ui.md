## What it is for

Seeing an inbox and the task graph without a terminal or an editor, and acting on them with exactly the rules the CLI runs. Daniel: "I really want a web UI hosted by the daemon" (R, 2026-09-25); Leptos, taking cues from Ankurah's community chat app for the Leptos idioms and from simplikeys and properlydone for the React-era patterns that transfer (R).

## Shape (P)

- **`crates/fwd-web`** is a Leptos 0.8 client-side app compiled to wasm32 by trunk into `crates/fwd-web/dist`. It is its own Cargo workspace: it only ever targets wasm32, so the root Cargo workspace excludes it and `cargo build|test|clippy --workspace` stay native. `scripts/build-web.sh` builds it.
- **The daemon embeds and serves it.** `crates/fwd/build.rs` makes sure the dist directory exists and asks cargo to rebuild `fwd` when it changes; `crates/fwd/src/serve.rs` embeds it with `include_dir!` and serves `/` and the files beside it with `no-cache` headers (stable asset names, no hashes). A binary built before the UI was built serves a page saying how to build it. Among those files trunk copies `mark.png`, the project's mark (`../DECISIONS.md`, D102, "The project's mark is the blue centaur with a forward arrow"), which `assets/logo/derive.py` makes from the mark's rendering: the page's favicon, and the mark before its name in the header.
- **`fwd ui [--lan] [--no-open]`** ensures the daemon, prints `http://127.0.0.1:<port>/?p=<uuid>` (the project the current directory resolves to; without one the URL has no `?p=` and the page opens on the first project, with the selector; a resolution that goes wrong, such as a marker that does not parse, is reported instead) and hands it to the desktop's opener. With `--as <name>` it acts as the principal that name or id names, which it never makes (an agent names itself with `fwd principal add`), and adds `?as=<its id>`, which names that principal however many share its name, only when there is a project. `--lan` prints `http://<the machine's LAN address>:<port>/?p=<uuid>` for a phone on the same Wi-Fi, first switching the daemon to listen on the LAN when it listened on loopback only, and says so (`fwd daemon start --loopback` reverts; `daemon.md`, Security).
- **Every project, with a selector** (R, 2026-09-25: "the daemon-embedded webapp should service all projects and have a selector"). The page lists the projects the daemon hosts (`GET /projects`) and shows the one `?p=<uuid>` names (with the daemon's reason when it could not open it), else the one this tab last opened (`sessionStorage`, written only once a project has opened, and passed over when the daemon can no longer open it), else the first that opened. A page that cannot show its project links to the other projects that opened, since its header and selector never appear. The header's selector is always shown, even while the daemon hosts one project (R, 2026-09-26: "I want a project selector in the web UI"); choosing loads the page again with the new `?p=`, which boots a fresh node on that project's socket; it leaves `?as=` behind, since principals belong to one project's graph. The selection lives in the query string because the page's router owns the fragment (`#/inbox` and the rest). `?lock=1` hides the selector: the VS Code webview opens the page pinned to its window's project. The webview is the only page opened so, which makes `?lock=1` also how the page knows it runs there, where a task opens full screen with Back (below, Tasks). Right after the selector (in the webview, after the project's name) sits the scope the Questions, Tasks, Decisions and Graph pages list by (below, "One scope selector for the Questions, Tasks, Decisions and Graph pages"); choosing another project loads that project's Inbox, so no choice among this project's scopes goes with it.
- **The page is an ephemeral Ankurah node**, as the CLI is (R: every client is an ephemeral node with ordinary reads, live queries and transactions; no bespoke RPC for data): IndexedDB storage named after the project id and a random suffix: one database per load, deleted once no tab holds its Web Lock any more, the WASM WebSocket connector to the same-origin `/p/<uuid>/ws`, and `ReactiveGraphObserver` from ankurah-signals so every Ankurah signal read inside a Leptos closure is a Leptos dependency. Booting gives the node at most 8 seconds in all to join the project's system and then finish its own initialization, and keeps the context it gets then for every read and write (a joined node has not always finished its own initialization, and its synchronous `context` refuses until it has). A daemon that does not answer, a daemon with no projects, a join that does not finish in time, any other boot failure and any panic each leave a sentence on the page, never a blank one.
- **Who reaches the daemon.** Nothing secret: the page needs only the daemon's address (Daniel, 2026-09-25: "Yes, remove it. We'll do an auth pass later."). The daemon refuses any request whose `Host` is not one of its own addresses, or whose `Origin` (a browser's) is neither its own page nor that of fwd's own VS Code webview, which the extension registers with the daemon (`vscode-webview://<id>`: the webview runs the page from the extension's own files, so the daemon also names that origin in its answers; `?daemon=` below has the detail), so another site, or another extension's webview, cannot reach the graph through the browser. No page at all, the daemon's own included, reaches the routes that stop the daemon, open a project or read the checkout registry. The daemon sends the page with `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'`, so another site cannot show it in a frame either. It listens on loopback unless the person chose the LAN; on a LAN bind every device on that network can open the page and read and write the graph until the auth pass (`daemon.md`, Security).
- **The daemon's address, `?daemon=`** (2026-09-26). A page the daemon serves finds the daemon at its own origin. The VS Code webview runs the page from the extension's own copy of it, so the page's origin is the webview's (`vscode-webview://<id>`), not the daemon's; the extension opens it with `?daemon=http://127.0.0.1:<port>`, and the page then asks that address for `/health` and `/projects` and opens the project's socket at `ws://127.0.0.1:<port>/p/<uuid>/ws`. The page honours the parameter only when its own origin is neither `http:` nor `https:`: a page served over HTTP was served by the daemon (or by a dev server proxying to it), reaches it at its own origin and ignores `?daemon=`, so a crafted link cannot point the daemon's own page at another port on this machine, which would receive whatever the person writes. The address must be `http://` with `127.0.0.1`, `localhost` or `[::1]` and a port, and the page says so otherwise: the webview's daemon is always on the same machine. `?p=` and `?lock=1` mean what they did, and the webview passes both. The daemon admits the webview's origin only once the extension has registered it (`POST /webview-origins`, `daemon.md`, Security), which the extension does before the page boots and again each time the page's connection drops (a restarted daemon has forgotten it): any extension's webview, a Markdown preview with scripts or a notebook's output can run script, so being a webview proves nothing, and another webview's origin is refused like any other site's. The daemon names a registered origin in its answers (`Access-Control-Allow-Origin`), since a browser shows a page an answer from another origin only when the answer names it. From another origin the page cannot tell a daemon that is down from one that refuses it (the browser hides a refused answer), so its sentence for a daemon that does not answer names both.
- **The page says how it is doing** (2026-09-26), to whoever embeds it: a `fwd:state` event on its window whose `detail` is `failed` when the page could not boot or stopped on an error, and otherwise its connection's state (`Connected`, `Connecting`, `Error`, `Closed`) each time that changes (`session::announce`). The VS Code webview's bridge listens: it has the extension register the page's origin again when the connection drops, and the extension gives a page that failed, or lost the daemon, a new document when a command opens it again (`vscode-extension.md`). In a browser tab nothing listens.
- **A newer page after a restart** (2026-09-29, task pNkDAdfq, "Tell a page that the daemon it talks to runs a newer build than the page, and offer a reload"; P). A restart is silent and the page's connection comes back by itself (`DECISIONS.md`, D80, "A daemon restart is silent and never ends a watch; only a long outage surfaces"), so a tab left open across a restart on a new build went on showing what the old build drew, and nothing said so: on 2026-09-28 Daniel looked at such a page for a quarter of an hour. The page notes the build the daemon names on `/health` when the page boots (`daemon.md`), which for a page the daemon served is the build the page came from, and asks again each time its connection comes back (`session::follow_restarts`). When the daemon now runs another build, a bar above the header says that the daemon restarted on a newer build and serves a newer page, with a Reload page button and a tooltip naming both builds; the bar goes if the daemon comes back on the page's own build. It never reloads the page by itself, since a reload loses a draft in a reply box. In the VS Code webview the page's files are the extension's, so there the bar says that the view's page comes with the extension and offers Reload window. The button sends a cancellable `fwd:reload` event on the page's window, which the webview's bridge takes, and the extension has VS Code reload the window (`vscode-extension.md`); in a browser nothing takes the event, and the page reloads itself. The page compares the daemon's build with the one it booted against, not with a stamp compiled into the page: the page and the binary are built at different moments, a checkout can change between the two, and a page's stamp would then differ from its own daemon's for good, showing a bar that no reload clears. A daemon that comes back on another port is out of the page's reach, since the page belongs to the old port, so no bar shows there; `fwd ui` opens the page at the new one.
- **The page asks for a highlight to be shown in the editor** (2026-09-28, R: "in the webview the same click reveals the span in the editor"; the event P). It does not call the VS Code API itself: a click on a highlight's lozenge, or on a step that is a highlight, sends a `fwd:reveal` event on the window, which can be cancelled and whose `detail` is the anchor's id (`session::reveal`). The webview's bridge takes it by cancelling it and posting `{type: 'reveal', anchor}` to the extension, and the page stays where it is; in a browser tab nothing cancels it, and the page goes to the highlight's own page. The extension opens the file at the lines, never a diff (Open, below; `vscode-extension.md`).
- **The page's text takes its size and fonts from what shows it** (2026-09-29, task RicmChrd, "Size the page's text to VS Code's workbench font in the webview, and scale the rest with it", after Daniel asked on 2026-09-28: "the font size seems too big in the vscode webview. is that sized to match the editor text?" It was not; P). So that in the VS Code panel the page reads as the workbench around it, and its code as the editor, the stylesheet takes the root element's size from `--vscode-font-size` and the page's font from `--vscode-font-family`, which VS Code puts on the root element of a webview's document (13 px and the system font by default); a browser puts neither there, and the page keeps its own 14 px and fonts. The root's size is the base: every other size of text (headings, pills, buttons, lozenges, metadata) is a fraction of it in rem, written as the pixels it comes to beside a 14 px base, over 14 (`calc(12rem / 14)`), and a line height a fraction of its text's size in em, so a browser draws the page as before and the panel draws it smaller in the same proportions. The lines of code a highlight shows (on its row and its page, in a lozenge's preview, and the first line a step shows) take the editor's size and font (`--vscode-editor-font-size`, `--vscode-editor-font-family`); ids, paths, branches and a code lozenge take the editor's font at the page's own sizes. Spacing, widths and borders stay in pixels, and so does the Graph's drawing, whose boxes, and the length its titles are cut to, are pixels too.

- **Waiting on you** (R, 2026-10-03, D137, from the design pass of task RgAEFRFb; the details P). A notification asks its reader for a move, a request, or tells them something, a conversation, and a request keeps asking until what it is about changes, which reading it does not change. ## Four modes (R, 2026-09-28; the details P)

What it is for: every kind of entity drawn the same four ways wherever it shows, so a new kind is one component rather than a change to every page, and a list, a thread or a page can show any entity without knowing its kind (Daniel: "we need to have ~3-4 different render modes / component variant for each kind of Entity"; `DECISIONS.md`, "Every kind of entity renders in four modes").

- **The four.** *Lozenge*, the fewest words that name it in an outline, with a preview on hover and a click going to it (below, "Lozenges"). *List item*, one line in a list: a task's steps, the lines of the Tasks, Decisions and Scopes pages, which lay the same things out in columns and stay tables. *Embedded*, more of it with the conversation about it beneath: a thread's row and what hangs beneath it (below, "Rows"), the one mode in which the page recurses. *Full*, everything its own page shows: the task, decision and scope panels, a highlight's page. What the page already drew is mapped onto the four rather than drawn again.
- **One component per kind, chosen by the models an entity carries.** `modes.rs` holds a `Kind` for each kind (its four renderers side by side) and a registry that picks one by the models the entity carries, as rows were picked before (below, "Models, not kinds"): the most specific registered match wins, and an entity carrying no model the page draws gets a lozenge with its short id, a line and a row with its id and its models, or a sentence. A new kind is one `Kind` and one line in the registry.

  | Kind | Lozenge | List item | Embedded | Full |
  |---|---|---|---|---|
  | task | its title, struck through once closed | short id, title (to its panel), labels, status, "3 of 8" when it has steps | its row, its comments and the messages about it beneath | its panel on the Tasks page |
  | decision | `D<n>` and its title, a fallen one in the warning colour | `D<n>`, title (to its panel), status | its row, its comments beneath | its panel on the Decisions page |
  | message | its author and first words | its author and its first line, references in words | its row (the highlights its text names beneath the text), its replies beneath it | its row alone, with its references |
  | scope | its name in green | its name (to the tasks worked in it), status | its row, nothing beneath | its panel on the Scopes page: its fields to change in place, who made it and when it started, and what names it |
  | highlight | `path:lines` in monospace | its name as the CLI and the extension give it too (fwd-core's `anchor_name`): `path:lines` in monospace, the basis, then the first line of the highlighted text cut at about fifty characters, as code; a whole file as its path and basis | its row: where it is, the highlighted lines, its threads beneath and a box for a new one | its page, `#/anchors/<id>` |
  | person | the handle, with the role (or "agent") beside an agent's | handle, display name, role | its line as a row, nothing beneath | its line and the open tasks assigned to it |

- **An embedded thing never embeds another in full** (`DECISIONS.md`, "Every kind of entity renders in four modes"). A thing asks for another in a mode and gets that mode, or the richest the mode it is drawn in allows (`Mode::nest`): inside a full page anything but another full page; inside an embedded thing the recursion goes on but never in full; inside a list item or a lozenge, lozenges only. Under the outline ruling of 2026-09-26 that means messages hang beneath a row as rows and everything joined by a relation is a lozenge on it.
- **Standing alone.** The embedded mode outside a card (a step opened in place) is a thread of its own for the acting principal, its own row's reply box always there, as a selected card's is (a highlight opened in place beneath a message opens its box on demand instead: below, "Inline references"); a lozenge outside a group (a reference in a message's text, the assignee beside a task's scope) has no label and looks as what it names looks in a group.

## Rows, and what hangs beneath them (R, 2026-09-26; the details P)

What it is for: a conversation reads the way it happened under whatever a card is about: a question, the answer under it, the follow-up under that; a task's comments; a decision's comments (Daniel: "Lets make sure that renderable referrent entities (reply for instance) is rendered under each message"; `DECISIONS.md`, 2026-09-26). Only messages hang beneath a row: every entity joined to a row's entity by a relation is a lozenge on that row instead (R, the same day, on the noise of the outline beneath cards: "I think a better approach would be to have each referent be merely a rendered as lozenge, and the user can mouse over to get more detail, or click to navigate to that thing", and, asked whether that includes replies: "Not referring to replies. Just things like relates to, and such"; below, "Lozenges"). The structure is his: a card mounts the row of the thing it is about; a row shows its own fields, its lozenges and its actions, and decides which messages it follows beneath it; every child is again a row of its kind, so the recursion is rows deciding their children.

- **A message row** (`message_row.rs`) shows its author, whom it asks when it asks someone (a question, or a forward), its age (with its priority when it asks someone), when it was edited if it was ("edited, 16:40", in the reader's time zone, with the day before the time when that day is not today), and by whom when an agent that succeeded its author made the last edit ("edited by triage-2, 16:40"), since the words are then not all the author's, a pill once it is resolved, its lozenges (what it was written on, when it opens a thread; the task filed from it; a ruling it cites, or one decided in its context; the task it is a step of; not what its text names, which shows in the text: below, "Inline references"), its text, each reference in it drawn as a lozenge; beneath the text, each highlight the message names, as a step shows beneath its task (below, "Inline references"); and reply and resolve, which on the first message of the first thread on a highlight that is a step reads "resolve and check the step", naming the tasks in its title, since resolving that message checks the step (`DECISIONS.md`, D99, "Checking a step resolves its highlight's first thread, and resolving that thread checks the step; each control says it does both"), and edit on a message the acting principal wrote, or whose author it succeeded (below, "Editing a message"). Beneath it come its replies and the forwards of it (messages whose `reply_to` is it; a forward's row says whom it asks).
- **A task row** (`task_row.rs`) shows its short id, its title linked to its page, its labels, its status and its lozenges (its scope, which leads to the Tasks page filtered by that scope; the rulings it cites; what it depends on and what waits for it; its subtasks; where it came from; its code); Enter on it opens the task. Beneath it come the comments that open a thread on it (messages whose `task` is it and that answer no other message: a reply to a comment carries the comment's task too, and belongs under the comment) and the messages linked to it by a `concerns` relation that is neither retracted nor rejected ("about it"). A task row whose task the page does not hold says "loading…" until the daemon has answered the standing queries, and "no such task" once it has (task 7dq1vEd_). As the own row of an inbox card that holds a review or a proposal, it shows the task's done-when and evidence, or its why and what, each labelled, between its line and the rows beneath it.
- **A decision row** (`decision_row.rs`) shows `D<number>`, the decision's short id (a click copies the whole id and says "copied", or "copy failed" when the browser copied nothing), its title linked to its panel on the Decisions page (on the scope the pages share), its status and area, the scope it governs as the scope's lozenge or "project-wide" (left out of the card's own row in a decision's panel, which shows it above with its picker), who ruled and on which day (or who proposed it), who recorded it when someone else did, its lozenges (what cites it, what it cites and where it was decided, what supersedes it and what it supersedes), and one line of the ruling. As a card's own row (in a decision's panel on the Decisions page, or in the inbox under a proposal, a repeal or a supersession) that line opens onto the whole record (why it came up, the ruling, its consequences, why it closed, which is the note of the comment its closing move wrote, as the panel gives it (above); a decision's panel shows the record above the row, so it hides the row's folded copy), and beneath its line the row offers the moves its status allows as the page's buttons, as a task's panel offers Approve and Reject (P, 2026-09-28, after Daniel found nothing on a proposal's panel to accept it with: the moves were small grey words beside the row's "comment"): Accept, the primary one, and Reject on a proposal, Supersede and Repeal on a ruling in force. A move asks for its reason in a box where Enter applies it, and Supersede also for the accepted ruling that replaces it; the reason becomes a comment on the decision, as `fwd decision` records it. A move made from an inbox card marks the card's notifications read, as a reply from it does; the form forgets its reason and its chosen successor whenever it is opened, cancelled or applied, so it never supersedes with a choice it no longer shows. Beneath it come its comments.
- **A scope row** (`scope_row.rs`) shows the scope's name, its short id, its status and branches, with its intention on hover (its owner and how long since its heartbeat as well until 2026-09-29: D108), and a lozenge counting the tasks worked in it. Nothing hangs beneath it (R, 2026-09-26, above): the tasks worked in a scope are the Tasks page filtered by it.
- **A highlight row** (`anchor_row.rs`) shows where the highlight is (`path:lines` and the basis, its name without the first line, which the lines beneath show; leading to its page, or in the VS Code webview to the editor), its lozenges, the highlighted lines each with its number (at most about twenty in sight, the rest scrolled), and a "comment" button; Enter on it opens its reply box, whose text opens a new thread on the highlight. Beneath it come its threads: the messages whose `anchor` is it and that answer no other message, each with its replies beneath.
- **A person row** (`person.rs`) is the person's line (handle, display name, role) with nothing beneath it.
- **Order, carets and bounds.** Siblings list oldest first, then by id, so every client lists them alike. A row with children, or whose children are not known yet, has a caret (▸ closed, ▾ open) that opens or closes it. Which rows are open lives outside the rows, keyed by each row's appearance (below), so a live update never resets it. Six levels below a card's own row open by themselves; a row at the sixth level starts closed and says how many wait below it ("3 more below"), and a row a person opens gets six more levels below it. A row lists at most 50 children, then "N more" shows the next 50. A row whose children are still loading says "loading…" and one whose query failed says why, never an empty list for something unknown.
- **Appearances, cycles and repeats.** A row is keyed by its appearance: for a card's own row, the card and the entity; for any other, the row above it, the link that placed it and its entity's id, never its position or the bare id. So a row keeps its focus, its reply box and its draft while rows around it arrive and move, and one entity can show in several places. A row whose entity already shows above it on its own path (a cycle: a chain of replies that arrived looping back on itself) is a "see above" row naming the entity, which leads back there. An entity that shows twice on the page says so on each row with a small muted mark (↗) at the row's end, whose hover says where ("also under" the row above the other, or "also a card of its own") and whose click leads there, so the note does not compete with the row's own content (2026-09-26); a row whose entity is already open elsewhere starts closed. A "see above" row beneath a row, closing a cycle back to it, is not somewhere else, so it earns no note.
- **Reply boxes.** A message row's reply box opens under the rows beneath it, where the reply will appear, by the row's reply button or Enter on the row. Sending replies to that message: the box closes, the row opens, and the new reply's row takes the focus once it arrives (for up to five seconds after the write returns). Cancel drops what was written. A box with a draft stays in sight when a branch above it closes. The card's own row's box is the card's reply box: it shows while the card is selected, replies to the card's message and stays open after sending. A reply sent from any box of a notification's card marks the notification read, as `fwd reply` does. A thread standing alone off a page of cards (a highlight's page, a step opened in place) shows its own row's box always; there the arrows at its first or last line leave it, as any other box's do. A highlight opened in place beneath a message's text is a thread standing alone too, but its box opens only by its "comment" button or Enter on its row, since it can sit on a card.
- **Editing a message** (R, 2026-09-28: Daniel asked an agent whether it could edit a question it had sent him, and the only fix then was a second question, which split the discussion across two threads; task rRHro34D, the details P). A message's author corrects it where it stands, and so does an agent that succeeded its author, which carries on the author's job (task sVCUXcEg): the edit button, among the row's actions on a message the acting principal wrote, or whose author it succeeded directly or through a chain of successions, and on no other (`message_row::offers_edit`, under the rule `rules::can_edit_message`, given the author's successors as the page's principals record them, tested natively), opens a box in place of the message's text, looking as a reply box does and holding the text as its author would type it again: a person as `@handle` where no other principal of the project has the handle (else as anything else is), a decision as `[[D12]]`, anything else by the first eight characters of its id in double brackets (`fwd_core::references::editable`), so the box shows names rather than ids and each resolves back to what it named. Enter or Save saves the new text through `ops::edit_message`, as `fwd message edit` does: the message keeps its id, its thread and its place, and whoever the new text names and the old one did not hears of it (`agents-and-inbox.md`, rule 13). A refusal (a name that fits nothing, a blank text) shows under the row in the words the command line uses, with the box open and the text as written, to correct. Escape or Cancel closes the box and leaves the text as it was. After a save or a cancel the row takes the focus back, and the edit button, hidden while the box is open, returns. The box's text lives with the row's appearance, as a reply box's draft does, so it stays while rows around it arrive and when a branch above it closes; its keys are its own, so the rows' arrows and Enter leave it alone. An edit made anywhere (the page, the CLI, the extension) shows at once, with its mark.
- **Queries.** Every row holds, for as long as it is on the page (open or closed, so a closed row can say how many wait below it), the live query behind each of its links that needs one: `reply_to = ?` under a message, `task = ?` under a task, `decision = ?` under a decision, `anchor = ?` under a highlight (Daniel: "It's ok if each message has its own livequery showing referring messages (recursively)"). Rows that show the same entity share one query through a page-wide cache that counts the rows holding each; when the last of them leaves the page (a branch closed, a card gone, another acting principal chosen), the query is dropped, which unsubscribes it at the daemon, so closing a branch or switching principals brings the count back where it was. With `?debug=1` in the URL the page header shows the count. The messages joined to a task by `concerns`, and every lozenge, read the page's standing queries and open nothing, as a row of the Inbox's Waiting on you and a line of Settled before you looked do until they are opened: opened, a row mounts the rows beneath its subject, and a notification on a line its thread, which hold theirs. Rows are built from each entity's own state, and a member that no longer matches the link that placed it is left out, since a live query's members have been seen to linger.
- **Models, not kinds.** Manifold is to be an entity-component graph, where one entity id carries several models, and its generic models are meant to sit on fwdcentaur's entities later. So a row's component, the embedded mode of its kind, is chosen by the set of models its entity carries (the most specific registered match wins; an entity carrying no model the page draws gets a row with its id and its models rather than nothing), and the links to follow are declared per model: an entity carrying both a message and a task would follow the links of both, each child appearance once. Every fwdcentaur entity carries one model today; where the page holds only an id (a step, a reference in a message's text), the first of its standing queries that holds the id gives the model.
- **Where it lives.** `referents.rs` (what refers to an entity: models, the links per model, children, appearances, levels and their states, the registry of components, and the four modes with the rule that an embedded thing never embeds another in full), `navigation.rs` (which row heads a card's rows, where the keys take the focus, which rows open by themselves, where the focus goes when its row leaves), `query_cache.rs` (the counted cache) and the first half of `lozenges.rs` (the table of how each kind of relation is drawn, and the plan of a row's lozenges: their groups, order, caps and counts) hold no Leptos, Ankurah or browser code and are tested natively with `cargo test --manifest-path crates/fwd-web/Cargo.toml` (the crate compiles natively; its tests never touch the browser). `modes.rs` is the registry of kinds, each kind's four renderers side by side. `thread.rs` draws the frame every row sits in and the rows beneath it, and answers the keys; `message_row.rs`, `task_row.rs`, `decision_row.rs`, `scope_row.rs`, `anchor_row.rs`, `person.rs` and `notification_card.rs` are the components above, each row module declaring the links its model follows and holding its kind's lozenge, list item and embedded renderers, and `cards.rs` the selection and keys shared by the Inbox and Questions pages; `waiting.rs` sorts the inbox's notifications into the rows of Waiting on you and the conversations, `accordion.rs` holds the inbox's sections and the stops of its selection, and `request_row.rs` draws a row of Waiting on you with its moves; the rest of `lozenges.rs` draws the lozenges, their one preview and where a click leads; the Decisions (`decisions.rs`) and Scopes (`scopes.rs`) pages are lists, the Decisions page with the panel that mounts a decision's own row and the Scopes page with the panel that makes a scope or changes one (`scope_panel.rs`), `new_task.rs` is the form for a new task in the Tasks page's panel, `anchors.rs` is a highlight's page, `steps.rs` a task's steps, `references.rs` a message's text with its references, `attachments.rs` the highlights a message names beneath its text, and `comment_box.rs` is the box beneath a task's or a decision's panel; ## Lozenges (R, 2026-09-26; the details P)

What it is for: naming, on a row's own line, everything its entity is joined to, so that what hangs beneath a card is the conversation alone and a writer who cites everything a task touches cannot bury it (Daniel: "I think a better approach would be to have each referent be merely a rendered as lozenge, and the user can mouse over to get more detail, or click to navigate to that thing"; "Not referring to replies. Just things like relates to, and such"). This retracts, for relations, the outline of the same day (tasks, subtasks and rulings as rows beneath what they are joined to), and the interim rules of the same night that tamed it (chips that collapse past three, "also under" notes on the rows it repeated, a decision row closed behind a line of counts): the lozenges' caps and counts are what is left of them (`DECISIONS.md`, 2026-09-26, "Relations render as lozenges").

- **What gets one.** Every relation joined to the row's entity, from it or to it, that still stands (accepted, proposed, or resolved as a checked step is; not retracted or rejected), read from the page's standing relations query; and, for a message that opens a thread, what it was written on (its task, decision, scope or code: fields of the message rather than relations, but referents all the same; a reply's are its thread's). Not the entity of the row it hangs under, which shows just above it (a comment beneath its task carries no "on" that task; a step opened in place beneath its task carries no "step of" it), not the messages linked to a task by `concerns`, which hang beneath the task as rows, not a task's own steps, which are its checklist (below, "A task's steps"), and not what a message's text names, which shows in the text (below, "Inline references"). One entity joined twice the same way is one lozenge, marked proposed only while every relation behind it is.
- **Groups, in a fixed order, each kind drawn its own way** (R, the same night: "Not all relationship types should be rendered the same"). One group per kind and direction, each headed by its label; the look and the default of each live in one table (`lozenges.rs`, `TABLE`), so changing how a kind reads is changing one row:

  | Group | Labels | Look | At rest |
  |---|---|---|---|
  | what a message is on | on; about (`concerns`) | plain | on: all; about: two, then a count |
  | citations | cites; cited by; decided in; decided here | the ruling's look: `D<n>` in monospace, then its title; a fallen ruling in the warning colour, first in its group; a proposed one muted, a rejected one struck through | three, then "+N more" |
  | dependencies | depends on; blocks | the other task's state: done muted and struck through, open or in progress in the accent, blocked (held, or waiting on something) in the warning colour | each while two or fewer; past two, one count per direction: "3 dependencies (1 done)", "blocks 4" |
  | structure | subtask of; subtasks; step of | a quiet tree glyph before the title, a done part struck through | subtask of and step of: shown; subtasks: a count first, "4 subtasks (2 done)" |
  | lineage | discovered from, led to; motivated by, motivates; supersedes, superseded by; duplicates, duplicated by | muted; "superseded by" on a decision in the warning colour, since it marks a fallen ruling | two, then "+N more" |
  | mentions | mentioned in | plain: the message's author and how it begins | three, then "+N more" |
  | association | relates to, either way | the quietest | always one count: "relates to 3" |
  | scope | none (a task's scopes); in this scope, on a scope ("worked here" until 2026-10-03) | the scope's green outline, its name; on a scope, the tasks in it as one count, "3 tasks in this scope" | on a task, each scope it is worked in (one until 2026-10-03, when a task was worked in one: D136); on a scope, the one count |
  | code | code; code of, on a highlight | `path:lines` in monospace; code of: the task's title | two, then "+N more" |

  A lozenge names its entity in a few words: a task by its title, a ruling as "D3" and its title, a message by its author and how it begins, a scope by its name, code by its path and lines (or its path alone for a whole file), a whole file a message names at a version by its path and that version (below, "Inline references"), a person by the handle, with the role or "agent" beside an agent's; one whose relation is only proposed has a dashed outline and says "proposed". "+N more" shows the rest of its group in place, and is in the warning colour when a fallen ruling is among those it holds back; a count lozenge shows its group in place and closes it again.
- **Hover, and the keyboard.** The pointer resting on a lozenge, or the keyboard's focus reaching it (Tab), opens its preview beside it, below it where there is room and above it otherwise, inside the viewport, in the VS Code webview as in a browser (`vscode-extension.md`, the webview's Content Security Policy): a task's short id, title and labels, status, priority and scope and the first lines of its why; a ruling's number, title, status and area, who ruled, and a line of the ruling; a message's author, whom it asks, its age and its text (about six lines, its references in words); a scope's name, status and intention; code's `path:lines` and basis, then its first four highlighted lines, as they were anchored (where they are now is per checkout, kept on the machine that resolved them, not in the graph); a person's display name, handle and role, and that the lozenge leads nowhere yet. There is one preview on the page (`LozengePreview`), fed by the standing queries; it opens no query of its own, and closes when the pointer or the focus leaves, on Escape, and when the page goes elsewhere. A lozenge taking the focus does not select its card: that would move the page under the pointer (the card selected before closes its reply box) between the press and the release.
- **Click.** A task leads to its panel (`#/tasks/<id>`), a ruling to its panel (`#/decisions/<id>`), each list behind it on the scope the pages share, which the page puts in the route (above, "One scope selector for the Questions, Tasks, Decisions and Graph pages"; until 2026-09-29 a task's kept the Tasks page's filter and a ruling's the Decisions page's, each on its own page alone), a scope to the Tasks page filtered by it, a message to its card on the acting principal's Questions page (`#/questions/<id>`, where it shows whomever it asks) when it asks someone, to its question's card when it answers one, else to the panel of the task or the decision it is on, else to the inbox; code to the highlight's page (`#/anchors/<id>`), or in the VS Code webview to the editor (above, "The page asks for a highlight to be shown in the editor"); a whole file a message names at a version to its whole-file highlight's page, or in the VS Code webview to the editor at that version; a person nowhere yet, since a person has no page. Enter on a focused lozenge does the same.
- **Touch.** Where there is no hover (a tap, or a device matching `(hover: none)`), the first tap on a lozenge opens its preview instead, with an "open" link that goes where a click would; a second tap on the same lozenge goes there too, and a tap anywhere else closes the preview.
- **In the panels.** The task panel's "Relations", the decision panel's "References" and a highlight page's "References" are the same lozenges, one group a line, above the panel's thread: the decision panel's and the highlight page's own rows leave their lozenges to them, and the task panel's thread has no row of the task's own (above, Tasks); the task panel leaves the scope out, since it shows beside the assignee.

## A task's steps (R, 2026-09-28; the details P)

What it is for: a review, or any task made of parts to look at in turn, reads as a checklist on the task's own page, each part drawn as what it is (Daniel, on the review guide: "the highlight itself should be the thing with the step_of link to the task. because the agent is saying \"look here\""; his sketch of a line: "[x] `highlight content first ~50 nonbreaking chars` @ foo.rs version lines xx-xx"; `DECISIONS.md`, "A step is an edge from any entity to a task, and the highlight is the step" and "The checked state is the step edge's status"). He reversed the sketch's order on 2026-09-29, so that a reader finds the file first ("I think we should reverse the order of code references. I suggest filename:line-line `code` or something like that. to make it more readable"; task ZYjo8Yyr): a highlight's line reads ``ws.rs:4-8 2418c54 `fn reconnect() {` `` on the page and in the CLI alike.

- **What is a step.** A `step_of` edge from anything (a highlight, a message, another task) to the task, while it is accepted (unchecked) or resolved (checked); a proposed, retracted or rejected edge is none. The steps list by the edge's position, a fractional key compared as text (a step with none, made by a client that gave it none, after every step with one), then oldest first, then by the edge's id, as `fwd step list` lists them, so every client lists them alike.
- **Where they show.** On the task's panel between its prose and its relations, under the heading "Steps" with how many are checked ("3 of 8"); nothing at all while the task has none. The Tasks list shows the same count beside the task's title ("3/8"), and a task's list item wherever it is drawn.
- **A step's line.** An expander, a check box bound to the edge's status, and the step drawn by its own kind's list item (a highlight's `path:lines`, basis and first line; a message's author and first line; a task's short id, title, status and its own progress). Pressing the box checks the step, resolving the edge with who checked it and when in its closing fields, or unchecks it, returning the edge to accepted (`ops::check_step`, as `fwd step check` and `uncheck` do); the box shows the edge's status, so it changes once the edge does. A highlight's first thread moves with its step (`DECISIONS.md`, D99, "Checking a step resolves its highlight's first thread, and resolving that thread checks the step; each control says it does both", which superseded D91): checking resolves that thread's first message and unchecking sets it back to active, with the highlight's steps on other checklists, so the box's title says "check the step and resolve its thread" or "uncheck the step and unresolve its thread" (just "check the step" for a highlight no one has started a thread on, and for a message or a task, which move alone), and the line shows the thread's state after the step's list item, "thread open" or "thread resolved": the two facts side by side, since a thread started after its step was checked is open while the step is checked. Until D91 and D99, the box checked the step only. A click on the line goes where a click on the step's lozenge would: a highlight to its page, or in the VS Code webview to the editor; a message or a task to where its lozenge leads. The expander shows the step's embedded form in place beneath its line: a highlight's lines, its threads and a box for a new one; a message's row and its replies; a task's row and its comments; each leaves out the lozenge of the task it shows beneath.
- **Taking a step off** (task 9dvGW0EI, "Take a step off a checklist and retire its highlight in one command: fwd step remove"; the details P). A step that no longer belongs on the checklist, because its work moved to other tasks or it was added by mistake, comes off it rather than being checked, which would record it as done. The task's creator and its assignee, whose checklist it is and who alone may take a step off (`rules::can_remove_step`), see "remove" at the end of each step's line; anyone else sees nothing there. It opens, beneath the line, a box for the reason, kept on the step, which takes the focus; Enter or "Remove the step" takes the step off through `ops::remove_step`, as `fwd step remove` does, and Escape or Cancel closes the box and gives the line the focus back. For a highlight with an open thread, a choice beneath the box retires it too: it says how many threads it resolves, so the editor stops drawing the highlight while its page keeps them, and names the tasks whose step on the highlight its first thread checks (`DECISIONS.md`, D99, "Checking a step resolves its highlight's first thread, and resolving that thread checks the step; each control says it does both"), worked out by `rules::retire_highlight` from the page's messages and relations; chosen, the button reads "Remove and retire". A step that is a message or a task, or a highlight with no open thread, offers no such choice. A refusal (a blank reason, among them) shows beneath the box, which stays open; once the step is off, the step after it takes the focus, else the one before. No one is told. Who is offered the control and what the choice and the button say are tested natively.
- **Keys**, on a step's line (Tab reaches the steps once, at the step last focused, else the first):

  | Key | What happens |
  |---|---|
  | ArrowUp, ArrowDown | the step above or below |
  | Home, End | the first or last step |
  | Space | checks the step, or unchecks it, and a highlight's first thread with it |
  | Enter | goes where a click on the line goes |
  | ArrowRight, ArrowLeft | opens or closes the step in place |
  | Delete | opens the step's removal beneath its line, for the task's creator and its assignee |

  Within a step opened in place the rows keep their own keys (above, "Rows"); Tab goes into them, and ArrowUp from its first row or ArrowDown past its last comes back to the steps.
- **Not yet.** Adding and ordering steps from the page: `fwd step add` adds one at the end, and nothing reorders steps yet. Taking one off was here too, done with `fwd unlink <step> step_of <task> --reason`, until the remove control above.

## A task's labels (R, 2026-09-28; the details P)

What it is for: seeing what kind of work each task is, a bug or a feature, and finding the tasks of one kind, without task types (Daniel, 2026-09-28, to the triager's recommendation of labels over a task type for bug and feature: "ah yes. label is better."; `DECISIONS.md`, D97, "A task's kind, such as bug or feature, is a label, not a task type").

- **Where they show.** As small pills after a task's title wherever the task is drawn: its line in the Tasks list, its row (in a thread, on an inbox card, on its own panel), its list item (a step of another task, say) and its lozenge's preview. A label's pill is filled, not outlined, so that it never reads as a status.
- **The filter.** "label" on the Tasks page offers "all labels", then every label a task of the project carries, `bug` and `feature` first and the rest in alphabetical order; choosing one keeps the tasks with it, together with the other filters. The choice lasts while the Tasks page shows, as the title filter does; the route does not carry it. A label chosen stays chosen, and shows so, after the last task carrying it loses it.
- **On a task's panel.** Beneath where the task is worked and who is assigned, "labels" shows its labels, each with a button that takes it off, then a box that adds one, or several with commas between them, when Enter is pressed or the box is left, as a picker's box on the form for a new task chooses. The box suggests `bug` and `feature` first, then the other labels in use, less those the task has; each suggestion follows whatever the box holds before the label being typed, so choosing one keeps the labels typed before it. The page writes them through `ops::label_task` and `ops::unlabel_task`, which change a task's labels by the rule `fwd task amend --label` and `--unlabel` follow, and a refusal shows beside the box. The form for a new task suggests labels the same way in its Labels box.
- **What a label is** is `fwd_core::labels`'s to say, for the page and the CLI alike: stored trimmed, each run of whitespace one space, and in lower case, so `Bug` typed in a box is the label `bug`; never blank; never holding a comma; each once on a task (`data-model.md`, Labels). What a box takes and suggests, in what order, and what the filter keeps are worked out as data and tested natively (`labels.rs`).

## Inline references (R, 2026-09-28; the details P)

What it is for: a message that names a task, a ruling, a highlight or a person shows each as the thing itself, and the thing named lists the messages that name it (Daniel: "each of them should shadow/be shadowed by and edge which corresponds to the inclusion point (and is not redundantly represented in the relationship list, but SHOULD appear in the references section of the thing its pointing to)"; each reference drawn as "the lozenge render component for the (first) member model of that entity"; `DECISIONS.md`, "Inline references are shadowed by `mention` edges").

- **In a message's text.** The posting path stores every reference as the entity's whole id in double brackets (`[[<id>]]`), whatever the writer typed, and writes a `mention` edge beside each. The page draws each `[[<id>]]` as the lozenge of the entity's first model, found in its standing queries; an id they do not hold draws as a lozenge with its short id. Text written before then kept `@handle` as typed: a bare `@handle` (not inside a word, so not an address) draws as the person's lozenge when one principal of the project has that handle, and stays text otherwise (when none has it, or several share it), as does anything in double brackets that is not an id. What counts as a reference is what the posting path reads (`fwd_core::references::find`), so code (a code span, a fenced block) stays text. Where a lozenge cannot go (a lozenge's own name, a preview, a list item, an inbox card's line) a reference reads in words: `@handle` for a person, the rest in brackets ("[Cap the retry delay]").
- **A whole file a message names at a version** (R, 2026-09-30, Daniel: "do we have a way of referencing a whole file (for a given commit / unstaged state) and having that appear as a lozenge? we should."; task nVE7KTeSqiX0; the details P). The posting path stores it as its whole-file highlight's id with the version after an at-sign, `[[<id>@<version>]]` (`data-model.md`, "Inline references"), and the page draws it as a lozenge in the code's look naming the highlight's path and the version the text names, the commit's first seven characters, `index` or `on disk` (`docs/using-fwd.md on disk`; fwd-core's `anchor_name::AnchorName::file_at`): the version comes from the text, since one whole-file highlight serves every version that holds the same bytes. Its preview says which version it is in a sentence, the commit's whole id among them; a click goes to the highlight's page, or in the VS Code webview asks the editor for the file at that version (`session::reveal`, the version after the id and an at-sign; `vscode-extension.md`, "Navigating from a step"). It stays its lozenge in the text and does not show beneath the message, as a highlight named by its id does (below), since a whole file has no lines to open in place. Where a lozenge cannot go, it reads `[docs/using-fwd.md on disk]`. The page has no checkout to read a file in, so a path written in one of its boxes (`[[docs/cli.md]]`) is refused by the posting path with a sentence saying to write it from the CLI or in a comment in VS Code's editor, which posts through the CLI in the workspace's checkout; the daemon knows every checkout it has seen, but a file on disk or in the index belongs to one of them, which the page cannot choose. The stored form the page's edit box writes back, the start of the highlight's id and the version (`[[vwugaN8h@index]]`), reads again with no checkout, so a message naming a file is edited on the page as any other.
- **The mention search** (`mentions.rs`; `../DECISIONS.md`, D107; the details P). Beneath each box that writes a message (the Ask box, a panel's comment box, a row's reply box, the box that edits a message), while the caret is in an `@` and a name being typed (an `@` that opens a mention: at the start, or after a space or an opening mark, never in code), a list offers the principals that belong to the project whose name starts with what is typed, without regard to case, by name, eight at most, each with what it is (person, its role, or agent) and, beside a name two or more principals of the project share, the scopes its work is in as lozenges (`agents-and-inbox.md`, "A principal's name"); the agents that have written nothing for twelve hours come after all the others, under a heading, "dormant", which the keys pass over, so that one is offered among the eight only where too few others match (`../DECISIONS.md`, D123). A click, or Up and Down and then Enter or Tab, writes the mention in place of what was typed, followed by a space, and Escape closes the list for that mention; the list takes those keys before its box and marks them used, so neither the box nor the page acts on them. A mention is written `@name`, or `@` and the first eight characters of the id for a name two or more share, which posting would refuse: posting stores either as the chosen principal's id.
- **What names a thing.** A `mention` edge shows on the thing named, never on the message: "mentioned in", a group of the message's lozenges among the task's relations, a decision's or a highlight's references, and on a scope's line where the Tasks list is filtered to it.
- **A highlight a message names shows beneath it** (R, 2026-09-28, Daniel in a review thread, to the agent there: "Are you able to attach a highlight to this thread showing me what you mean? This should be possible similar to attaching a step to a task, except it's a reply or part of a reply here"; the details P). Naming a highlight in the text is the attachment: no other syntax, and no command. Beneath a message's text, each highlight the text names shows as a step shows beneath its task: one line, the highlight's list item (`path:lines`, the basis, then its first line cut at about fifty characters), with an expander that opens the highlight's embedded form in place: its lines, its threads, and a "comment" button whose box opens a new thread on it. That box opens on demand rather than standing open as a step's does: on a page of cards the box that stands open is the card's own, which the page gives the keyboard to when it selects the card. A click on the line goes where a click on the highlight's lozenge goes, its page or, in the VS Code webview, the editor, and so does the heading of the highlight opened in place. Only highlights show there: a task, a decision, a message, a scope or a person a message names stays a lozenge in its text, and so does a whole file it names at a version (above). Each shows once, however often the text names it, in the order the text first names it, and not at all where it already shows above the message: a message in one of a highlight's threads, on its page or opened in place, shows only the other highlights it names. The message's row shows them wherever it shows (a thread, an inbox or Questions card, a highlight's page, a step opened in place); its list item, its lozenge and its preview do not. They are read from the text's stored ids, the ones its lozenges come from, rather than from the `mention` edges beside them, so a message posted before the page showed them shows its highlights too, and a highlight the page does not hold yet is only its lozenge in the text until it arrives. The keys, on a line (Tab reaches each): ArrowRight and ArrowLeft open and close it in place, Enter goes where a click goes, ArrowUp and ArrowDown move between the lines, ArrowUp from the first line goes back to the message's row and ArrowDown past the last goes on as from the message's row; within a highlight opened in place its rows keep their own keys, and ArrowUp on its own row comes back to its line.

## Leptos and Ankurah idioms (from the community app, kept here so they are not rediscovered)

- Read Ankurah signals (`LiveQuery::get`, a `Read<T>`) inside `move ||` closures in `view!`; import `ankurah::signals::Get as AnkurahGet` beside Leptos's `Get`.
- Look one entity up by its id through `store::Arrivals` (`store::task` and its siblings, a card's notifications), never by `get()` and a search, nor by the result set's `by_id` alone: `get()` copies every member and makes its reader run again at any change to any of them; `by_id` copies one but makes its reader run again whenever any member arrives or leaves; `Arrivals::member` copies one and makes its reader run again when that one arrives or leaves, which the query's change sets name, each field read tracking its own entity (tasks GEQEKfUd, unFIWd5c). Keep what a reader derives from such a lookup in a `Memo`, as a card keeps its notifications, so that a change elsewhere stops at the memo.
- Re-render a list whole in one closure rather than keying rows with `<For>`: an entity whose properties change keeps its id, so a keyed row would not redraw; whole re-renders are cheap at a project's size. The exception is a list whose rows hold the focus or own something: the cards are keyed by id, the rows beneath them by appearance and a task's steps by their edge with `<For>`, so a reply box (its focus, its caret, its draft) and a row's live query survive other rows arriving or changing, and each row reads what can change about it (a notification's status, a message's text) inside its own closures, so it still redraws. A recursive component erases its view type (`.into_any()`) where it recurses.
- The `view!` macro accepts only the ARIA attributes it knows (`aria-expanded`, `aria-label`, `aria-busy`), and `aria-level` is not among them: set such an attribute with `.attr(name, value)` on the built element.
- Focus and scroll after the page has drawn: an effect on the selection hands the work to `request_animation_frame`, by which time the newly selected card and its reply box exist.
- A select that shows state a link can also change (the header's scope filter, which the route carries) sets its value from an effect, which runs once its options are drawn: an option's `selected` attribute stops moving a select once a person or a script has chosen in it.
- App-lifetime handles live in `OnceLock` statics behind accessors (`ctx()`, `acting()`, `route()`), the community pattern; the WebSocket client is not `Send` and sits in a `SendWrapper`, reached through its accessor rather than captured.
- `wait_system_ready` has no timeout and resolves only over the socket: run it as its own task and poll a flag with a deadline.
- Never enable `ankurah/react` for a Leptos build (it pulls React-only glue and breaks). Every getrandom major in the graph needs its browser backend feature, and getrandom 0.3 also needs the `getrandom_backend="wasm_js"` cfg, which `.cargo/config.toml` sets for the wasm target only.
- Closures handed to `view!` need to be `Fn` and usually `Copy`: keep row-level state in `RwSignal`s and `Copy` values, and derive small `Copy` enums from JSON before building handlers from them.

## Building and developing

`scripts/build-web.sh` (trunk, release) then `cargo build -p fwd`; `cargo test --manifest-path crates/fwd-web/Cargo.toml` runs the crate's native tests (the pure modules behind the rows, and the reply boxes' line test in `keys.rs`); `fwd daemon stop` and any command restarts the daemon with the new binary. For a live-reload loop against a running daemon: one `[[proxy]]` table per backend path in `Trunk.toml` (`/p/` for the sockets, `/health`, `/projects`), the daemon started with `FWD_DEV_ORIGIN=http://127.0.0.1:8080` so it accepts the dev server's host and origin, and the dev server's page opened with the `?p=<uuid>` that `fwd ui --no-open` prints. CI installs trunk and the wasm32 target, checks fmt and clippy for the web crate on wasm32, builds the UI before `cargo build --workspace`, and the both-roles walkthrough checks that the daemon serves the built page.

## Open (U)

- **Ruled (2026-09-25): the VS Code extension bundles this Leptos app** in its own webview, with its own ephemeral node, rather than framing the daemon's page (Daniel: "i'm ok with bundling it"). So this crate is built twice from one source: into `fwd` for the browser, and into the `.vsix`. Closed 2026-09-26: the daemon admits the origin of fwd's own webview, which the extension registers with it (above, `?daemon=`); how the extension host reaches the graph is in `vscode-extension.md`.
- The graph is a drawing, not a canvas: no dragging and no Back stack (the extension design's graph panel). Enough for dozens of tasks; a real canvas comes when a project outgrows it. A scope of seventy tasks needed a way to follow one task through the drawing, so selecting a task lights its whole chain (above, Graph; task bL58YOSa); this note's "no focus depth" was a proof-of-concept limit, not a ruling.
- Whole-page snapshots (every message, every anchor) are fine for one project and wrong for the simulator's size; per-page queries and virtual lists come with that project.
- Short ids (T18, in part, 2026-09-26). The page shows an entity's first eight characters, and in the task panel, the decisions and scopes lists, and on decision and scope rows a click copies the whole id; the CLI takes six characters or more of any id, and `D<n>` for a decision; JSON output and stored references stay full ids. Still open: whether tasks and the rest get numbers of their own as decisions have, and a way to type a short id into the page.
- Every row holds a live query per link that needs one. That is good enough for a page of cards; Daniel expects a graph query language in Ankurah to do the recursion itself later (`DECISIONS.md`, 2026-09-26). A query closes the moment its last row leaves the page; a short grace, so that reopening a branch reuses its queries, is not built.
- The reactive_graph bridge in ankurah-signals (`signals/src/reactive_graph.rs` at the pinned revision) keeps an entry for every Ankurah signal it has ever tracked and never removes one, so a query per row grows that map for the page's life. Small now; the prune belongs in ankurah-signals.
- A row's models come from the query that found it (a message query finds messages), and an entity the page knows only by its id (a step, a reference in a message's text) takes the model of the first standing query that holds it, which is exact while every entity carries one model. Once entities carry several, they come from the entity itself (`entity().memberships()`, `research/multi-model-entities.md`). A row reads its models when it arrives on the page, so an entity that gains a model while its row shows keeps that row's component and links until the row is drawn again.
- CI checks this crate's formatting and wasm32 clippy but does not run its native tests yet.
- A lozenge naming code, and a step that is a highlight, lead to the highlight's page in a browser. In the VS Code webview the bridge takes the click and hands the extension a `reveal` message, and the extension opens the file at the lines in the normal editor, never a diff (`DECISIONS.md`, D115, "Clicking a highlight in VS Code opens the file at its lines in the normal editor, never a diff", 2026-09-29, which superseded D48; `vscode-extension.md`).
- The page shows a highlight's lines as they were anchored, never where they are now: that is per checkout, and the browser has no checkout. A code view that follows the lines through later versions would need the daemon to resolve them for the page.
- A person has no page, so the person's lozenge leads nowhere; its preview says so. Adding a task's steps happens in the CLI (`fwd step add`), not yet on the page; nothing reorders them yet.
- The arrows count lines by line breaks, not by how the box wraps them, so ArrowUp inside a long wrapped first line leaves the box (for the card above, from the card's own box; for the row above, from any other) instead of moving the caret up a row. Measuring wrapped rows would need the text laid out off screen.
