Implementer and Triage

Two agent roles share one graph with the people on a team. This page shows how they interact, what lands in each inbox, what each may do without asking, and a first point of view on why the lines are drawn where they are. Every mechanism here is a proposal until it has run. The second role was the supervising agent, a role any number of principals could hold, until 29 September 2026; it is now the role triage, which one agent in a project holds, one of the four roles each agent selects for its own principal: lead, triage, implementer and reviewer (Daniel, 29 September 2026; ../DECISIONS.md, D106, “Each project has its own triager user in place of the supervisor role, and a project’s pickers list only the principals that belong to it”).

The cast

The person human

Comments on code and tasks, asks and answers questions, approves Proposed tasks, accepts reviewed work. Works in scopes too, when working by hand.

Implementing agent implementer

Works in a scope, an area of work it may share: an intention, a branch, a set of tasks, owned by no one (D108, “A scope has no owner”). Takes ready work, does it, files what it discovers, and hears about comments on its code while it works.

Triage agent triage

The one agent in a project that holds the role triage; the questions asked of no one in particular reach it, and comments on scopes. Works in no scope. Keeps the graph tidy: links comments to tasks, turns musings into proposed tasks, approves within its policy, answers what it can, forwards the rest.

The graph daemon

The durable node. Every write is an ordinary transaction; a routing service decides who needs to know and creates notifications; nothing is sent, only pointed at.

The objects they share

Task what, why, done-when; one status; readiness derived from dependencies.
Relation a typed edge with its own status and provenance: depends_on, subtask_of, motivated_by, discovered_from, concerns, assigned_to.
Message free text, durable and visible, with a context map saying what it is about and who it is for. Some messages ask questions or make proposals; that is the writer’s choice, not a type.
Notification a thin pointer created only when a specific party needs to know: recipient, type, Unread / Read / Dismissed, target, originator.
Scope an area of work anyone may work in: intention, branches, the tasks worked in it. No owner and no heartbeat since 2026-09-29.
Anchor a line range in a file at a blob, with its own identity, so comments on code survive commits.

One conversation, end to end

Daniel is looking at task T60 and wonders aloud. Nothing here requires him to open the CLI; the triage agent turns the musing into a proposed task, Daniel is told the task exists and looks at it, one approval makes it real, the implementer picks it up, and a later comment on the code reaches the implementer while it is working.

  1. Daniel writes a comment on T60. It is a message with task_id in its context. Routing gives the triage agent a TaskCommented notification; nobody else needs to know yet.
  2. The triage agent reads it as a suggestion, not an order. It creates T80 in Proposed status with a discovered_from relation back to the comment. Because the task came from Daniel’s message, routing gives Daniel a TaskCreated notification pointing straight at T80. No reply to read first; he looks at the task, which is what he wanted to do anyway. The triage agent replies only when something needs explaining.
  3. Daniel approves. One verb: T80 goes Open. Had he written “do X” rather than “what if”, the triage agent could have created it Open directly; the difference between a musing and an instruction is the triage agent’s judgment, and when unsure it creates the task as Proposed.
  4. The implementer’s next task next --claim returns T80 with its what, why and done-when, and claims it into scope S3 in one transaction.
  5. While S3 works, Daniel comments on lines of the file it is changing. That comment carries an anchor. Routing notifies the triage agent and, because S3’s branch touches that file, the implementer. The implementer’s hook injects it before the next model call; on Claude Code the daemon also pushes it into the session between tool calls.
  6. The triage agent links the comment to T80 with concerns and appends the requirement to T80’s done-when, so the acceptance criterion now says what Daniel said.
  7. The implementer acts and replies with what it did. Its reply is a message in the same thread; Daniel sees it as a notification and, in the editor, as a resolved comment on those lines.
  8. The implementer submits with evidence. T80 needs review, so the triage agent gets ReviewRequested (its card shows T80’s done-when beside the evidence), accepts when the evidence settles it, and otherwise asks Daniel. T80 is Done; anything that depended on it is now ready and its assignees are told.

The implementing agent

What it is for. It turns ready tasks into changes without losing the reasons, and it stays steerable while it works. The graph is its memory across compaction and sessions: why a task exists, what done means, which lines people care about. The inbox is the person’s steering wheel mid-task.

What it may do

  • direct start, submit, return-to-work, hold and release its own assigned tasks.
  • direct create subtasks of its own tasks, and discovered_from and motivated_by relations for them.
  • direct comment, ask, reply, forward, dismiss its own notifications.
  • as Proposed any other task, any depends_on between tasks it does not own.
  • ask, in a message cancelling anything, retracting a relation, changing another task’s text, reassigning work.
  • never approve its own Proposed tasks, accept its own submissions.

The hooks that drive it

  • SessionStart: attach the session to its scope, print the primed context.
  • PostToolBatch and UserPromptSubmit: pop unread notifications into context.
  • Stop: refuse to end with unread notifications, up to eight times.
  • PreCompact: re-prime, so the tracker survives compaction.
preliminary point of view

The implementer’s rights stop at the edge of its own tasks because that edge is where an agent’s confidence is well founded. It knows what it is doing; it does not know what the rest of the team intends. So subtasks of its own work are direct, and anything that touches someone else’s work is created as Proposed and costs a person one approval. The one exception is discovery: an agent that finds necessary work mid-task must be able to record it instantly, in Proposed status, without stopping to ask, because the alternative is that the discovery lives only in a transcript that will be compacted.

The triage agent

What it is for. People should be able to talk to the graph in plain language, on code or on tasks, and have it stay correct without clicking through a form. The triage agent is the interpreter: it turns comments into links, requirements and proposed tasks, answers what the graph already knows, and routes the rest to whoever can answer. It is also the janitor: orphaned anchors, Proposed tasks nobody decided.

What it may do

  • direct link a comment to tasks (concerns), add relates_to, motivated_by, discovered_from.
  • direct append to a task’s why, what and done-when; never rewrite them wholesale.
  • direct create tasks in Proposed status; create subtasks under an existing task.
  • direct approve or reject Proposed tasks and relations within its policy; re-triage a message’s priority.
  • direct answer, reply, forward.
  • ask, in a message cancelling a task, retracting an accepted relation, reassigning work, replacing a task’s text.
  • never accept a submission (that is review, and review is a person’s), start tasks, edit code, dismiss someone else’s notifications.

Guardrails

  • Caps per run; dedupe by target; a hop count on forwards.
  • A confidence threshold below which it asks (“I think this concerns T72; confirm?”).
  • A reply on everything it touches, a skip reason on everything it leaves; all of it in fwd log.
  • One-command revert for each direct power: unlink, reject, edit.
preliminary point of view

The triage agent is cheap, observable and optional, or it will burn down. The evidence is Gas Town, whose mayor cost ten times a normal session and merged a pull request despite failing tests, and whose author declared it dead while keeping the work graph underneath. GitHub’s agentic workflows answer the same risk with hard caps per run and a written failure record; Linear prices its grooming agent per run with tokens at cost. So the triage agent here gets exactly the powers whose worst case is one revert: linking, appending, proposing, approving within a policy. The powers whose worst case is lost work, cancelling and retracting, cost a person one approval. Daniel expects to have stronger opinions once he has watched it run; this split is the starting point, not the verdict.

The person

Comments on code or on tasks are the normal way to talk to either agent; a message addressed to someone is the way to talk about anything else. Approvals, review acceptance and re-triage are single verbs in the panel or the CLI. A person’s inbox holds questions from agents, replies, forwards, review requests and “a task was created from your comment” pointers, with the same three statuses, and it never fills with the fine-grained churn of proposed subtasks unless they are mentioned.

“Proposed status” means the task or relation is created and drawn as a ghost until approved; the requester is notified it exists. “Ask in a message” means plain text to someone who may do it; there is no proposal object. Policy is configuration, not code; this table is the default.

Statuses

Message status

Free text with no type. Active until someone settles it; Resolved when the question is answered, the suggestion acted on or declined, or the comment addressed; Deleted only by its author. Priority (now, next, later) is set by the author and may be re-triaged.

Notification status

Unread when routing creates it; Read when injected into an agent’s context or opened by a person; Dismissed by its recipient. What the recipient did is never on the notification; it is a reply in the thread.

Preliminary, and what to watch for

  • The rights split is provisional. Daniel will revise it after watching real sessions. The first thing to watch: how often a link of the triage agent’s gets reverted, and how often a proposed task sits undecided.
  • Musing versus instruction. The triage agent decides whether “what if we…” becomes a Proposed task or an Open one. If it guesses wrong in either direction the cost is one verb, but the pattern will tell us whether a default (always Proposed) is safer.
  • Notify, don’t narrate. When an agent creates a task from someone’s message, that person gets a pointer to the task, not a paragraph. Watch whether people still want the one-line “why I did this”; if so it belongs in the task’s why, which they will read anyway.
  • Which questions belong in the graph. Not every implementer question should be a message; some are better asked in the session that raised them. The working rule is: record it if someone other than the current session needs it or if it blocks a task; mark it now only if the answer changes what gets built next. A real standard comes after a few weeks of this.
  • Delivery reliability. Hooks are the portable path; the Claude Code socket push is a bonus that may change underneath us. The Stop guard is the last line: an implementer should not end a session with unread notifications.
  • Cost. The triage agent’s per-run caps and per-day budget are guesses. They exist so the first surprise is a skipped notification, not a bill.
