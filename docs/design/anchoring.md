# Code anchors: representation, resolution, and what happens when the code moves

Draft for discussion, 2026-09-24. P unless marked. Evidence in `../research/code-annotations.md` (sections 2 and 3) and Manifold's pointing contract (`../research/manifold-crossover.md`, item 3). The design for robustness is `../research/anchoring-robust-proposal.md`; its first two milestones are built (see "Implementation notes").

**Requirements added by Daniel on 2026-09-25 (R):** an anchor must be *deterministically identifiable* from what was anchored (file identity plus span content and basis), not a random id; it must be robust for files that are partly or wholly unstaged at annotation time, including spans that cross arbitrarily many staged and unstaged hunks; it must follow changes as the file is edited and as hunks are staged and unstaged; creative hashing, storing the actual content, and CRDTs (Automerge was named) are all in scope, including a separate non-Ankurah store dedicated to span resolution if robustness needs it. The proposal's first two milestones meet the first two: a key made from the content's git object id, and a basis for a file in any state, split into pieces across staged and unstaged hunks. They follow the lines between any two versions git can name (the working tree, the index, a commit, a blob); following edits in the editor as they happen is the version tracker and editor sessions of the later milestones (Daniel, 2026-09-28, "Anchor robustness: the first two milestones now; the goal is highlights as a CRDT over git history").

## What an anchor is

An anchor is an interior sub-entity of a file at a particular version: "lines 120 to 134 of `src/net/ws.rs` as they were in blob `9f3c…`", or with no lines, the whole file at that version. Forming it gives that range its own identity (`C40`). Messages (through their `anchor` field: `../DECISIONS.md`, D58, "Message subjects as typed reference fields") and tasks (through `anchored_at`) target the anchor, not the file. The anchor's defining fields never change; what changes is our knowledge of where that range is *now* in some other version of the file, which is a separate, cached computation with its own honesty states.

Manifold's distinction carries over exactly: **location certainty** (do we know where it is?), **content change** (has the selected text changed?) and **availability** (does it exist at all in this version?) are three separate facts, and an unresolved location never replaces the anchor's identity.

## Representation

The version an anchor counts its lines in, its *basis*, is git's object id of the content the person was looking at, whether that content was committed, staged or only in the working tree: git gives content an id without a commit, so a dirty file has a basis as stable as a committed one. The anchor's identity is a hash of what was anchored, so two people pointing at the same lines of the same content make one anchor. Beside the basis the anchor keeps more than one way to find itself, as every robust system in the survey does (GitHub review comments, Gerrit, CodeStream, Hypothesis):

| Field | Purpose |
|---|---|
| `repo`, `path` | the repository (identified by its upstream) and the path relative to the checkout root |
| `basis_blob` | git's object id of the content seen, written to the repository and pinned under `refs/fwd/basis/<id>` so `git gc` keeps it |
| `head_blob`, `index_blob` | the file's HEAD and index blobs at that moment, absent when it had none |
| `nearest_blob`, `basis_patch` | whichever of those two differs least from the basis, and a unified diff from it (from an empty file when there is neither) to the basis, up to 256 KB: a checkout without the basis rebuilds it and checks the rebuilt content's id before trusting it |
| `pieces` | the anchored lines as runs that were committed, staged only, or in the working tree only at that moment (on an anchor made on a revision, only in that revision), each with its lines in HEAD and in the index |
| `anchor_key` | `fwd-anchor:1:` and the SHA-256 of the repository's entity id, the path, the basis and the line range: creating an anchor whose key exists returns that anchor |
| `span_key` | `fwd-span:1:` and the SHA-256 of the anchored text with its whitespace runs made one space, for recognising two anchors on the same text |
| `start_line`, `end_line` | the range in the basis, 0-based, end exclusive; columns later |
| `whole_file` | true for an anchor on the whole file, which has no range |
| `side` | where the lines were chosen: the file on disk (`worktree`), or the left (`base`) or right (`modified`) side of a diff showing a revision (Diff views, below) |
| `anchored_text` | the exact selected lines, so a match can always be verified |
| `context_before`, `context_after` | up to three lines each, for fuzzy recovery (Hypothesis uses 32 characters of prefix and suffix; a few lines is the code equivalent) |
| `commit_sha` | the commit checked out when the anchor was made |
| `blob_sha` | only on anchors made before `basis_blob` existed: the HEAD blob the first cut mapped a clean selection onto |
| `symbol_path` | optional tree-sitter path (`impl WsClient > fn reconnect`), later |

**Whole-file anchors.** A reference to a whole file is an anchor with no line range (Daniel, 2026-09-28, "A whole-file reference is an anchor with no line range"): the same entity, its key made with an empty range, its text, context and pieces empty, `whole_file` set, and `start_line` and `end_line` both 0. `fwd anchor create --path <file>` and `fwd comment --path <file>` make one when `--lines` is left out, from any file, text or not, and so does a message whose text names a file in double brackets, on disk, in the index or at a commit (task nVE7KTeSqiX0; `data-model.md`, "Inline references"). One such anchor serves every version of the file that holds the same bytes, since its key is its content, so the version a message names goes with the message's reference to it, not on the anchor. It resolves by availability alone (present at its path, renamed, deleted, or not in this checkout) and claims no line. It is a flag rather than optional line fields because the extension's host node, the web page and the routing of code comments read `start_line` and `end_line` from the entity directly: optional fields would have broken all three until each changed, where 0 and 0 keep them working (the unchanged extension puts a whole-file thread on the first line) until they read the flag. Routing and the inbox's sentences read it: a comment on a whole file reaches whoever works a task anchored anywhere in the file, rather than only near its first line, and the sentence names the file by its path alone, never `path:1` (`agents-and-inbox.md`, rule 1).

## Creating an anchor on a dirty file

The editor is often on uncommitted text. The first cut followed CodeStream: a selection unchanged since HEAD was stored against the HEAD blob at the mapped lines, and any other as a worktree anchor with no basis, to be rebased onto a blob once a commit carried it. The content-addressed basis replaces that (the proposal's first milestone): nothing is ever rebased, because content keeps its id when it is staged or committed.

The basis is the index blob when the working-tree file matches the index (git's own comparison, `git diff --quiet`), and otherwise `git hash-object -w --stdin --path=<path>` fed with the file as seen. `--path` applies the repository's clean filters, so the id is the one `git add` will record; the index blob comes first because, when the index already holds the file with CRLF line endings, git keeps them where `hash-object` would convert them (experiment E1 in the proposal's section 6). The blob is pinned with `git update-ref refs/fwd/basis/<id> <id>`, a ref under `refs/fwd/`: never a branch, the index or the working tree.

At the same moment the anchor records the file's HEAD and index blobs and splits its lines into pieces: a line diff from the basis to each of them says, line by line, whether the line is committed, staged only, or in the working tree only, and maximal runs with the same answer (and consecutive lines in each version) are the pieces. A span over a staged hunk, the unchanged lines after it and an unstaged hunk is three pieces. When the index is later committed, that commit carries the index blob's id, and resolution against it answers piece by piece: the staged piece and the unchanged lines are there, the unstaged piece is not (`partial`). When the rest is committed, the commit's blob is the basis and the answer is `exact`.

## Resolution

Resolution answers: where is anchor `C40` in a target version? A target is the working tree, the index, a commit (`HEAD`, a branch, a commit id), or a blob id; a target this checkout does not have is `absent`, with nothing compared. Every answer states three facts apart:

- **location**: `exact` (the anchor's own lines; for a whole file, its own path), `shifted` (other lines, where following the edits put them), `moved` (found elsewhere by its text, or in the file its file was renamed to), `recovered` (a likely place, by similarity), or `unknown`;
- **content**: `same`; `changed`, with a similarity and the resolved lines that are not anchored ones; `gone`; or `unknown` when nothing was compared;
- **availability**: `present`; `partial`, with each run of lines, where it is in the target if anywhere, and where it stood when the anchor was made; or `absent`, because the text is `deleted`, the file is missing (`file_missing`), the target is the HEAD or index version the anchor was made beside, older than its basis, and never held those lines (`before_creation`), or no checkout here has the target (`not_in_checkout`).

They sum to a label: `exact`, `shifted`, `modified` (every line there, with other text among them), `moved`, `recovered`, `partial`, `orphaned` (absent), or `absent` (not in this checkout). The answer also names the target it found (kind, commit, blob, path), how it got there (`same_blob`, `diff`, `fingerprint`, `file`), where the basis text came from, and a hint (the line the anchor was last known at, and how many places hold its text when more than one does). The first cut's `state`, `start_line`, `end_line`, `path` and `confidence` stay beside these for the readers written against them, `state` being the label with `partial` reported as `modified`.

It runs cheap-first and verifies after every strategy:

1. **Locate the file**: at the anchor's path in the target, else where a rename took it (a rename in the target's history, one staged in the index, or for the working tree, an untracked file whose content is a blob the anchor knew). A whole-file anchor is answered here: present (`exact` when its blob is the basis, `modified` otherwise), renamed (`moved`, with the new path), or deleted.
2. **Same blob**: the target's blob is the basis: `exact` at the stored lines, no text compared.
3. **Diff mapping**: the basis text (the pinned blob, else rebuilt from the nearest blob and the patch and trusted only when its id is the basis) is mapped line by line to the target with a Myers diff, lines compared without their line ends. Every line surviving in order is `exact` or `shifted`; every line surviving with others among them is `modified`; some surviving is `partial`, run by run. When the target is the HEAD or index version the anchor was made beside and it is older than the basis (both, for an anchor made on the file on disk; HEAD, for one made on the index), the diff is the whole truth, since the lines it lacks were never there; otherwise a survival below half the lines is only a candidate a search may beat.
4. **Search**: the anchored text as a whole block (the place nearest the anchor's lines, and only `recovered` when the text occurs more than once), else the window of the same length most similar to it by characters, 0.6 or better, with the context lines as a bonus and the distance from the old place as a small penalty: `recovered`. An anchor whose basis this checkout cannot supply (a clone lacking both the pinned blob and the nearest one) never claims more than `recovered`.
5. **Orphaned**: nothing matched. The anchor keeps its identity and its original snapshot; the UI shows it with the original text and offers manual reposition, which creates a new anchor and links it with `supersedes`.

After any strategy the resolved lines are compared with `anchored_text`, and a difference is changed content: `exact` is never claimed when the text differs.

Answers are cached in the anchors' own SQLite file beside the project's database (`projects/<id>/anchors.sqlite` in the data directory), keyed by the anchor's key (its id before it has one), the file's path in the target and the target's blob, with the resolver's version, so a branch switched back to or a stash popped answers from the cache. A resolution is knowledge about one checkout that changes with every commit, so it is no longer written to the anchor entity, where each machine's answers fought over one synced field. Answers made without the basis, and `absent` ones, are not kept. The cache is advisory; any reader may recompute.

## Live buffers in the editor

VS Code shifts a comment thread's glyph as lines are inserted or deleted, but it never reports the shifted range back to the extension (F: `../research/code-annotations.md`, section 1). The extension therefore keeps its own range per open document: on `onDidChangeTextDocument` it applies the content changes to every anchor's range in that document (a plain delta walk), writes the new range to `thread.range`, and treats the result as `shifted`; on save it asks for a proper resolution against the saved text. A commit needs nothing: the content keeps its id. The extension never persists live-buffer positions; they are visit-local.

## Diff views

Both sides of a diff are separate documents with URIs. The sides of VS Code's own diffs that show a revision rather than the file on disk (the index, HEAD, a commit) are `git:` URIs carrying `{path, ref}`; the PR extension's sides carry their own query parameters. An anchor made on the base side stores `side = base` with the base side's content as its basis; on the modified side, the modified side's content.

**Anchors on a revision** (task Iz0HMyk0, "Let a comment, a question or a step anchor lines on a revision's side of a diff", 2026-09-29). So that the old side of a diff takes a comment, a question or a step as the file on disk does, `fwd comment`, `fwd ask`, `fwd step add` and `fwd anchor create` take `--against <index|HEAD|rev>` (a branch or a commit; `cli.md`), and the anchor is formed from that revision's content, as `git show <rev>:<path>` gives it (for the index, `git show :<path>`), in place of the file on disk. It records:

- `basis_blob`: the revision's blob of the file, pinned under `refs/fwd/basis/` as every basis is (the index's blob is otherwise kept only while the index holds it). The anchor's lines are that blob's lines, and the file need not be on disk: HEAD's side of a file the working tree deleted takes a comment.
- `side`: the side of the diff that showed the revision: `base`, the left (the index in the working tree's changes, HEAD in the staged changes), unless `--side modified` says it was the right (the index in the staged changes). The index is on the left of one of those diffs and on the right of the other, so the revision alone cannot say which side the person was on. An anchor made on the file on disk keeps the side `worktree`, as every anchor made before 2026-09-29 has.
- `head_blob`, `index_blob`, `nearest_blob`, `basis_patch` and `pieces` as an anchor made on the file on disk records them: the file's HEAD and index blobs of the moment, the nearer of the two with a patch from it to the basis (empty when the basis is one of them, as it is for the index and HEAD), and the anchored lines as runs committed (`head`), staged only (`index`), or in neither of them. A run in neither was in the working tree only when the anchor was made on the file on disk (`worktree`), and in the revision only when it was made on a revision (`revision`: lines of an older commit that HEAD and the index had lost, or of a commit on another branch).

The key is made from the basis and the lines, as it always is, and not from the side: the same lines of the same content are one anchor wherever they were chosen, so a comment made on the index's side of a file whose working tree matches the index joins an anchor already made on the same lines of the file on disk, and keeps that anchor's side. Which revision an anchor was made on follows from its side and its blobs: the index when its basis is its `index_blob`, HEAD when its basis is its `head_blob` and not the index's, and otherwise a commit, which the anchor does not name. A click on a highlight opens the file on disk at its lines as the working tree has them, wherever the highlight was made (`../DECISIONS.md`, D115; `vscode-extension.md`, Navigating from a step), and a diff the person opens shows it on each side that has its lines.

Resolution against another side is just resolution against another version, so a base-side comment can be shown on the modified side as `shifted`, `modified` or `moved`, and a comment made on the index's side of the working tree's changes is `exact` in the index and `shifted` in a working tree with lines added above it. The HEAD and index recorded beside an anchor made on HEAD, or on an older commit, may be newer than its basis: a line they lack may have been deleted or moved since, so it is searched for as in any other version, and is `deleted` when nothing is found, never `before_creation`, which names lines a version older than the basis never held (Resolution, above). A comment on the base side of a branch diff is usually a question about existing code; on the modified side, a comment on the change; the triage agent of the scope the comment concerns, else the one that serves the whole project, sees both.

## Cross-repo and renames

Anchors carry a `repo` reference, so a project can span repositories; resolution never crosses repos. Renames are followed when the file is located (step 1); the anchor's `path` remains the path at its basis, and the resolution carries the current path.

## What triggers resolution

- Lazily: any read that shows an anchor against a target (`fwd anchor show` and `list`, the extension opening a file) resolves it, answering from the cache when the target's blob is one it has answered for.
- On commit and branch switch: a git observer will re-resolve anchors in touched paths against the new HEAD (none exists yet).
- On demand: `fwd anchor resolve`.
- Never in bulk on a timer.

## What the agent sees

`fwd anchor show` returns, for an anchor, its lines against the agent's checkout (the working tree by default), the three facts and the label, and the original text. An agent acting on `modified`, `partial` or `recovered` anchors is told so, and a comment on an `orphaned` anchor still reaches the agent with the original snapshot; it just cannot claim a current location.

## Tests the implementation must pass

Exact, shifted (insert above, delete above), modified (edit inside the range, trim start, trim end), moved within file, moved across a rename, deleted (orphan), fuzzy recovery after a reformat, an anchor on uncommitted text exact once its content is committed, a span over a staged and an unstaged hunk partial once the index is committed and exact once the rest is, history rewritten by amend, squash or cherry-pick leaving an unchanged span exact, the basis rebuilt from its patch in a clone that never had it, a whole file present, renamed and deleted, base-side anchor shown on the modified side, and the same fixture set run against a live buffer through the extension's delta walk. Plus the two rules borrowed from Manifold and Hypothesis: a mismatch after any strategy downgrades the state, and an orphan keeps its snapshot and identity.

## Implementation notes

The first cut (T8, 2026-09-25) backtracked clean selections onto the HEAD blob, kept every other anchor as a worktree anchor resolved by text alone, and cached resolutions on the entity; milestones M1 and M2 of the proposal replaced it on 2026-09-28.

`crates/fwd-core/src/anchoring.rs` forms anchors (`form` for lines, `form_whole_file`, and `form_on_revision` for either as a revision has the file) and resolves them (`locate`, then `resolve_located`; `resolve_against` does both from a target's name), with the cascade above driven through the `git` executable and a Myers line diff (the `similar` crate). It also builds and applies the basis patch (split after each newline, so the rebuilt content hashes to the basis byte for byte), and backfills anchors of the first cut (`backfill`). `crates/fwd-core/src/sidecar.rs` is the cache. `ops::create_anchor` is get-or-create by key; `ops::resolve_anchor` answers from the cache or resolves and keeps the answer, and backfills. CLI: `fwd anchor create --path <file> [--lines a-b] [--against index|HEAD|<rev> [--side base|modified]]` (Diff views, above), `fwd anchor show <id> [--against worktree|index|HEAD|<rev>|<blob>] [--also <target>]...`, whose `--also` puts each further target's answer under `also.<target>` in the same call, so a reader that needs two versions waits for one process (the editor asked `--also index` while a click could open the staged changes, D48, and asks for none since D115), `fwd anchor list --path <file> [--against ...]`, `fwd anchor resolve`, and `fwd comment --path <file> [--lines a-b] [--against ...] "text"`, which creates the anchor and the comment together, as `fwd ask` and `fwd step add` do with a question and a step.

Anchors of the first cut keep resolving as they did: one mapped onto a HEAD blob follows its lines by diff from that blob, one made on a dirty file searches for its text. Each gains a key and a basis once a checkout can supply one: the HEAD blob it was mapped onto, when this object database holds it; else, for one made on a dirty file, the version an `exact` answer just found its text and both context blocks in, exactly at its lines, which is written to the repository and pinned. Their `pieces`, `head_blob` and `index_blob` stay empty: they describe a moment the first cut did not record.

Not yet built, and in the proposal's later milestones: the fingerprint index and cross-file moves beyond renames (M3), the per-file version tracker with cursors (M4), editor sessions (M5), and the git observer, `known_in`, coincident anchors and shared pins (M6). Two machines creating one key at the same moment can make two entities; the proposal's section 3.7 makes that a relation between them, later.

An anchor stores its path relative to the checkout root (`anchoring::normalize_path`): `--path` takes that form, or an absolute path inside the checkout, which is converted (Daniel, 2026-09-26: "is there a good reason why absolute paths would be problematic? I don't see an issue"; this settles the review dispute in `DECISIONS.md` that had refused them); a path that climbs out with `..`, lies outside the checkout, resolves through a symlink to outside it, or leads into another checkout nested inside it (a worktree under `.claude/worktrees/`, a submodule: a directory below the root with a `.git` of its own) is refused with a sentence saying where it points. Anchors are created from the checkout the command runs in (`fwd whoami` shows it).

An anchor resolves in one checkout on this machine (`checkout_for` in `crates/fwd/src/main.rs`), since the working tree and the index a target names belong to one checkout, and the basis blob may be in only some checkouts' object databases: one that holds it follows the lines by diff from the content they were anchored on, where another rebuilds that content from the patch or searches for the text. The command's own checkout is asked first. When it is one of the anchor's repository, has the target (the working tree and the index always; a revision or blob when it exists there) and holds the basis, the anchor resolves there and no other checkout is asked. Otherwise the other checkouts of the repository that the daemon's registry knows are asked, in the order the daemon first saw them, and the best wins: one holding the basis with the target branch checked out, else one holding the basis, else one with the target branch checked out, else any with the target, the command's own checkout first among equals. With none that has the target the answer is `absent`. The target branch counts only when a branch names the target (never for `worktree` or `index`), and it matters only between clones, whose branches of one name can point at different commits; the worktrees of one clone share their branches. Each checkout is asked the cheapest question first, and nothing more once it could no longer beat the best found so far: whether its object database holds the basis, asked of git once for all the worktrees of a clone, since they share that database (`project::git_common_dir` finds it from their `.git` files without running git); then whether it has the target; then what git says the checkout is now, its upstream and branch. The walk stops when nothing could be better. Until 2026-09-28 every checkout was asked all of this before any resolved, at five git processes each, and a click on a step in the editor waited three seconds on a machine with 57 checkouts of one repository.
