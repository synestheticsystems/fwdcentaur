# VS Code extension

Draft for discussion, 2026-09-24. P unless marked. Platform facts in `../research/code-annotations.md` (sections 1, 4 and 5); projection rules in `../research/manifold-rendering.md`.

## Surfaces

1. **Editor comments and highlights**: comment threads on lines of code, in the working tree and on both sides of VS Code's git diffs; each highlight (lines with a thread not resolved yet) drawn over its lines, its thread opening inline from VS Code's comment icon in the gutter; a highlight on a whole file badging the file's name; comments and questions made in the editor, on the file or on either side of a diff, from the right-click menu or the comment box, going to the task the page shows with their code as the context, a highlight added as a step of that task only when asked for, and a step clicked on the page opening the file at its lines; one's own comment edited in place with VS Code's Edit.
2. **Graph panel**: a webview rendering the task graph: layered by `depends_on`, sub-tasks collapsible, proposals as ghosts, anchors as chips, open messages and notifications as badges; add, remove, propose, link, comment, filter, focus, Back.
3. **Scope view**: a tree view in the sidebar: the scope this checkout works in (intention, tasks), the other active scopes, my inbox, diagnostics.

## Transport

The extension host runs the bundled `fwd daemon start` on activation (the shared startup routine, `daemon.md`) and reads `fwd daemon status`, which prints the daemon's port and the project the window's folder resolves to. The webview is an ephemeral Ankurah node in WASM (the existing browser bindings and the WASM WebSocket client) connected to the daemon's listener at `/p/<project-uuid>/ws`: live queries over Task, Relation, Scope, Message and Notification drive rendering, and edits are ordinary transactions run through the same `fwd-core` pre-checks the CLI uses (R: every client is an ephemeral node). The extension host, which needs git and the Comments API, is a second ephemeral node, native or WASM-in-Node (U: which binding; ankurah-ts is not ready). Storage on both is in-memory; the daemon is always local, so there is nothing to persist.

**2026-09-25.** The daemon now serves a web UI (`web-ui.md`) whose pages are the graph panel and the inbox described here, as an Ankurah node in WASM. Daniel ruled that the extension **bundles** that same Leptos app in its webview (its own ephemeral node), rather than framing the daemon's page. Ruled later the same day: the webview and the extension host are separate JavaScript realms (a sandboxed iframe inside the window, and a Node process; only `postMessage` joins them, and only while the webview is alive), so one node cannot serve both, and Daniel ruled **two ephemeral nodes**: the webview's (the bundled Leptos app in WASM, with its own connection to the daemon) and the host's (comment threads, gutter marks, anchors). The two are consistent through the daemon; `postMessage` between them carries UI coordination only (the daemon's port and the window's project at startup, "open this task", "reveal this anchor", the theme), never graph data. Ruled the same day: the host runs fwd-core's **WASM build in Node** (VS Code 1.138 runs extensions on Node 24, which has a global `WebSocket`, `WebAssembly` and the built-in `node:sqlite` module, and no IndexedDB) over `ankurah-storage-sqlite-node`, a separate Ankurah engine crate that mirrors the native SQLite engine over Node's built-in SQLite from WASM (built 2026-09-25 as a stacked PR on Ankurah's `storage-engine-contract` branch; fwdcentaur pins that line from GitHub by hash and moves to the 0.10.0 API). Git, anchoring and daemon spawning are native-only code in fwd-core, so the host keeps the bundled `fwd` binary for those (child processes), and the node handles reads, live queries and transactions. `ankurah-ts` can replace the WASM build later without changing the design.

**Shipping and updating `fwd`** (ruled 2026-09-25): the extension ships as per-platform packages (as rust-analyzer and Claude Code do) with the `fwd` build inside and spawns the daemon from that copy, so client and daemon are one build and nothing is downloaded at runtime; `fwd.path` overrides. It offers once to copy `fwd` into a user bin dir as the command for agents and terminals (naming the PATH line to add on macOS), records that it owns that copy, and refreshes it when the extension updates; a copy it did not install only gets a notice with the update command. A running daemon on an older build is asked to drain and restart, immediately when no other client is connected and by prompt otherwise; the port file gains the `build` field `daemon.md` lists. Until those packages exist (2026-09-28), an empty `fwd.path` means `fwd` on the extension host's PATH, else `~/.cargo/bin/fwd`, where `cargo install` puts it and which the PATH of a VS Code started from the Dock often lacks; and each build stamps its version with the commit it is made from, which the VSIX carries, so `code --list-extensions --show-versions` tells one build from another (implementation notes, below).

## Editor comments and highlights

So that a person sees in the editor where people and agents are talking about the code, and can ask about lines where they are, one `CommentController` (`fwd`) shows the project's comments on code as threads and marks the ones still open as highlights. A highlight is an anchor with at least one thread whose first message is not resolved (`reviews-and-highlights.md`); an anchor whose threads are all resolved keeps them, marked resolved, and is not drawn. Built 2026-09-28.

**Where they show.** Every open document of a file inside the workspace folder: the file itself (a `file:` document: the plain editor, and the working-tree side of a diff), and the other sides of VS Code's git diffs, which are `git:` documents the built-in git extension serves, with the file's absolute path and a ref in their query (`''` the index; `'~'` the left side of the working tree's changes, which is the index when the file has staged changes and HEAD, with the same content, when it has none; `'HEAD'`; or a commit). Not the `git:` document the git extension opens of its own for each file an editor shows, the version the gutter's change markers compare the file against (the index, or HEAD when the file has staged changes), which it names as the file with `.git` after its name: no person opened it and it is no side of a diff (`src/sides.ts`). Until 2026-09-30 it showed the threads too, and VS Code's Comments panel, which lists every thread under the document it is on, listed each thread twice, under `lib.rs` and under `lib.rs.git` (task Lj8otCIi). For each document, a live query on the anchors in the file's repository-relative path and one on each anchor's messages and one on the steps each anchor is rebuild its threads on every change set: one per root message, its replies as the thread's comments. Each comment is headed by its author's name, the principal's handle, and a person or an agent a message's text mentions reads as `@handle`, in a thread and in the inbox tree alike. Both names are read when a view first shows the principal and kept from then on by one live query on the project's principals, people and agents (`src/principals.ts`), so that the threads and the inbox follow `fwd principal rename` with no reload, as a task's name in a thread's label follows the task's renaming: the authors since task Qn-Vskuy and the mentions since task V_vU3k0l (both 2026-09-30; until then each name stayed as first read until the window reloaded). A reference in a comment's text to anything else, a task, a decision, a scope, lines of code or a message, reads as the thing is named now too, in a thread and in the inbox tree alike (since task 2EUFcIRc, the same day; until then it kept the name first read): the name is read when a view first shows the thing and kept from then on by a live query on that one thing, for as long as an open document's threads or the inbox show it (`src/referents.ts`), the store a thread's label and its line of what its highlight is joined to read a task's title from too, so that a renaming (`fwd task amend --title`, `fwd scope rename`, a message edited) draws again only the documents whose threads show the thing, and the inbox tree only when a message behind it mentions it. Where each anchor sits in the version the document shows comes from `fwd anchor list --path <file> --against <version>` (`worktree`, `index`, `HEAD` or the commit): when the document opens and when an anchor arrives; in the working tree after each save and whenever a change leaves the document as the file on disk (VS Code reading the file again after an agent wrote it, an undo back to the saved text); on a revision whenever the git extension serves it again (the index after a stage). Between those, each edit moves each anchor's lines as it is made: lines before an edit keep their numbers, lines after it move by the lines it added or removed, and lines it falls inside grow or shrink with it, while text put in exactly at the start of a highlight's first line, or of the line after its last, goes outside it, so that lines added right above a highlight move it down, where the CLI finds it once the file is saved, rather than growing it. The extension draws the highlights on the moved lines again at once, and the hover below and its "open" read the same lines, so that right after an unsaved edit a hover finds a thread on the lines drawn with its highlight and gutter mark. Until 2026-09-29 the hover read the lines as the threads were last built: after the first edit since a save, once the CLI answered the placing that edit asks for (VS Code hands that edit over with the document not yet dirty, its dirty flag following in an event of its own), half a second to a second later; after a later edit, only when something else built the threads again, the save's placing at the latest. VS Code also moves drawn highlights and threads along with the text by itself, by rules of its own: a drawn highlight takes in a line typed at the start of its first line, and a thread moves whole, by as many lines as its last line moved. It never tells the extension where it moved a thread, whose `range` stays where the extension last put it (VS Code 1.139.1: the workbench keeps the moved range in its own copy of the thread), so the hover cannot read a thread's `range`; the extension puts the threads on its lines when it next builds them. A placing the CLI began before a save leaves the lines as the edits moved them, since the CLI may have read the file before the save wrote it, and the placing the save asks for comes next. Until the CLI first answers, a thread in the working tree sits on the lines its anchor was made on, when it was made on the file on disk; a revision shows only the anchors whose lines the CLI found in it, so lines added in the working tree show nothing on the index or HEAD side, and the working tree shows an anchor made on a revision (which counts that revision's lines) only once the CLI has found it there. A thread's label says where its anchor sits when its lines are not there as they were (`anchor modified`, `moved`, `recovered`, `partial`; `orphaned` with the lines it was made on, its thread then on the whole file); the thread is marked resolved when its root message is, and its label then says `resolved`; the first thread of a highlight that is a step also says whether the step is checked, for each task whose checklist it is on (`Step of “Review: the retry loop”: checked`), and does not say `resolved` when every step it moves with is checked, which says so already. References in a comment's text, which a posted message stores as `[[<id>]]`, read in a thread as links that name them in a few words (The thread box, below), and in the inbox tree as a person's `@handle` or the thing's name in brackets, as in the CLI's text output.

**How a highlight is drawn.** Its lines get a background (the colour `fwd.highlightBackground`), a gutter mark and a mark in the overview ruler (`fwd.highlightRuler`): one `TextEditorDecorationType` over whole lines, which VS Code moves with edits while the file is open. A highlight on the whole file, an anchor with no line range, is drawn nowhere in the text (`../DECISIONS.md`, "A whole-file reference is an anchor with no line range"): its thread is on the file in the working tree (not on the other sides of a diff), and while any of its threads is open the file's name carries a badge, `◆` with the number of open threads in its tooltip, in the explorer and on its tab. The badge comes from a `FileDecorationProvider` over a live query on every whole-file anchor in the project, so it shows on files that are not open. A status-bar item counts the highlights in the active editor's file, on lines and on the whole file; clicking it goes to the next thread.

**Opening a thread** (`../DECISIONS.md`, D98, "In VS Code a highlight's thread opens from the gutter's comment icon, not when the cursor enters its lines"). So that clicking or selecting in highlighted code does not unfold its conversation over the code, a highlight's thread starts closed, and VS Code's comment icon in the gutter, on the highlight's last line, opens and closes it inline; the cursor or the selection entering or leaving the lines leaves the thread as it was, and the extension sets a thread's `collapsibleState` only when it makes the thread (closed) and when the hover's "open" link is followed. Daniel, 2026-09-28: "its kind of obnoxious that the thread auto expands when you click the highlighted region in vscode. Can we disable that and just use the chat icon in the gutter for that?" D98 narrows D47 (A highlight's page in the browser shows only the highlighted text; the extension shows its threads inline on focus) on its "on focus" half: the threads still show inline in the editor, opened from the gutter, and the browser half stands. Until D98 the extension opened a thread when the cursor or the selection entered its lines and closed it when they left. A hover on a highlighted line shows the first three lines of each of its threads not resolved, with the author and the number of replies, and an "open" link that opens the thread.

**Resolve and Unresolve** are on a thread's title bar, as fwd: Resolve and fwd: Unresolve. Resolve runs `fwd message resolve <root>`, and Unresolve `fwd message unresolve <root>`, which sets the root message back to active and forgets who resolved it and when; either way the thread follows its root message through the live query. On the first thread of a highlight that is a step, fwd moves the step with the thread (`../DECISIONS.md`, D99, "Checking a step resolves its highlight's first thread, and resolving that thread checks the step; each control says it does both", which superseded D91), so that there the same two actions read fwd: Resolve and Check the Step and fwd: Unresolve and Uncheck the Step (the thread's `contextValue` is `unresolvedStep` or `resolvedStep` rather than `unresolved` or `resolved`), and the status bar names the tasks whose steps moved. Which thread is a highlight's first is fwd-core's rule (`rules::first_thread`, which the host's package exports), and which highlights are steps comes from a live query on their standing `step_of` relations, so the actions and the label follow a step checked on the page or with `fwd step check` as it happens. There is no action that checks the step alone: D99 retracted the Check step that D91 gave a thread meant to stay open, since checking a step now resolves its thread. Until 2026-09-28 Unresolve was a transaction through the host's node, since the CLI had no opposite of resolve.

**Editing one's own comment** (task rRHro34D, after Daniel asked an agent on 2026-09-28 whether it could edit a question it had sent him, and the only fix was a second question in another thread). So that a comment is corrected where it stands, VS Code's own comment editing maps to `fwd message edit`. A comment the window's principal wrote (`fwd.as`, else the project's person, as for the inbox, found by its id and kept, so that an agent the window acts as keeps its Edit when it renames itself) carries `own` as its `contextValue`, and the comment's title bar offers Edit (an icon, `comments/comment/title`) on such a comment and on no other, since a message's author edits it. An agent that succeeded a comment's author edits the comment too (`cli.md`, "Messages"), but the window does not offer it Edit, since the extension's node reads principals by name and not who succeeded whom: such an agent edits it from the CLI or the page (task 0v1yNbNb, "Offer Edit in VS Code on a comment whose author the window principal succeeded"). Edit puts the comment in VS Code's editor (its `mode` Editing), holding its text as its author would type it again: a person as `@handle` where no other principal of the project has the handle, a decision as `[[D12]]`, anything else (a person whose handle another principal shares among them) by the first eight characters of its id in double brackets, as fwd-core's `references::editable` writes it (`src/references.ts`, `editable`), so the editor shows names and each resolves back to what it named. Beneath the editor, Cancel and Save (`comments/comment/context`): VS Code hands either the comment with the editor's text as its body. Save runs `fwd message edit <message> -- "<text>"`: the message keeps its id, its thread and its place, the comment shows the new text labelled `edited` (as an edited message always is), and whoever the new text names and the old one did not hears of it (`agents-and-inbox.md`, rule 13). A refusal (a name that fits nothing, a blank text) comes back as an error message in the CLI's words, and the comment stays in its editor, holding what was written, to correct (VS Code 1.139.1 leaves a comment's editor open when one of its actions has run; the extension closes it by showing the comment in preview). Cancel shows the text as it was. While a comment is in its editor, the thread keeps that comment as it is when the live queries draw the thread again, so what is being written stays.

**Making comments and asking questions.** New comments and questions start on lines of the file on disk and of every revision a side of a diff shows, and, with VS Code's comments on a file, on the whole file on disk: a whole file's threads show on the file itself and on no revision, so a revision's side takes no comment or step on the whole file. On a revision's side (the index's in the working tree's changes, HEAD's and the index's in the staged changes, a commit's), each command below that anchors lines also passes `--against` the revision (`index` for the git extension's `''` and `~`, `HEAD`, or the commit) and `--side` of the diff that showed it (`base` on the left, `modified` on the right: the side of the diff in the active tab that shows the document, else the side the git extension puts it on, the index's own document on the right of the staged changes and every other on a left), so that the lines are anchored as that revision has them, and the anchor says whether they were chosen on the code as it was or on the change (task Iz0HMyk0, "Let a comment, a question or a step anchor lines on a revision's side of a diff", 2026-09-29; `anchoring.md`, "Anchors on a revision" and Diff views). Until then a side of a diff that showed a revision took none, since the CLI anchored lines of the file on disk only. The lines, or the file, become a highlight whose thread the comment or the question starts. Where it goes depends on the window's current task (below), as Daniel ruled on 2026-09-28 (`../DECISIONS.md`, D92, "A new highlight made in the editor with a task current is a comment or a question on that task, with the highlight as its context; adding a step is a separate, explicit action"). With no task current, a comment box that fwd's items open says "For the agents working here" (one opened with VS Code's own + says VS Code's "Type a new comment": What a comment box says, above), and the box's buttons are Send to agents, which runs `fwd comment --path <file> --lines a-b "<text>"` (without `--lines` for the whole file), which routing sends on, and Ask, which runs `fwd ask --path <file> --lines a-b "<text>"`, a question asked of no one in particular, which the triage agent of the scope this checkout works in answers, else the one that serves the whole project. With a task current, fwd's box says "A comment or a question on <title>, about this code", and the buttons are Comment on the task, which runs `fwd comment <task> --path <file> --lines a-b "<text>"`, a comment on the task with the highlight as its context, which reaches the task's assignee and the triage agent of the task's scope, and Ask, which runs `fwd ask --about <task> --path <file> --lines a-b "<text>"`. Neither makes a step. Adding a step of the current task is an action of its own, taken only when asked for: Add as a Step of the Current Task on a thread's title bar (an icon, while a task is current) runs `fwd step add <task> <anchor>`, making the highlight the thread is on the task's next step, and the right-click menu's items for it (below) make the selected lines, or the whole file, a highlight that is the next step, with its first comment (`fwd step add <task> --path <file> --lines a-b "<text>"`, without `--lines` for the whole file), which fwd posts after making the step, so that the comment reaches the task's creator and assignee (`agents-and-inbox.md`, rule 14; the whole file's item since task wmNoucjv, "Make a whole-file step's first comment reach the task's parties: create the step before its comment"). Until D92, with a task current, the box's one button, Add as a step, made every new highlight a step. The CLI's text refusals (a reference that names nothing) come back as an error message, and the draft stays.

## Graph panel

**Rendering.** React with @xyflow/react for the canvas (DOM nodes, so badges, inline editors and VS Code theme tokens are ordinary CSS), elkjs `layered` computed in a Web Worker for the `depends_on` DAG, dagre as a synchronous fallback for small graphs. No positions are stored on entities; a visit-local layout cache keeps the arrangement stable across small updates and Back.

**Node card**: short id, title, status as a small mark, assigned scope as a colour band, badges for open messages, Proposed subtasks, anchors, and a "changed since you last looked" mark. Ghost style for `Proposed` tasks and `Proposed` relations. Collapsed sub-task groups show `(+n)` with an exact count (Manifold's omission rule); a sub-graph omitted by a filter shows the count of omitted nodes, never nothing.

**Edges**: `depends_on` solid with arrowhead (partial order, never drawn as a timeline); `subtask_of` as nesting or a light bracket, not an arrow; `motivated_by` and `discovered_from` dotted and off by default; `anchored_at` as a chip on the node rather than an edge.

**Interactions**: add task (title, why, after, under; direct or propose by a toggle that remembers its last state); link by dragging from a node's handle (creates a relation with the kind chosen from a small menu; cycles are refused with the cycle highlighted, the daemon's answer, not the panel's guess); remove or propose removal; comment on a node (a message whose typed `task` field names it, `../DECISIONS.md`, D58, "Message subjects as typed reference fields"; routed like any other); approve or reject a Proposed task or relation from its ghost; open a task's detail (what, why, done_when, relations, messages, anchors with jump-to-code); filter by scope, label, ready, mine; focus a node and set the neighbourhood depth; search.

**Back and passive change** (Manifold's rules): a Back stack of view states (filter, focus, depth, selection, layout cache) with a checkpoint before any filter or focus change. When agents mutate the graph while the panel is open, changes are highlighted rather than applied silently: new nodes appear with a mark and the layout is re-run only in the affected region, with "n changes since you last looked, re-layout?" as the action for large passive changes. A selected node that a new filter would hide stays selected and visible with a "hidden by filter" mark rather than being rebound.

**Scale**: collapse by sub-task groups and hidden nodes keep the DOM under a few hundred nodes at a time; the daemon's neighbourhood query is bounded and returns omission counts.

## Scope view and inbox

A tree view with three roots: This checkout's scope (the scope the checkout is bound to, else the one its branch names: intention, editable inline; tasks with readiness and their assignees), Active scopes (each with the tasks in progress in it and who is assigned them), Inbox (notifications for me with status; ack and dismiss inline), Diagnostics (cycles, orphaned anchors, old proposals). Until 2026-09-29 the design gave each teammate or agent a scope of its own, with a heartbeat and staleness, which went when scopes lost their owner (`../DECISIONS.md`, D108); none of this view is built beyond the Inbox. Clicking anything opens the task, the anchor in the editor, or the graph focused on it.

- Content Security Policy allows only the bundled script, stylesheet, WASM module and images (the project's mark, `mark.png`, which the stylesheet shows before the page's name), and `connect-src` to those files and to the daemon's loopback address: its WebSocket, and the two HTTP routes the page asks before it opens the socket (`/health`, `/projects`). The panel's tab shows the same `mark.png`, as a browser's tab shows it as the page's favicon.
- `retainContextWhenHidden` is off; the panel persists its view state (filter, focus, Back stack) with `setState` and rebuilds from live queries on show. As built (The page in a webview, below), that state is the route alone, with the scope the pages list by in it: the other filters, the focus and what the task panel's Back returns to start afresh when the page is shown again.
- Theme tokens from VS Code CSS variables; no custom colours beyond scope bands.
- All essential operations have keyboard equivalents (Manifold's accessibility gate); dragging is never the only way to link.

## Implementation notes (T14 proof of concept, 2026-09-25)

`extensions/vscode` is a TypeScript extension bundled with esbuild. Since 2026-09-26 its inbox and its comment threads read the project through the extension host's own node (`crates/fwd-host`, below) with live queries, so they change when the project changes instead of when a timer asks the CLI again. On activation the extension runs `fwd daemon start` and `fwd daemon status` in the first workspace folder; when the status names a project, it loads the package the build copied into `dist/` (`fwd_host.js` and `fwd_host_bg.wasm`) and joins a node to that project's socket, and a folder that belongs to no project gets no node and no message. The inbox tree is a live query on the notifications of the principal the extension acts as (`fwd.as`, a name or an id read as `--as` reads one, so that a name two or more principals of the project share is refused with them listed; else the project's person) that are not dismissed, shown in `fwd inbox`'s order (unread first, then priority, then oldest first), each with the text of the message behind it, where a person or an agent it mentions reads as the handle it has now, and anything else it mentions by the name it has now; marking read and dismissing are transactions through the node, and the tree redraws when the live query hears them, so the 15-second poll is gone and the refresh button only runs the query again. The node finds the principal the extension acts as once, the first time it is needed, and the extension keeps its id from then on, through the refresh button and a new node, until `fwd.as` changes (`src/fwd.ts`, `actingAs`): the inbox follows that id, only that principal's comments offer Edit, and every command the extension runs through the CLI gets that id as `--as`. So when an agent the window acts as renames itself (`fwd principal rename`), after which `fwd.as` gives a name no principal has, nothing changes but the name shown (task 2EUFcIRc, 2026-09-30; until then the refresh button and a new node looked the old name up again and found no one, and the inbox stopped). A window reloaded finds `fwd.as` anew, so by then it must give the new name, as `fwd principal rename` says. Each open document of a file inside the workspace folder, the file or a side of a git diff, gets a live query on the anchors in its repository-relative path, one on each anchor's messages and one on the steps each anchor is, and every change set rebuilds that document's threads and highlights (Editor comments and highlights, above). Still through `fwd --format json` (child processes): starting the daemon and reading its status; everything that needs git: creating a comment or a question (`fwd comment [<task>] --path <file> --lines a-b` and `fwd ask [--about <task>] --path <file> --lines a-b`, which anchor the lines) and a step on new lines (`fwd step add <task> --path <file> --lines a-b`), each with `--against <revision> --side <side>` on a revision's side of a diff, finding where each anchor sits in the version a document shows (`fwd anchor list --path --against`), and finding where a highlight's lines are in the working tree before opening it (`fwd anchor show`); resolving a thread and setting it back to active (`fwd message resolve`, `fwd message unresolve`); editing one's own comment (`fwd message edit`); and replies from a thread or the inbox (`fwd reply`). The task graph is the web UI's page in a webview since 2026-09-26 (below); the proof of concept's hand-written graph panel, which ran `fwd graph` every five seconds and wrote through the CLI, is gone. `deactivate` frees every live query, subscription guard and the context before it closes the node, because each of them holds the node and the timer it runs, and frees the context only once no call still uses it (Closing the node, below). Not built: passive-change handling, and the later additions listed at the end of Editor comments and highlights. Back is built on the page's task panel only, as a way back to where a task was opened from (A clicked task, full screen with Back, below), not as the stack of view states the Graph panel section describes.

**Highlights, diff sides, the current task and navigation (2026-09-28).** The code: `src/comments.ts` (the controller, one `FileThreads` per open document with its live queries, placement, line tracking, threads and drawn highlights; the hover, the count and Resolve), `src/sides.ts` (which version a document shows, from its `git:` query, and the arguments that anchor lines as that version has them), `src/badges.ts` (the whole-file badges), `src/current.ts` (the current task and its status-bar item), `src/reveal.ts` (opening a highlight in the file at its lines), `src/references.ts` (references in text read as names, and in a thread drawn as links, skipping code as fwd-core does), `src/principals.ts` (the name each person and agent of the project has now, which the threads and the inbox show) and `src/fwd.ts` (running the binary, the settings, and the default binary). It answers two messages from the extension: `route` moves the page, and `probe` reports the document's title, origin, URL, text and stylesheets, what the page last said about itself, what the Content Security Policy refused, and the webview's state, for the headless test, which has no other way to see into a webview; a probe may carry an event, which the script sends first: a mouse event on the first element a selector finds, or an event on the page's window as the page sends one (how the test clicks a step).

The daemon admits only the webview origins the extension registers with it (`daemon.md`, Security; `crates/fwd/src/serve.rs`), since any extension's webview, a Markdown preview with scripts or a notebook's output can run script, and names a registered origin in its answers (`web-ui.md`, on the daemon's address). VS Code gives an extension no way to read its webview's origin (the API the extension targets, 1.90 up to the 1.139 the test runs, has no `webview.origin`), so the script's first message to the extension carries the document's `location.origin`; the extension registers it (`POST /webview-origins`, sent from the extension host, from this machine and with no `Origin`, like the CLI's control calls) and answers `admitted`, and the page's boot waits for that answer (five seconds at most, after which it boots anyway and says what it cannot reach), while its module loads. The page tells the script how it is doing (a `fwd:state` event: `failed`, or its connection's state; `web-ui.md`), the script relays it to the extension, which rebuilds a page that failed or lost the daemon when a command opens it again (above), and asks for the registration again each time the connection drops, since a restarted daemon has forgotten it; the page's own retries then get back in. Nothing in the extension polls while its node is connected; only after the node has lost the daemon does it ask `fwd daemon status` again, until the daemon answers (When the daemon restarts, below).

**When the daemon restarts (2026-09-28).** So that the inbox tree, the threads, the highlights and the badges keep following the project when the daemon restarts, as it does at every install of a new build, the extension joins its node to the daemon again. In event order: the daemon stops, and the node's socket to it closes. Ankurah marks each of the node's live queries as waiting for a daemon (its log says "No durable peers available for remote subscription setup" every five seconds until one is back: waiting, not a failure), and its WebSocket client starts retrying the address the node joined at, half a second later, then half a second longer each time, up to ten seconds apart. The extension hears the socket close (`host.connectionState()`, below) and asks `fwd daemon status` one second later, then after two, four and so on up to thirty, until the daemon answers for the window's project. It never starts a daemon itself: one stopped to install a new build stays stopped until something else starts it, as `fwd watch` waits for it (`crates/fwd/src/watch.rs`). Nor does the other call the window makes by itself, placing a document's highlights (`fwd --no-autostart anchor list`): with no daemon running, the CLI refuses it and the threads stay where they are. A placing does not outlive its document's threads either: when the document closes or the window deactivates, the extension kills the placing under way and asks for none after, since a call it started would otherwise run on after its extension host had exited, and a placing whose daemon stopped runs on until the CLI gives up on the daemon, up to ten seconds later, and at once when the daemon comes back on another port (`daemon.md`, "Stop neither refuses nor drains"); until 2026-09-30 such a placing waited for good when the daemon came back on another port. So a closing window leaves a stopped daemon stopped (task lK-_4TEE). Meanwhile the views show what they last had, and Mark read and Dismiss, which go through the node, fail at once with Ankurah's "No durable peers available for fetch operation", which the extension shows. Once the daemon answers, the extension joins a new node at the port it answers on and opens each live query the views hold again on the new node: the inbox's, each open document's anchors and each anchor's messages, the whole-file anchors and theirs. Each view goes on reading its old query's results until the new query has answered, then reads the new one, so nothing empties while the node changes, and what changed while the daemon was away shows then. Every call through the node goes to the new node from then on; the old node's context is freed and its socket closed once the calls under way on it have settled (Closing the node, below), and the old node goes when the last of its queries has been replaced. A daemon that goes away again meanwhile is waited for again.

What the old node does alone, and why the extension replaces it anyway: when the daemon comes back on the same port, as it does whenever that port is still free (`daemon.md`), Ankurah's client gets back in and registers the node's queries again, so the views follow the project again by themselves (before the extension replaced its node, the headless test's restart check passed on that alone, and a scripted Node run showed it after outages of three and forty seconds). But the client retries only the address the node was made with, so it never finds a daemon that came back on another port (its old port taken while it was down: the headless test holds it, and without a new node the reply made after the restart never shows); a node offered a different system halts and stops retrying for good; and a query Ankurah gave up on stays given up. So the extension joins a new node after every restart, even when Ankurah has put the old socket back: one path for every case, and a fresh query for every view. Ankurah could follow a moved daemon in place only if its WebSocket client asked for the address before each retry, from a function its caller gives it (which could read `fwd daemon status`), rather than keeping the one it was made with. A page open in the webview when the daemon moved keeps trying the old port as well, until a command opens it afresh (above).

**Closing the node (2026-09-29).** `deactivate` closes the node, and a new node put in the old one's place lets the old one go, without freeing anything a call still uses (task gQAnXJKM, "Close the extension host's node safely while a call is in flight: freeing the wasm context while it is borrowed throws"). wasm-bindgen lends a value it handed JavaScript to each function of the package that takes it, from the function's first step until its promise settles, and `free()` on a lent value throws "attempted to take ownership of Rust value while it was borrowed". Every read and write through the node takes the context (whom the window acts as, a principal's handle, a task's title, a message's text, what a reference names, marking a notification read or dismissed) and holds it until the daemon has answered. `close` used to free the context one turn after the live queries, so a read still waiting for its answer then made `deactivate` throw: CI's `extension` job hit it on 17b12b9 (run 36621654854) and on 85580d4 (run 36625522470), two of the first five runs of the whole suite there, in the check that `deactivate` frees the node, and a window reloading or closing could hit it too (the page's reload bar now offers a reload, task pNkDAdfq). `rejoin` freed the old node's context at once, under any read still waiting on it. Now the node keeps each call's promise until the call settles (`Joined.lend` in `src/node.ts`), and `HostNode.close` goes in this order: it refuses new calls and new live queries, which fail with "the fwd node is closed", so that no call starts while it waits; it stops hearing the node's socket, which it is about to close; it frees every live query and subscription guard, so that nothing more reaches the views; it waits a turn, in which the queries' unsubscribes go out over the socket, and then until every call under way has settled; and only then does it free the context, close the socket and drop the node. `rejoin` sends every call to the new node from the moment the new node is in place, and lets the old node go the same way once the calls under way on it have settled; `close` waits for an old node still going as well. A call settles when the daemon answers it, when the node's socket closes (Ankurah fails the requests waiting on the daemon it lost), or at once when the node has no daemon to ask, so `close` sets itself no deadline: only a daemon that kept the socket open and never answered would keep it waiting. The suite checks both twenty times over in one test, through two hooks the extension's `Api` gives it, `reconnect` (join the window again after `deactivate`, as activation does) and `rejoin` (put a new node in the node's place now). Each round deactivates while reads are under way (the inbox's refresh, which asks the node whom the window acts as): from an I/O callback, right after four more reads, whose answers cannot arrive before the event loop next polls for I/O, however soon closing would free the context; and a millisecond later than the round before after the last node took its place, so that across the rounds `deactivate` meets that node's live queries before, while and after they answer. Then it joins the window again and puts a new node in the node's place while reads are under way on it. On the code before the change, putting the new node in place threw in all twenty rounds, and `deactivate` in nineteen (in the first, the node had not yet joined the daemon again since an earlier check stopped it, so its reads failed at once, with nothing to wait for); a first version of the check, which deactivated from a turn of its own rather than from an I/O callback, never saw `deactivate` throw there, since the daemon answered within the turn the old `close` waited. With the change, all twenty rounds pass, in twenty to twenty-five seconds.

The container gets the checkout, git's object store (so that the build stamps the checkout's commit, which the suite checks) and, while `crates/fwd-host` takes the engine by path, the Ankurah worktree, all read-only. It copies the checkout's files into a copy of its own at a short path, writing only the files whose content changed, so that cargo rebuilds only what changed; then it does what `scripts/test-extension-headless.sh --here` does on any Linux machine with `xvfb-run`: it builds the page, `fwd` and the host's node (wasm-pack, whose wasm-opt pass takes about five minutes, runs only when cargo has built the library again), and runs `xvfb-run -a npm test`, whose exit code is the script's. The copy, the build outputs and the downloads stay on two named volumes: on Daniel's machine the first run, with no image and no volumes, took ten minutes and a second one a minute, and all forty-six checks passed in each. CI's `extension` job (`.github/workflows/ci.yml`) runs the same `--here` on ubuntu-latest. It needs the Ankurah branch that carries `storage/sqlite-node` (`feat/storage-node-sqlite-wasm`) on GitHub, and clones it beside the checkout; until that branch is there, the job says so in a notice and runs nothing more.

`crates/fwd-host` (2026-09-25) is the host's node the Transport section rules for, loaded by the extension since 2026-09-26 (above): fwd-core compiled to WASM for Node, its own Cargo workspace, built with `wasm-pack build --target nodejs` from that directory into `crates/fwd-host/pkg/` (CommonJS glue beside `fwd_host_bg.wasm`, 2.8 MB in release). `Host.connect(url, timeout_ms)` joins an in-memory node on `ankurah-storage-sqlite-node` to the daemon's socket (`ws://127.0.0.1:<port>/p/<project-uuid>`, port and project from `fwd daemon status`) and rejects with a sentence when the node has not joined in time; `host.context()` feeds the classes the Model derive generates for every model (`Notification.query(ctx, "status = 'unread'")` and the rest, all exported); `host.connectionState()` (2026-09-28), so the extension hears the daemon go away, is Ankurah's signal of the node's socket state (`Connected`, `Connecting`, `Closed` or `Error`), whose `subscribe` calls back with each new state while Ankurah is changing it, so the callback must not call into the package; ten functions wrap fwd-core's operations on the inbox, messages, anchors and task status, taking and returning plain objects and failing with strings, and one more, `first_thread` (2026-09-28), is fwd-core's rule for which thread on a highlight is its first, so that the extension labels a step's thread by the rule the operations follow; everything that needs git stays with the `fwd` binary. Its Ankurah dependencies are temporary: until the Ankurah branch that carries `storage/sqlite-node` is pushed, the engine comes by path from Daniel's worktree (`../ankurah-storage-node-sqlite`), and a `[patch]` points its two git dependencies (`ankurah` and the WebSocket client) at that same worktree so the graph holds one copy of each Ankurah crate. `node crates/fwd-host/smoke.mjs` starts a scratch daemon (its own `FWD_RUNTIME_DIR` and `FWD_DATA_DIR`) and shows on Node 24.13 that the node joins, that a live query on unread notifications hears the mention a CLI comment causes, that the node finds the comment's anchor, replies (the author's `fwd inbox` shows the reply) and reads the thread back, marks the mention read, resolves the comment, claims and submits a task, that the node says its socket is connected and then, as the daemon stops, that it no longer is, and that `close()`, once the script has freed its context and live query, lets the Node process exit on its own (a context or live query left unfreed keeps the node and its timer alive).
