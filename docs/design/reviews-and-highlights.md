# Highlights, their conversations, steps and reviews

The design for highlights on code, the conversations on them, and reviews made of steps, so that people and agents discuss lines of code where the code is, and an agent can walk a person through a change as a checklist, "basically a guided, commented form of my line-by-line workflow". Daniel's spec of 2026-09-28 is the why of task `o5S4VZNL`, verbatim; the headings cite its numbered points. This note was that morning's proposal (commit a591b91). Daniel settled it in the foreground the same day (D39 (A design cluster is settled in the foreground, then filed)), and agents built it that afternoon. Each section gives his words, his ruling and what exists, pointing at the design that holds the detail, and names what replaced any proposal of this note that was turned down.

## What a highlight is

**Asked.** "Active Highlights (two-anchor span with one or more nonresolved comments) need to appear in every file and diff view automatically" (point 1).

**Ruled.** Nothing changed the definition this note proposed. D43 (A whole-file reference is an anchor with no line range) allows a highlight on a whole file, and D41 (A step is an edge from any entity to a task, and the highlight is the step) makes the highlight, not a comment on it, what a checklist points at.

**Built.** A highlight marks lines someone is still talking about: a code anchor with at least one thread whose first message is not resolved. The extension works that out from the anchor's messages and stops drawing the anchor once every thread is resolved (the threads stay, marked resolved); a step stays on its checklist regardless, so a step added without a comment shows there and not in the editor. "Two-anchor span" is read as one anchor, keyed by its repository, path, basis and lines (`anchoring.md`), whose two ends follow the code as far as "Robustness", below, says.

## Where highlights show (spec points 1 and 2)

**Asked.** Highlights "need to appear in every file and diff view automatically" (point 1), and "User can click a highlight and the conversation thread expands inline (as a modal or something like that) and the user can reply/resolve comments there" (point 2).

**Ruled.** D47 (A highlight's page in the browser shows only the highlighted text; the extension shows its threads inline on focus), narrowed by D98 (In VS Code a highlight's thread opens from the gutter's comment icon, not when the cursor enters its lines) on its "on focus" half. D43 (A whole-file reference is an anchor with no line range): "main thing is to avoid drawing the highlight color in vscode for whole-file anchors". D44 (Every kind of entity renders in four modes) gave the anchor a list item, a row and a page beside its lozenge.

**Built.** VS Code draws each highlight over its lines in every open document of a workspace file, the file itself and each side of its git diffs; the thread opens inline from VS Code's comment icon in the gutter, with Reply, Resolve and Unresolve, and a whole-file highlight badges the file's name instead (`vscode-extension.md`, "Editor comments and highlights"). VS Code's Comments panel lists only open documents' threads, so it is no workspace-wide list. The web UI gives each highlight a page, `#/anchors/<id>`, with its lines as they were anchored and its threads; in the VS Code webview the same click opens the editor (`web-ui.md`, "A highlight's page"). This note first proposed that a highlight's lozenge lead nowhere in a browser; that page replaced it.

## The CLI (spec point 3)

**Asked.** "Agents can view/add/comment/resolve hilights using the CLI".

**Ruled.** No ruling named a command; the rulings on steps, assignment and whole files gave the CLI its new verbs.

**Built** (`cli.md`, "Steps", "Messages" and "Anchors"). `fwd comment [<task>] --path <file> [--lines a-b] "text"` makes a highlight and its first thread (the whole file without `--lines`; a comment on the task when one comes first), `fwd comment <anchor>` adds a thread, `fwd reply` answers, `fwd message resolve` resolves and `fwd message unresolve` sets back to active (on the first thread of a step's highlight, checking and unchecking the step with it: below, "A review"). `fwd anchor show` and `fwd anchor list --path` print an anchor's threads and where it sits in the working tree, or `--against` the index, a commit or a blob. `fwd step add|list|check|uncheck|remove` works a task's checklist (`step remove --retire` also resolves a highlight's threads: below, "A review") and `fwd task assign|unassign` its assignee. `step add --path` takes lines or, without `--lines`, the whole file. The CLI anchors lines of the working tree, and with `--against` the lines a revision has (the index, HEAD, a commit), which is how a comment, a question or a step is made on the old side of a diff (task Iz0HMyk0, "Let a comment, a question or a step anchor lines on a revision's side of a diff"). This note first proposed `fwd highlights [--path] [--task] [--all]`; it was never built, since `fwd anchor list --path` and `fwd step list` list a file's and a task's highlights.

## Routing (spec points 4 and 5)

**Asked.** "A notification per each new highlight/reply added by the user are queued into the respective agent's inbox (supervisor if new, commenting agent if a reploy)", and "agent replies to a user comment are queued into the user's inbox as well".

**Ruled.** Nothing was ruled on these two points, which the existing rules met. D45 (Assignment is an optional field on the task, never an edge; the scope edge means where the work happens) sent to the assignee what had gone to the owner of a task's assigned scope, and D46 (Inline references are shadowed by `mention` edges) made the edge, not the text, what tells a person they were named.

**Built** (`agents-and-inbox.md`, rules 1, 2, 6, 13 and 14). A new comment on code reaches the triage agent of the scope it concerns, else the one that serves the whole project, and the assignees of the tasks anchored near it (the owners of the scopes those tasks were worked in until 2026-09-29, when scopes lost their owner: `../DECISIONS.md`, D108); a comment on a task, its assignee and the triage agent of its scope; a reply, whoever wrote what it answers or wrote in its thread, so the person and the agent hear each other; a message naming someone inline, whoever it names; and a comment on a step's highlight, the task's people (below). The commenter is left out.

## A review (spec point 6)

**Asked.** "A new concept of a "Review" exists - with a new tab in the web UI/webview - similar to a task (could even be an actual task type - yeah lets do this)", attaching "a series of anchors/highlights with comments" as "a sort of checklist using the resolve status as a way to mark them off"; and "should it be that the highlight is attached to the task? or that the comment is attached to the task with the highlight as context for the comment?"

**Ruled.** D40 (A review is a task, not a task type): "Review should just be in the title of the task, and maybe a label", though nothing keys on a label. D41 (A step is an edge from any entity to a task, and the highlight is the step): "the highlight itself should be the thing with the step_of link to the task. because the agent is saying "look here""; a step is a `step_of` edge from anything to a task, and a highlight's comments are its own threads. D42 (The checked state is the step edge's status; position is a fractional key now and a predecessor pointer later). D99 (Checking a step resolves its highlight's first thread, and resolving that thread checks the step; each control says it does both), ruled on 2026-09-28 after Daniel resolved a step's thread in VS Code and the step stayed unchecked, then checked a step on the page and its highlight's thread stayed open: "I resolved one of the steps in the steps list, and the highlight didn't resolve. It should." It superseded D91 (Resolving a step's first thread checks the step, and the control says which it does), which had linked the thread to the step one way only, on the condition D99 keeps: "as long as its clear what specifically is getting resolved".

**Built** (`data-model.md`, "Steps"; `web-ui.md`, "A task's steps"). A review is a task whose steps are the highlights to look at, in the order they were added. Its panel lists them under "Steps" with how many are checked ("3 of 8"), each a check box on its edge beside the step's list item (for a highlight, `path:lines`, the basis and its first line: `ws.rs:4-8 2418c54` then `fn reconnect() {`), opening in place onto the highlight's lines and threads; the Tasks list shows "3/8". A step that is a highlight moves with the first thread on the highlight (D99; `rules::move_step_and_thread` in `crates/fwd-core`): checking the step resolves that thread's first message and unchecking sets it back to active, and resolving that message checks the step and setting it back unchecks it, with who and when recorded on both. A highlight that is a step of several tasks has one first thread, so its steps on every checklist move together. A later thread, a reply, a step that is a message or a task, and a highlight no one has started a thread on move alone; none of it notifies anyone, as a check never did. Each control says it does both: the step's box ("check the step and resolve its thread"), with the thread's state beside it on the step's line; the page's resolve on that first message ("resolve and check the step"); the editor's Resolve and Check the Step and Unresolve and Uncheck the Step on that thread, whose label says whether the step is checked (`vscode-extension.md`); and the CLI, whose `message resolve`, `message unresolve`, `step check` and `step uncheck` list what moved with them. Until D91 and D99, checking a step left its threads alone and resolving a thread left its step alone. The reviewer finishes with the task's own transition, whatever is checked; `scripts/smoke-roles.sh` walks a review. This note first proposed a `kind` field, items that were comments checked by resolving them, and a Reviews page; the rulings above replaced the first two with steps, and with no kind to list reviews by, the page went too, as Daniel confirmed that afternoon.

**The example from the spec.** "create a review guide for me for the unstaged changes in this branch focusing on the meaningful changes": the agent creates "Review: …", assigns it to Daniel (`fwd task assign`), and for each material change runs `fwd step add <review> --path whatever.rs --lines a-b "This mutex is necessary in order to serialize X and Y …"`; Daniel reads each step beside its code, checks it off or asks in its thread, and finishes the task.

**Taking a step off** (task 9dvGW0EI, "Take a step off a checklist and retire its highlight in one command: fwd step remove"; the Ankurah review session asked for it at Daniel's request on 2026-09-28, after a review of 172 steps was replaced by fewer, smaller ones and it asked how to archive the old steps so they no longer show, as opposed to checking them off). Checking a step says it was looked at. A step that no longer belongs on the checklist, because its work moved to other tasks or it was added by mistake, comes off it instead: `fwd step remove <review> <its number, or the highlight's id> --reason "..."`, or the remove control on its line on the page, which the review's creator and its assignee alone are offered, since the checklist is theirs (`rules::can_remove_step`). Its `step_of` relation is retracted with the reason, and the highlight and its threads stay. With `--retire`, the page's choice to retire it, the highlight's threads are resolved too, so the editor stops drawing lines no one is talking about any more, while the highlight's page still lists them; resolving its first thread checks the highlight's steps on other checklists, as resolving it by hand does under D99 (Checking a step resolves its highlight's first thread, and resolving that thread checks the step; each control says it does both), and the page's choice names those tasks while the CLI lists the steps it checked. Neither tells anyone, as an unlink and a resolve tell no one. Until then it took `fwd unlink <highlight> step_of <review> --reason` and `fwd message resolve` on each thread's first message: two commands and two ids per step.

## Assigning a review to a person

**Asked.** "The reviews would generally be assigned to a human user".

**Ruled.** D45 (Assignment is an optional field on the task, never an edge; the scope edge means where the work happens): "Assignment should be a single field on the task. not an edge. And the act of assigning should produce a notification"; starting a task assigns it. D87 (Starting a task worked in another scope is refused, with a prompt to switch to that scope first) narrowed the start.

**Built** (`data-model.md`, Task and "Starting"; `cli.md`, "Tasks"). A task has an optional `assignee`, a person or an agent, set by `fwd task assign|unassign` or the assignee control on its panel, and the new assignee is told, never whoever assigned (`agents-and-inbox.md`, rule 7). `fwd task start` makes the starter the assignee, refused while the task is someone else's or worked in another scope; "mine" means assigned to me; the edge to a scope, renamed `worked_in`, says where the work happens. This note first proposed a standing scope per person, or a reviewer field; the ruling made the assignee a field of every task and withdrew the standing scope.

## Routing for a review's steps

**Asked.** The reviewer "would be able to ask questions", and "add followup questions to each of them as a thread".

**Ruled.** D41 (A step is an edge from any entity to a task, and the highlight is the step) put a step's comments on the highlight, not the task. Who hears of them was settled in the same conversation, with no record of its own: adding a step tells no one, and a comment on a step's highlight reaches the people whose checklist it is on. D95 (A burst of comments and additions from one author on one task reaches a person as one notification) changed the first half: a step added now reaches them too, in one notification with the author's comments.

**Built** (`agents-and-inbox.md`, rules 10 and 14). A comment on a highlight that is a step (no task, answering nothing) reaches each such task's creator and assignee, "impl-x commented on ws.rs:5-7, a step of your task Review: the retry loop", and the triage agent, as any comment on code does. So the reviewer's question reaches the agent that made the review, and the agent's first comment on each step reaches the reviewer, which is why `fwd step add` posts it after making the step, on lines or on a whole file. Until task wmNoucjv ("Make a whole-file step's first comment reach the task's parties: create the step before its comment"), a whole file became a step only by commenting on it first and adding its anchor after, so that first comment, posted before the step existed, reached neither the task's creator nor its assignee; `fwd step add --path` without `--lines`, and the extension's item for the whole file, now make the step first. What one author does on one task (steps added, comments on it or on its steps' highlights) reaches each recipient as one notification while it stays unread, which says how many of what, "impl-x added 3 steps and commented twice on your task Review: the retry loop", and lists them on its card (task IxKVGSn0). This note first proposed two rules keyed on the review kind: a comment on a review reaching its author, which the rule above replaced; and the author's items staying silent, with one card per review, which D95 replaced with that one notification.

## The current task as the context for editor comments

**Asked.** "I think that you should be able to open a task in the webview in vscode, and while that task is ope, any comments added to the code would automatically attach to that task, and create a notification to the counterparty, which would be made available in their inbox."

**Ruled.** D92 (A new highlight made in the editor with a task current is a comment or a question on that task, with the highlight as its context; adding a step is a separate, explicit action): "I don't think it should add a highlight as a step when I do it in the vscode ui - more like a question on the task with the highlight as the context for the comment", since a new highlight is "usually either a question or a comment, and should be triaged". D48 (Navigating from a step in VS Code opens the diff or the file), superseded on 2026-09-29 by D115 (Clicking a highlight in VS Code opens the file at its lines in the normal editor, never a diff).

**Built** (`vscode-extension.md`, "The current task" and "Navigating from a step"). The task the webview shows is the window's current task, named in the status bar, which clears it on a click, as closing the panel does. Under the ruling, a new highlight made then is a comment on that task with the highlight as its context, which routing sends to the assignee and the triage agent of the task's scope, or a question about it, asked of no one in particular, to that triage agent; a step is added only by an explicit action (the thread's Add as a step, or `fwd step add`). Task cPwI_2xf built that, with fwd's items on the editor's right-click menu, and landed on 2026-09-28 (`extensions/vscode/src/comments.ts`); until then the comment box made the new highlight a step of the current task. A step clicked on the page opens the file at its lines as the working tree has them, never a diff (D115, built by task HaUnUYA4); until then it opened the diff its lines were changed in, or the file when they were committed, and a modifier-click the other (D48). This note first proposed that comment on the task; the extension was built to make a step instead, which the ruling retracts.

## Inline references (spec point 7)

**Asked.** "All comments (particularly useful for review comments, but all comments in all places) should also be able to attach references to tasks inline with the text".

**Ruled.** D46 (Inline references are shadowed by `mention` edges): "each of them should shadow/be shadowed by and edge which corresponds to the inclusion point", listed on the thing named and not among the message's relations. The ids a writer types follow D35 (Short ids: the page shows the first characters of an id, and the CLI takes them). D125 (Anything a message names in its text is a mention, whatever its kind: a file at a version, a highlight, a person or agent, a task, a decision or a scope), of 2026-09-30, extended it to a whole file at a version, which Daniel asked for that day: "do we have a way of referencing a whole file (for a given commit / unstaged state) and having that appear as a lozenge? we should."

**Built** (`data-model.md` and `web-ui.md`, "Inline references"). A writer types `@handle` for a person, and an id, its first six characters or more, or `D<n>`, in double brackets or after an at-sign, which tries the handle first (commit 69c6e6a, after Daniel was refused typing an at-sign and a task's id on the page). `ops::post_message`, which every client posts through, refuses a reference that names nothing, fits several ids, or is a handle that two or more principals of the project share, stores each as `[[<full id>]]`, and writes one `mention` edge per reference with the message; a person named hears of it (`agents-and-inbox.md`, rule 13). The page draws each reference as the named thing's lozenge and lists the message under "mentioned in" on that thing. A whole file is named by its path in double brackets, on disk (`[[docs/cli.md]]`), staged (`[[docs/cli.md@index]]`) or at a commit (`[[docs/cli.md@HEAD]]`, kept as the commit it named), read in the checkout the command runs in (task nVE7KTeSqiX0, `crates/fwd-core/src/file_mention.rs`): it becomes its whole-file highlight, and the text stores that highlight's id with the version after an at-sign, since the highlight is keyed by its content and cannot say which version the writer named; the page and VS Code draw it as a lozenge naming the path and the version, which opens the file at that version in VS Code and the highlight's page in a browser (`cli.md`, "Messages"). This note first proposed `concerns` relations marked inline; `mention` edges replaced them, and `concerns` stays the triage agent's judgment link.

## Robustness (the addendum)

**Asked.** "(oh, and anchor/highlight robustness too)".

**Ruled.** D49 (Anchor robustness: the first two milestones now; the goal is highlights as a CRDT over git history): milestones M1 and M2 of `../research/anchoring-robust-proposal.md` ahead of the extension, and the goal: "if parts are deleted, the highlight deterministically resizes to reflect the changed/truncated range", "essentially making highlights a CRDT over git unstaged/staged/commit-history".

**Built** (`anchoring.md`). M1 gives an anchor a basis, git's id for the content the person saw, committed or not, and one entity per key; M2 answers, against the working tree, the index, a commit or a blob, where its lines are, whether their text changed and whether they are there at all, run by run. So a highlight on unstaged lines resolves once they are committed, and one partly deleted comes back as the lines that survive. The rest of the goal is milestones M4 and M5, a cursor at each end of a span over the file's versions and editor sessions, which is where each end of one anchor would follow every edit; it is open (below). This note first proposed building the display on the old resolver while M1 and M2 landed beside it; the ruling put them first, and both landed that day (78551c3), before the extension (aa81d6a).
